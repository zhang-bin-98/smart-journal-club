# Paper2PPT 架构文档

> 版本：MVP Architecture v0.2  
> 状态：与 MVP PRD 对齐，可进入实现阶段  
> 产品范围：面向生物医学原创研究论文（Biomedical Original Research Article）的纯前端、Local-first、Agent-assisted PPT 生成 PWA。

---

# 1. 架构目标

Paper2PPT 的架构目标是用尽可能少的组件完成以下闭环：

```text
Biomedical Research PDF
        ↓
     Paper AST
        ↓
Claim–Evidence Model
        ↓
   Story Strategy
        ↓
      Deck AST
        ↓
┌───────────────┬───────────────┐
│ Web Preview   │ PPTX Export   │
└───────────────┴───────────────┘
        ↕
 Agent Revision
```

系统的核心不是“生成一个 PPTX 文件”，而是维护一份可持续编辑、可追溯、可恢复的结构化 Project。

---

# 2. 核心架构原则

## 2.1 Workflow-first

首次生成使用固定工作流：

```text
PDF
→ Parse
→ Understand Paper
→ Analyze Figures
→ Build Claim–Evidence
→ Plan Story
→ Build Deck
→ Validate
→ Commit
```

Agent 在每个阶段处理非确定性判断，不负责自由探索下一步。

---

## 2.2 Structured-first

系统中最重要的稳定对象是：

```text
Paper AST
Deck AST
Revision Transaction
Project Checkpoint
```

Agent 不直接：

- 写 PPTX；
- 写 PptxGenJS 代码；
- 修改底层 JSON 文件；
- 操作 OPFS 路径。

---

## 2.3 Local-first

默认本地保存：

```text
Original PDF
Paper AST
Figure References
Deck AST
Revision History
Agent History
Project State
Figure Cache
```

只有执行模型推理时，必要的：

- 文本片段；
- 页面图片；
- Figure；
- 结构化上下文；

会发送给用户所选择的模型供应商。

---

## 2.4 Biomedical-first

首版只针对：

> 生物医学原创研究型论文。

架构允许针对以下常见研究结构优化：

```text
Mechanistic
Omics / Bioinformatics
Clinical
Translational / Mixed
```

但不会为每一种论文建立独立的数据模型或独立应用。

---

## 2.5 Source-first

科研结论必须尽量保持：

```text
Claim
↕
Evidence
↕
SourceReference
↕
PDF / Figure / Panel
```

模型是解释引擎，不是科学证据来源。

---

## 2.6 Minimal mutation

Revision Agent 默认只修改完成用户目标所需的最小范围。

```text
局部请求
→ 局部上下文
→ 局部 Mutation
→ 局部 Validation
```

不重新生成整个 Deck。

---

## 2.7 Recoverable by default

所有长流程：

```text
work
→ validate
→ checkpoint / commit
```

模型失败、刷新页面、网络中断都不应该破坏最近稳定状态。

---

## 2.8 不过度设计

MVP 不建设：

- 通用 Web Agent；
- Shell；
- MCP；
- Plugin Marketplace；
- 通用文件管理器；
- 云端后端；
- 多人协作；
- CRDT；
- 完整 PowerPoint 编辑器；
- Review 论文工作流。

---

# 7. Project Model

一个 Project 对应一篇固定论文和围绕它产生的演示文稿工作状态。

```ts
interface Project {
  schemaVersion: number

  id: string
  name: string

  createdAt: number
  updatedAt: number

  paperId: string

  currentDeckId?: string
  previousMajorDeckId?: string
  workingDeckId?: string

  status: ProjectStatus
  checkpoint: ProjectCheckpoint

  generationPreferences?: GenerationPreferences

  lastOpenedSlideId?: string

  degraded?: ProjectDegradedState
}
```

---

# 8. ProjectStatus

UI 高层状态：

```ts
type ProjectStatus =
  | "new"
  | "preparing"
  | "generating"
  | "ready"
  | "revising"
  | "exporting"
  | "interrupted"
  | "error"
```

`ProjectStatus` 用于产品状态展示。

真正的恢复逻辑依赖：

```text
Checkpoint
+
已持久化 Artifact
```

而不是只依赖一个 status 字段。

---

# 9. Project 不保存 Provider 为科学状态

Provider 是运行设置，不是 Project 的科学内容。

应用可以记录最近使用：

```ts
interface ModelRunMetadata {
  providerId: string
  modelId: string
  createdAt: number
}
```

用于 Debug / provenance。

但切换：

```text
DeepSeek ↔ GLM
```

不会使：

- Paper AST；
- Figure；
- Deck；

自动失效。

# 10. GenerationPreferences

创建项目时用户只有一个自然语言生成要求。

系统内部可以解析为：

```ts
interface GenerationPreferences {
  rawInstruction?: string

  language?: string
  targetSlides?: number
  presentationMinutes?: number

  audience?: "research"
  focus?: string[]

  presentationType?: "journal-club"
}
```

这些字段是内部便利表示，不需要 UI 做完整参数表单。

如果无法可靠提取，则只保存：

```text
rawInstruction
```

# 15. Biomedical StudyProfile

StudyType 不分裂 Paper AST，只作为分析结果和 Deck Planning Strategy 输入。

```ts
type StudyType =
  | "mechanistic"
  | "omics"
  | "clinical"
  | "translational"
  | "mixed"

interface StudyProfile {
  primaryType: StudyType
  secondaryTypes: StudyType[]

  species?: string[]
  tissues?: string[]
  cellTypes?: string[]

  cohorts?: StudyCohort[]
  groups?: StudyGroup[]

  modalities?: string[]
  interventions?: string[]
  endpoints?: string[]

  confidence?: number
}
```

---

# 16. 为什么 StudyProfile 只是一层 Strategy Input

不创建：

```text
MechanisticPaper
OmicsPaper
ClinicalPaper
```

三个不同 AST。

原因：

- 真实生物医学研究经常混合；
- 转化论文可能同时包含 cohort、单细胞和动物实验；
- Deck Planning 需要组合证据，不是分类后走完全不同系统。

因此：

```text
Paper AST
+
StudyProfile
→ Story Strategy
```

是更稳定的架构。

---

# 17. PaperStory

PaperStory 是面向演示规划的高层论文理解。

```ts
interface PaperStory {
  background: string[]
  knowledgeGap: string[]

  researchQuestion: string[]
  hypothesis?: string[]

  studyDesign: string[]

  mainFindings: string[]
  novelty: string[]
  conclusion: string[]

  limitations?: string[]
}
```

PaperStory 不是科学证据本身。

它必须通过：

```text
Claim / Evidence / Source
```

回到论文。

---

# 18. Claim Model

```ts
interface Claim {
  id: string

  text: string

  category?:
    | "observation"
    | "association"
    | "mechanism"
    | "causal"
    | "validation"
    | "clinical"
    | "method"

  strength?:
    | "descriptive"
    | "associative"
    | "supportive"
    | "causal"

  evidenceIds: string[]

  importance?: "primary" | "secondary"
}
```

`strength` 用于约束：

```text
association ≠ causation
```

Revision Agent 不应该随意提高科学措辞强度。

---

# 19. Evidence Model

Claim 与 Source 之间增加 Evidence 层，可以表达不同证据类型。

```ts
type EvidenceType =
  | "observational"
  | "association"
  | "omics"
  | "spatial"
  | "perturbation"
  | "rescue"
  | "animal"
  | "clinical"
  | "external-validation"
  | "statistical"
  | "methodological"

interface Evidence {
  id: string

  type: EvidenceType
  summary: string

  sourceIds: string[]
  figureIds?: string[]

  supportsClaimIds: string[]
}
```

这样 Deck Planner 可以优先选择：

```text
Observation
+
Perturbation
+
Rescue
```

而不是三个重复表达同一关联的 Panel。

---

# 20. SourceReference

所有关键可追溯内容统一使用一个 SourceReference。

```ts
interface SourceReference {
  id: string

  pageNumber: number

  kind:
    | "text"
    | "figure"
    | "panel"
    | "caption"

  bbox?: NormalizedBBox

  textQuote?: string

  figureId?: string
  panelId?: string
}
```

`textQuote` 只保存必要的短定位文本，不复制整篇内容。

---

# 21. FigureRef

Figure 默认保存：

```text
来源 + bbox + 语义
```

而不是只保存导出后的 PNG。

```ts
interface FigureRef {
  id: string

  label?: string
  caption?: string

  pageNumber: number
  bbox: NormalizedBBox

  panels: FigurePanel[]

  description?: string
  interpretation?: string

  sourceId: string
}
```

---

# 22. FigurePanel

```ts
interface FigurePanel {
  id: string
  label?: string

  bbox: NormalizedBBox

  description?: string

  manuallyAdjusted?: boolean
}
```

用户手工修正 bbox 后：

```text
manuallyAdjusted = true
```

后续：

- Theme change；
- Deck regenerate；
- Provider switch；

默认不重新覆盖。

---

# 23. NormalizedBBox

```ts
interface NormalizedBBox {
  x: number
  y: number
  width: number
  height: number
}
```

范围：

```text
0.0 ~ 1.0
```

Figure 数据与渲染 DPI 解耦。

---

# 24. PDF Engine

PDF Engine 只负责确定性文档操作。

```text
Original PDF
 ↓
PDF.js
 ↓
Text Extraction
Page Metadata
Page Canvas
```

职责：

- PDF 打开；
- 页数；
- 页面大小；
- 文本提取；
- 页面图片渲染；
- bbox crop；
- Source Preview 页面渲染。

不负责：

- 生物医学故事理解；
- Claim 判断；
- Figure 是否重要；
- Slide 规划。

---

# 25. PDF Rendering Strategy

避免全文高 DPI 常驻内存。

```text
Slide / Page Thumbnail
→ low resolution

Vision Analysis
→ medium resolution

Final Figure Export
→ high resolution
```

最终 Figure 通过：

```text
PDF
+
pageNumber
+
bbox
```

按需重建。

```text
 ↓
PDF.js Canvas
 ↓

 ↓
Figure bbox

Label

 ↓
```

# 27. Figure 的手动 Crop

Source Preview / Crop Editor：

```text
FigureRef
 ↓
Render Original Page
 ↓
Show Current bbox
 ↓
User Adjust
 ↓
Update FigurePanel / FigureRef
 ↓
Persist
 ↓
Re-render affected slides
```

不重新调用模型。

---

# 28. 不做 PDF Object Reconstruction

MVP 不做：

- PDF vector path extraction；
- clipping mask reconstruction；
- original font reconstruction；
- Figure 语义对象级重建。

统一采用：

```text
Page Render + Crop
```

满足首版。

# 29. Story Strategy Layer

Paper 分析完成后，不直接让模型“随便生成 PPT”。

先得到：

```text
Paper
+
StudyProfile
+
Claims
+
Evidence
+
GenerationPreferences
```

再进入 Story Planner。

---

# 30. StoryStrategy

内部可实现为少量策略 Prompt / Planning Rules：

```text
mechanistic
omics
clinical
translational / mixed
```

它们不是用户模板，也不是独立子应用。

---

# 31. Mechanistic Strategy

优先故事逻辑：

```text
Background
→ Gap
→ Hypothesis
→ Study Design
→ Phenotype
→ Molecular Change
→ Mechanism
→ Perturbation / Rescue
→ Validation
→ Working Model
→ Conclusion
```

Planner 优先选择因果升级证据链。

---

# 32. Omics Strategy

优先故事逻辑：

```text
Biological Question
→ Samples / Modalities
→ Analysis Overview
→ Global Landscape
→ Key Cell / State / Feature
→ Biological Program
→ Interaction / Spatial / Regulation
→ Validation
→ Interpretation
→ Conclusion
```

明确禁止默认按工具流水线：

```text
QC → UMAP → DEG → Enrichment → CellChat
```

来生成故事。

---

# 33. Clinical Strategy

优先：

```text
Clinical Problem
→ Population
→ Study Design
→ Endpoint
→ Main Outcome
→ Secondary / Subgroup
→ Validation / Sensitivity
→ Interpretation
→ Limitations
→ Conclusion
```

主要 endpoint 的优先级高于视觉上“更有故事感”的次要结果。

---

# 34. Translational / Mixed Strategy

优先围绕 Claim 串联：

```text
Human Evidence
→ Omics Evidence
→ Experimental Evidence
→ Validation
→ Translational Implication
```

不强行分成：

```text
Clinical Chapter
Omics Chapter
Wet-lab Chapter
```

# 50. Agent Layer

使用 Pi Agent Core 作为执行循环。

Agent 负责：

- 模型调用；
- Tool Calling；
- Generation reasoning；
- Revision reasoning；
- 多轮上下文。

Agent 不负责：

- PDF IO；
- OPFS；
- Layout geometry；
- PPTX；
- 本地事务持久化。

```ts
interface ProviderSettings {
```

- Custom Base URL；
- Custom Model ID；
- Routing；
- 多 Provider 混合工作流。

# 53. Provider 切换

```text
只影响下一次模型调用
```

不自动：

```text

```


# 61. Revision Scope

```ts
type RevisionScope =

```

默认选择最小合理范围。

# 62. Revision Transaction

一次用户编辑请求映射到一个 Revision Transaction。

```ts
interface RevisionTransaction {
  id: string

  projectId: string
  deckId: string

  userMessage: string

  scope: RevisionScope

  baseRevision: number

  mutations: DeckMutation[]

  affectedSlideIds: string[]

  createdAt: number

  status:
    | "planning"
    | "validating"
    | "committed"
    | "rolled-back"
    | "failed"
}
```

---

# 63. DeckMutation

Agent 不能 raw edit JSON。

统一通过受控 Mutation：

```ts
type DeckMutation =
  | AddSlideMutation
  | DeleteSlideMutation
  | MoveSlideMutation
  | PatchSlideMutation
  | PatchElementMutation
  | SetThemeMutation
```

所有 Mutation 必须验证。

---

# 64. Revision Commit

Revision 流程：

```text
User Request
 ↓
Resolve Selection / Scope
 ↓
Agent Plan
 ↓
Generate Mutations
 ↓
Apply to Working Copy
 ↓
Schema Validation
 ↓
Source Integrity Check
 ↓
Layout Validation
 ↓
Commit Transaction
 ↓
Persist
 ↓
Incremental Render
```

只有最后 Commit 后 Current Deck 才变化。

---

# 65. Revision Rollback

若任一步失败：

```text
Working Copy discard
Current Deck unchanged
```

不允许留下“只执行了一半”的 Deck。

---

# 66. Undo / Redo

Undo 单位：

> 一个 RevisionTransaction。

例如用户：

```text
“把第5页拆成两页”
```

内部可能产生：

- Patch；
- Add；
- Move；
- Rewrite；

但用户只需一次 Undo。

---

# 67. 用户手工编辑也走 Transaction

包括：

- 文本修改；
- Slide reorder；
- Figure crop；
- 删除元素；
- Theme change；

都统一进入 Deck Mutation 层。

这样 Agent 修改和手工修改共享：

- validation；
- persistence；
- undo；
- revision number。

---

# 68. Scientific Integrity Validation

涉及内容修改时至少检查：

```text
Claim 是否仍有 Evidence
SourceReference 是否存在
Figure 是否属于对应 Paper
Panel 是否存在
因果措辞是否高于 Claim strength
关键组别是否被错误改变
```

不试图自动“证明所有生物学结论”，但必须阻止明显结构性失真。

---

# 69. Layout Validation

至少检查：

```text
Element 是否越界
标题是否明显溢出
Figure 数量是否超出 Layout
关键 Figure 是否过小
空 Slide
```

失败时优先：

```text
换 Layout
→ 减少非核心文字
→ 拆页
```

而不是无限缩小字体。

---

# 70. Source Integrity

任何包含主要科学 Claim 的 Slide，应尽量存在：

```text
claimIds
+
sourceIds
```

FigureElement 必须绑定：

```text
sourceIds
```

修改 Claim / Figure 后要重新验证映射。

---

# 71. Agent Tools

MVP 工具保持少且高层。

最终推荐 Tool Surface：

```text
paper.get
paper.get_section
paper.get_page
paper.get_figure
paper.get_claim

deck.get
deck.apply_revision

deck.render
pptx.export
```

其中读工具允许 Agent 按需取上下文。

所有 Deck 写操作统一经过：

```text
deck.apply_revision
```

一次调用可以包含多个受控 `DeckMutation`，但由 `RevisionCoordinator` 作为一个事务：

```text
validate
→ apply to working copy
→ commit / rollback
→ persist
```

因此天然满足：

```text
一句用户请求
=
一个 RevisionTransaction
=
一次 Undo
```

内部 Mutation 仍然区分：

```text
add-slide
delete-slide
move-slide
update-slide
add-element
replace-element
delete-element
set-theme
set-language
```

但不需要给 Agent 暴露多个相互独立的写工具，减少中间半完成状态。

工具内部不直接暴露：

- IndexedDB；
- OPFS；
- 文件路径；
- raw JSON write。

# 72. 为什么不提供 read/write/bash

Paper2PPT Agent 不需要：

```text
read
write
edit_file
bash
grep
shell
```

因为：

- 工作流固定；
- Project AST 已经结构化；
- 高层工具更安全；
- 更容易验证；
- 更容易 Undo；
- 更容易恢复。

# 75. Generation Coordinator

# 76. Stable Checkpoint

```ts
type ProjectCheckpoint =
  | "project-created"
  | "pdf-parsed"
  | "paper-ready"
  | "figures-ready"
  | "deck-plan-ready"
  | "deck-ready"
```

只有阶段完全成功后更新 Checkpoint。

---

# 77. Checkpoint 对应 Artifact

```text
project-created
→ Project + PDF

pdf-parsed
→ Pages / Sections

paper-ready
→ StudyProfile + Story + Claims + Evidence

figures-ready
→ FigureRef + Panel

deck-plan-ready
→ DeckPlan

deck-ready
→ Current Deck
```

---

# 78. 从 Checkpoint 恢复

例如：

```text
checkpoint = figures-ready
```

则恢复：

```text
Story Planning
→ Deck Planning
→ Deck Generation
```

不重复：

- PDF Parse；
- Figure Detection。

---

# 79. Working Artifact Pattern

所有大范围生成使用：

```text
Stable Artifact
+
Working Artifact
```

例如整套 Deck：

```text
Current Deck
+
Working Deck
```

成功验证后才：

```text
Working → Current
```

---

# 80. Deck 三态模型

Project 中只需要简单的：

```text
Current Deck
Working Deck
Previous Major Deck
```

### Current

用户当前正在编辑的版本。

### Working

正在构建、尚未 commit 的整套新版本。

### Previous Major

整套 Regenerate 前保留的上一版本。

不建设无限版本树。

---

# 81. Regenerate Slide

属于普通 Revision Transaction：

```text
Current Slide
→ Working Mutation
→ Validate
→ Commit
```

一次 Undo 可恢复。

---

# 82. Regenerate Deck

流程：

```text
Current Deck
 ↓
save as Previous Major Snapshot
 ↓
create Working Deck
 ↓
generate
 ↓
validate
 ↓
success?
 ├─ yes → Working becomes Current
 └─ no  → discard Working
```

当前 Deck 在生成过程中保持可用。

---

# 83. Reanalyze Paper

与 Regenerate Deck 分离。

```text
Original PDF
→ update Paper interpretation
```

可以重新生成：

- StudyProfile；
- Story；
- Claims；
- Evidence interpretation。

现有 Deck 不自动删除。

---

# 84. Reanalyze 后的下游行为

Reanalyze 完成后：

```text
Paper AST updated
Current Deck remains
```

用户可以选择：

```text
Regenerate Deck
```

使用新的 Paper AST。

不自动覆盖已有人工修改。

# 85. Local Persistence

推荐职责：

### IndexedDB

保存结构化状态：

```text
projects
papers
deckPlans
decks
revisionTransactions
agentMessages
providerSettings
workflowMetadata
```

### OPFS

保存大文件 / Blob：

```text
original PDF
page render cache
figure cache
temporary exports
generated PPTX
```

---

# 86. 为什么 IndexedDB + OPFS 分工

结构化数据需要：

- 查询；
- transaction；
- versioning。

大 Blob 更适合：

- OPFS；
- 按需读取；
- 避免塞进结构数据库。



并尽量保留内存工作状态。

# 96. Agent History

持久化最小可见历史：

```ts
interface AgentMessage {

  revisionTransactionId?: string

```

- 隐藏 reasoning；
- 全量 Prompt；

# 97. Revision History

普通编辑：

```text

```


不做完整 Git 历史。

# 98. Schema Version

所有长期保存的主要 AST 应包含：

```text

```

包括：

```text

Paper

```

只实现必要 migration，不建设通用 schema platform。

# 101. Error Recovery

常见恢复：

```text

→ retry current stage

MODEL_AUTH_ERROR
→ change API key / provider
→ continue from checkpoint

VISION_ANALYSIS_FAILED
→ retry figure analysis
→ 已完成上游不重跑

PPTX_EXPORT_FAILED
→ keep Current Deck
→ retry export
```

# 102. Provider Failure Recovery

如果 DeepSeek 在中途失败：

```text

→ continue from checkpoint
```

合法。

# 103. Cancellation

所有模型调用使用 AbortController 或等价机制。

### Generation

取消：

```text
abort current request
→ discard incomplete working artifact
→ preserve latest checkpoint
```

### Revision

取消：

```text
abort
→ rollback transaction
→ Current Deck unchanged
```

# 104. Project Reopen

打开 Project 时：

1. 读取 Project；
2. 检查 Current Deck；
3. 检查 Paper；
4. 检查 PDF 是否存在；
5. 恢复 `lastOpenedSlideId`；
6. 如果上次中断，显示恢复入口。

不开启任何自动模型调用。

# 137. Schema Validation 与 Domain Validation 分离

Zod 负责：

```text

枚举合法
```

但 Zod 不负责所有跨对象关系。

例如下面的问题需要 Domain Validator：

```text

figure panel 是否属于对应 figure
slide claimIds 是否属于当前 paper
layoutId 是否存在于 registry
```

因此验证分两层：

```text
Zod Parse
 ↓
Domain Validation
```

# 139. bbox Validator

只有 Renderer 才转换到实际像素 / PPT 坐标。

# 150. Optimistic Concurrency

执行 Revision 前验证：

```text
transaction.baseRevision
==
currentDeck.revision
```

如果不相等：

说明 Deck 已被其他操作修改。

MVP 不做多人并发，但这一检查仍能防止：

- 延迟 Agent 响应；
- 用户同时手工编辑；
- 旧 Tool Call；

覆盖更新后的 Deck。

冲突时：

```text
discard stale transaction
→ 重新基于当前 Deck 规划
```

---

# 151. Undo 的 MVP 实现策略

为了不过度设计，首版不强制构造复杂 inverse mutation。

推荐：

```text
Revision 开始前
→ 保存 Current Deck JSON snapshot
→ 得到 undoSnapshotId

Commit
→ RevisionTransaction 保存 snapshot ID
```

Undo：

```text
读取 snapshot
→ 恢复 Deck
```

因为 Deck AST 是结构化 JSON，通常远小于 PDF / Figure Blob。

这是比通用 event sourcing 更简单、更可靠的 MVP 方案。

---

# 152. Undo Snapshot 保留范围

Snapshot 属于结构化本地数据。

建议：

```text
只保留最近有限数量
```

防止 Revision History 无限增长。

具体保留数量属于实现参数，不写死进 Domain Schema。

Major Regenerate 的：

```text
Previous Major Deck
```

独立于普通 Undo Snapshot。

---

# 153. Revision Commit Algorithm

推荐实现顺序：

```text
1. Read Current Deck
2. Verify baseRevision
3. Save undo snapshot
4. Clone to Working Copy
5. Apply mutations
6. Zod validate
7. Deck domain validate
8. Scientific/source validate
9. Layout validate
10. revision++
11. Persist new Current Deck
12. Persist transaction
13. Refresh affected slides
```

任何 5–9 步失败：

```text
Current Deck 不变化
```

# 160. Schema 与 Prompt 的关系

Prompt 中不手写另一份 JSON 规范。

优先从 Zod / JSON Schema 派生工具描述。

即：

```text
Domain Schema
→ Tool JSON Schema
→ Model
```

避免：

```text
TypeScript 一套
Prompt 文本一套
Tool Schema 又一套
```

三份协议逐渐不一致。

---

# 161. 不让 LLM 直接生成完整 Paper Schema 的所有字段

Paper AST 建议分阶段构建。

例如：

```text
PDF Parser
→ pages / sections / source candidates

Vision
→ figure refs

Biomedical Analyzer
→ StudyProfile / Story

Claim–Evidence Builder
→ claims / evidences
```

最后由 Application Layer 合并。

这样比让一次模型请求输出整个巨大 `Paper` JSON 更稳定。

---

# 162. 不让 LLM 一次生成完整复杂 Deck Mutation

简单修改：

```text
单次 structured output
```

即可。

复杂 Deck-level 修改可以：

```text
Agent plan
→ read required context
→ build mutation batch
→ apply_revision
```

但仍然只 commit 一次。

# 163. 科研强度校验

ClaimStrength 提供最小等级：

```text
descriptive
associative
supportive
causal
```

首版不需要复杂 epistemic ontology。

主要用途是避免明显升级：

```text
associative
→ causal
```

如果 Revision 后 Slide 文本出现强因果措辞，而 Claim strength 不支持：

Validator 可返回 warning / error。

# 164. DomainValidationResult

Domain Validator 使用统一：

```ts
interface DomainIssue {
  code: string
  message: string
  entityType?: ...
  entityId?: string
  severity: "warning" | "error"
}

interface DomainValidationResult {
  ok: boolean
  issues: DomainIssue[]
}
```

### error

阻止 Commit。

### warning

允许 Commit，但可供：

- QA；
- Agent Review；
- Debug；

使用。

---

# 165. 推荐 error / warning 边界

### Error

例如：

```text
Figure ID 不存在
Source ID 不存在
bbox 越界
layout 不存在
baseRevision 过期
Slide schema 非法
```

### Warning

例如：

```text
Result Slide 没有 claim
Figure 很小
标题偏长
Claim 只有弱 evidence
```

避免因为主观质量判断让系统无法使用。

# 166. 实现级 Schema 验收

进入业务开发前，至少应有以下 Schema Test：

```text
valid mechanistic Paper parses
valid omics Paper parses
valid clinical Paper parses

invalid bbox rejected
missing required source rejected by domain validator
bad claim/evidence link rejected
invalid figure/panel relation rejected

valid Deck parses
invalid element rejected
invalid layout rejected by domain validator

valid RevisionTransaction parses
stale baseRevision rejected
failed transaction does not alter Current Deck

snapshot Undo restores identical Deck JSON
```

# 167. 当前 Schema 决策总结

现在最核心的数据关系可以压缩成：

```text
Paper
│
├── SourceReference
│
├── Figure / Panel ─────────┐
│                          │
├── Evidence ───────────────┤
│                          ↓
└── Claim              Deck Plan
                         ↓
                       Deck
                         ↑
                RevisionTransaction
```

并坚持：

```text
引用使用稳定 ID
来源集中存储
Agent 不 raw write
修改统一事务化
Zod 验结构
Domain Validator 验关系
Snapshot 负责简单可靠 Undo
```

这已经足够支撑首版实现，不需要继续引入更复杂的领域框架。
