## 1. 技术边界与术语

应用是 GitHub Pages 上的静态 PWA，所有项目处理、存储和 PPTX 导出均在浏览器执行，仅模型请求访问用户选择的供应商。

| 术语 | 唯一含义 |
|---|---|
| Project | 一份固定论文及其生成、编辑成果的本地工作单元 |
| Paper | 解析内容、图源与论文理解结果；是 Deck 的证据基础 |
| SourceReference | 原 PDF 中一个可定位来源，是来源页码与原始 bbox 的唯一持有者 |
| Figure / Panel | 论文原图或子图的身份及语义，通过 sourceId 定位 |
| Deck / Slide | 用户编辑的结构化演示文稿及单页；当前 Deck 是编辑真值 |
| DeckPlan | 持久化、可编辑、有 revision、须确认才能生成的学术计划；成功后由 Deck 承接最终结构 |
| Section | 单层叙事章节，kind 表示章节职责，与布局独立 |
| Plan status | draft / confirmed；编辑确认版后回到 draft，不新增 checkpoint |
| Narrative validation | 确定性的结构与叙事错误/警告检查，与来源及布局校验分开 |
| RevisionProposal | Agent 提出的内存修改提案，经用户应用后才进入 Deck 提交 |
| ResearchStrategy | 可配置的研究叙事指导，以 strategyId 选择；不等同于论文研究类型或独立工作流 |
| Revision | 一次用户编辑请求对应的一批原子修改，也是一次 Undo 单位 |
| Checkpoint | 首次生成已经完整持久化的阶段，不是实时进度或后台任务 |
| Current / Working / Previous | 当前已保存 Deck、未提交内存工作副本、整套重生成前保留的唯一上一版 |

前端沿用 React + TypeScript + Vite + Tailwind CSS，以及 Zod、PDF.js、HTML/SVG、PptxGenJS 和 IndexedDB。M0–M6 已完成 React 与 Pi AI 接入；读取的 package.json 声明 `@earendil-works/pi-ai` 为 `^0.85.1`，尚无 Agent Core。M10 才核对官方包文档、实际 lockfile 与浏览器兼容性，安装并锁定同系列兼容的 `@earendil-works/pi-agent-core`；M7 不安装或升级依赖。

固定生成使用显式 workflow：`preparePaper()` 完成 PDF → Figure → Paper 并停在 `paper-ready`；用户查看 Paper Understanding 并显式调用 `prepareOutline()`，得到 DeckPlan 后停在 `deck-plan-ready`；用户编辑、确认后才由 `buildPresentation()` 生成 Deck → 导出。单次结构化模型步骤可以沿用 `requestJson()` 或薄封装，不强行改为 Agent。开放式多轮问答、按上下文选择读取工具、审核后修改使用 Agent Core 的 `Agent` 与工具循环；M10 替换应用自维护的通用轮次循环，不建设第二套 runtime。

界面统一使用已接入 Vite 的 Tailwind CSS 4。页面布局、间距、字体、颜色、边框、响应式及 hover/focus/disabled/选中态均使用工具类；颜色与字体等公共主题值集中在 `src/style.css` 的 `@theme` 中，同类控件复用完整的工具类字符串。类名必须是构建时可扫描的完整字符串，不动态拼接工具类片段。

`src/style.css` 只保留 Tailwind 导入、主题声明和确有必要的全局基础规则；优先使用 Tailwind Preflight，不重复手写 reset，不用组件选择器或成片 `@apply` 重建另一套样式。PDF/Deck 的运行时坐标与尺寸由共享几何计算后通过内联 style 或 CSS 变量传入，固定视觉样式仍使用工具类。幻灯片文字按预览容器比例显示，不随浏览器视口宽度独立缩放；不改变第 3 节的共享几何和 PPTX 导出契约。

依赖方向为 UI → application/service → domain/schema；repository、LLM、PDF、export adapter 实现基础设施接入，由应用用例组合。协调函数管理顺序、取消和提交；领域函数不反向依赖适配器，不引入依赖注入容器、全局事件总线、CQRS、完整 DDD、注册中心或插件平台。

### React 界面边界

React 负责页面、组件和交互状态；选中项、对话框和未提交输入草稿由组件管理，已提交 Project/Paper/DeckPlan/Deck 通过 service/use case 和统一提交入口读取、修改和保存。ProjectWorkspace 组合步骤页；Outline 与 Inspector 的业务异步过程由 service/controller hook 承接，组件和 Agent tool 均不得直接读写 IndexedDB。组件展示提交后的数据，不另建一份可独立写入的 Deck 真值或第二套 Undo/Redo；数据契约、布局、存储、PDF 与导出模块保持普通 TypeScript，不反向依赖 React。

迁移保留现有 Tailwind 主题与工具类，重复控件通过小型 React 组件复用。文字编辑使用稳定的 Slide/Element ID 作为组件标识，输入期间保留草稿、焦点、光标和中文输入法组合状态，避免重新渲染覆盖正在编辑的 DOM；在既定编辑结束时机调用同一提交函数，保持一次编辑一次 Undo。会话、PDF 渲染资源和异步任务的创建与清理不得因组件重新渲染而重复执行；取消、项目切换和卸载沿用现有有效任务检查。

本次选型采用 React 的组件与状态能力，继续使用 Vite 静态构建；不配套引入 Next.js、服务端渲染、全局状态管理库或大型组件库。页面导航沿用第 7 节的 Hash 路由约定。

### 可读性与工程边界

一行表达一个主要动作，复杂页面拆组合组件与 controller；核心业务不在 render/effect 中动态 import。相关参数超过 5–6 个时用具名对象，避免嵌套三元和超长回调。Query 无副作用，Command 名称体现写入；关键不变量和失败语义写短 JSDoc。工具名称、Schema、实现和 UI label 放同一职责模块；不设机械 LOC 上限，三种以上职责混合或难以独立验证时拆分。

M8 引入单一格式/lint 工具（优先轻量方案，如 Biome）及 Vitest 或等价轻量测试，提供 format/lint/test/check 脚本；不并用三套重叠工具。必要全仓格式化单独提交，不混入逻辑迁移。高风险契约与同一 fixture 的检查边界见执行计划，不追求覆盖率或扩大测试矩阵。

## 2. 唯一数据契约

对象使用稳定、不含位置语义的字符串 ID；页码仅用于 PDF 定位，幻灯片序号仅用于显示。ID 创建后不会随重排变化。时间为毫秒时间戳；Project/Paper 仍为 schemaVersion=1，DeckPlan/Deck 在 M9 升为 2。结构版本与 IndexedDB 数据库版本分别管理，迁移见第 4 节。以下 TypeScript 定义为目标形状，实施时使用唯一 Zod Schema 派生类型与工具参数，不维护第二套手写协议。

### 项目与来源

```ts
type Checkpoint =
  | "project-created" | "pdf-parsed" | "figures-ready"
  | "paper-ready" | "deck-plan-ready" | "deck-ready";
type BBox = { x: number; y: number; width: number; height: number };
type Preferences = {
  instruction: string; language?: string; targetSlides?: number;
  strategyId?: string;
};
interface Project {
  schemaVersion: 1;
  id: string; name: string; nameIsCustom?: boolean; paperId: string; pdfAssetId: string;
  currentDeckId?: string; previousDeckId?: string;
  checkpoint: Checkpoint; preferences: Preferences;
  lastOpenedSlideId?: string;
  createdAt: number; updatedAt: number;
}
interface SourceReference {
  id: string;
  kind: "text" | "figure" | "panel" | "caption";
  pageNumber: number;
  bbox?: BBox;
  textQuote?: string;
}
interface FigurePanel { id: string; label?: string; sourceId: string; description?: string }
interface FigureRef {
  id: string; label?: string; caption?: string; sourceId: string;
  description?: string; panels: FigurePanel[];
}
```

用户重命名时在同一事务设置 nameIsCustom=true；解析或理解得到论文标题时，仅在该字段不为 true 时补充项目名称。论文原标题始终保存在 Paper.metadata.title，不随项目重命名变化。

来源集中放在 Paper.sources，Figure/Panel 不复制 pageNumber 或 bbox。figure/panel 类型的 Source 必须有 bbox。Source 不反向保存 figureId/panelId，反向查找由现有关系计算。

pageNumber 从 1 开始。BBox 使用 PDF.js 按原页旋转方向渲染后的整页坐标系，原点为左上角，x/y/width/height 均相对整页归一化；不是相对 Figure 或 Panel 的局部坐标。要求所有值有限，0 <= x,y < 1，width,height > 0，x+width <= 1 且 y+height <= 1。预览、模型页面图片和高分辨率裁图使用相同方向和坐标换算。

### 论文理解

```ts
type ClaimStrength = "descriptive" | "associative" | "supportive" | "causal";
interface Claim {
  id: string; text: string; strength: ClaimStrength;
  importance: "primary" | "secondary"; evidenceIds: string[];
}
interface Evidence { id: string; kind: string; summary: string; sourceIds: string[] }
interface StoryPoint { text: string; claimIds: string[]; sourceIds: string[] }
type StoryTopic = "background" | "knowledgeGap" | "question" | "studyDesign"
  | "mainFindings" | "novelty" | "limitations" | "conclusion";
interface Paper {
  schemaVersion: 1; id: string;
  metadata: { title?: string; authors?: string[]; journal?: string; year?: number; doi?: string };
  pages: { pageNumber: number; width: number; height: number; text: string }[];
  sources: SourceReference[];
  figures: FigureRef[];
  studyProfile?: { type: string; designSummary: string; sourceIds: string[] };
  story?: Record<StoryTopic, StoryPoint[]>;
  claims: Claim[]; evidences: Evidence[];
}
```

未到相应阶段的集合可以为空；paper-ready 要求理解结果及其引用完整。无法从论文得到的故事点保持空数组，不补造事实。研究设计摘要包含理解结果所需的样本、组别、模态或终点，不另建实体本体或按研究类型拆 Schema。

studyProfile.type 是基于论文的简短研究类型描述，不是提示词路由枚举。Project.preferences.strategyId 保存选中的叙事策略，取值来自第 7 节的策略文件；首次选择前可缺省，首次提交 paper-ready 时必须保存有效值。新增策略不修改 Paper Schema 或 TypeScript 枚举。Paper.story 的固定字段用于保存理解结果，不规定汇报章节或幻灯片顺序；实际顺序由满足基础学术骨架的 DeckPlan 决定。

Claim → Evidence → Source 是证据链的持久化方向，不重复存 supportsClaimIds、Evidence.figureIds 等可推导的反向关系。Evidence.kind 使用简短证据类型描述，仅供生成上下文，不作为自动科学强度证明。Paper.story 全部使用 StoryPoint，删除纯 string[] 版本。

PDF.js 提取页文字，模型分批分析候选图页，再基于文本与图源构建论文理解。模型输出先校验并由应用分配/映射 ID，再合并到阶段工作副本，不能一次要求模型生成整个完整 Paper。首版不保存字符级几何或第二套全文副本；文字来源至少可回到页和必要短引用。

### 演示文稿与计划

```ts
type LayoutId = "title" | "text-only" | "figure-full" | "figure-text" | "two-figures" | "panel-grid";
type SlideKind = "title" | "background" | "question" | "method" | "result"
  | "summary" | "discussion" | "conclusion" | "custom";
type SlideElement =
  | { id: string; type: "text"; text: string }
  | { id: string; type: "bullet-list"; items: string[] }
  | { id: string; type: "figure"; figureId: string; panelId?: string; cropOverride?: BBox }
  | { id: string; type: "citation"; sourceIds: string[] };
type SectionKind = "opening" | "background" | "question" | "study-design"
  | "results" | "synthesis" | "limitations" | "takeaways" | "discussion" | "custom";
interface DeckSection {
  id: string;
  kind: SectionKind;
  title: string;
  purpose: string;
  transitionToNext?: string;
}
interface Slide {
  id: string;
  sectionId: string;
  kind: SlideKind;
  title: string;
  purpose?: string;
  message?: string;
  layoutId: LayoutId;
  elements: SlideElement[];
  claimIds: string[];
  sourceIds: string[];
}
interface Deck {
  schemaVersion: 2;
  id: string;
  paperId: string;
  revision: number;
  title: string;
  language: string;
  sections: DeckSection[];
  slides: Slide[];
  createdAt: number;
  updatedAt: number;
}
type DeckPlanStatus = "draft" | "confirmed";
interface PlannedSection extends DeckSection {
  slideBudget: number;
}
interface PlannedFigure {
  figureId: string;
  panelId?: string;
}
interface PlannedSlide {
  id: string;
  sectionId: string;
  kind: SlideKind;
  title: string;
  purpose: string;
  message: string;
  layoutId: LayoutId;
  claimIds: string[];
  sourceIds: string[];
  figures: PlannedFigure[];
}
type ClaimEmphasis = "focus" | "omit";
interface ClaimEmphasisEntry {
  claimId: string;
  emphasis: ClaimEmphasis;
}
interface DeckPlan {
  schemaVersion: 2;
  id: string;
  paperId: string;
  title: string;
  language: string;
  status: DeckPlanStatus;
  revision: number;
  sections: PlannedSection[];
  slides: PlannedSlide[];
  claimEmphasis: ClaimEmphasisEntry[];
  createdAt: number;
  updatedAt: number;
  confirmedAt?: number;
}
```

DeckSection 为一层章节，允许多个 results；kind 是叙事职责而非布局。sections 数组定义章节顺序，slides 数组定义最终页序；同章页面连续且按章节顺序排列，每页必须归属一个有效 section。Claim 归属只由页面的 claimIds 表达，章节不重复持有 Claim 列表。transitionToNext 只作生成/检查提示，不自动导出。

PlannedSlide.purpose 表示该页回答的子问题或叙事目的，message 唯一含义是本页希望听众记住的 take-home。生成时把 purpose 与 message 复制到 Slide；purpose 供 Inspector、生成与检查，不直接导出、不新增 Notes。Slide.purpose 对旧稿和手工空页可缺省，界面明确显示未填写，不能用章节目的冒充页目的；新生成结果页必须保留确认计划的 purpose。message 按布局决定是否直接展示。

Zod 使用严格对象与字段白名单：ID 为非空字符串，引用数组不重复；revision、时间为非负整数，slideBudget 为非负整数，language 非空。草稿可暂留空标题/目的/message，确认时补齐有内容页面的语义字段，result 页必须有非空 purpose/message 与有效 Claim。Plan 初始 revision=0、status=draft；confirmed 必有 confirmedAt，draft 不含该字段。claimEmphasis 是稀疏覆盖：有 entry 时只能为 focus 或 omit，没有 entry 的 Claim 缺省为 brief；DeckPlan 不另设 Claim 层级，也不从 Paper.claims.importance 推导 emphasis。omit Claim 不得被章节/页面继续引用，focus Claim 未有足够结果页时给警告。计划偏好不修改 Paper.claims 的重要性。

slideBudget 是章节的目标页数，不是派生页数。draft 允许预算与实际页数不同；修改预算不自动生成或删除 Slide，新增、删除、移动 Slide 也不自动改预算。Outline UI 必须显示差额；confirmed 时每章预算必须与实际页数一致，且每个保留章节至少一页。

生成必须消费同一 plan ID/revision：Deck 的章节复制确认计划并去掉 slideBudget，页面 ID、sectionId、kind、title、purpose、message、布局、Claim/Source 和图源选择及顺序严格遵循确认版。不得在生成中自行增删页、换图或改预算；容量不适合时返回大纲修正，不静默重规划。Build 完成后由独立的 `validateBuiltDeckAgainstPlan(deck, confirmedPlan)` 检查构建契约，不把生成与计划失配混入叙事校验。

Slide.kind 是内容类别，用于“压缩背景”等操作；它不对应额外布局，章节职责由 DeckSection.kind 表示。一个 Figure 元素仅引用整图或一个 Panel，多 Panel 使用多个元素。panelId 必须属于该 figureId，Panel 与所属 Figure 的 Source 必须位于同一 PDF 页；元素来源从 Figure/Panel 推导，不重复写 sourceIds。

cropOverride 仍是原 PDF 整页坐标：它可用于纠正当前元素的误裁，页码始终取该 Figure/Panel 的 Source，不允许借裁图跳到另一页。有效显示区域为 cropOverride 或原 Source.bbox。Source Preview 可同时显示两者；删除覆盖值恢复默认裁图。更换引用对象时清除旧覆盖值，单纯换布局必须保留。

一个固定学术主题配置同时供预览和导出使用，不在 Deck 中预留 themeId、自定义样式、notes、lockedByUser 或任意元素坐标。DeckPlan 在确认前可编辑、确认后用于生成；首次或候选 Deck 成功保存后同一事务删除临时计划。最终结构由 Deck.sections + Slide.sectionId 持有，Current/Previous 不维护计划版本树。

确认计划和自动生成完成的 Deck 至少有一页；计划草稿可暂时零页但不能确认。手工或 AI 删除可使已有 Deck.slides 为空，零页是有效编辑状态，导出时单独拒绝。删空不清除 currentDeckId、不回退 deck-ready；清除失效的 lastOpenedSlideId 和元素选择。新增手工页允许空标题、空文字和空来源，不为占位提示伪造 Claim/Source；手工新增空页使用 custom，不能把 result 页缺证据作为占位状态。重新选择页时优先有效的原选择，再选相邻页或第一项，零页时不创建虚假 slideId。

### 计划修改与确认

```ts
type SectionPatch = Partial<Pick<PlannedSection,
  "title" | "purpose" | "transitionToNext">>;
type SlidePlanPatch = Partial<Pick<PlannedSlide,
  "kind" | "title" | "purpose" | "message" | "layoutId" | "claimIds" | "sourceIds" | "figures">>;
type PlanMutation =
  | { type: "add-section"; section: PlannedSection; afterSectionId: string | null }
  | { type: "delete-section"; sectionId: string }
  | { type: "update-section"; sectionId: string; patch: SectionPatch }
  | { type: "move-section"; sectionId: string; afterSectionId: string | null }
  | { type: "set-slide-budget"; sectionId: string; slideBudget: number }
  | { type: "update-slide"; slideId: string; patch: SlidePlanPatch }
  | { type: "add-slide"; slide: PlannedSlide; afterSlideId: string | null }
  | { type: "delete-slide"; slideId: string }
  | { type: "move-slide"; slideId: string; targetSectionId: string; afterSlideId: string | null }
  | { type: "set-claim-emphasis"; claimId: string; emphasis: ClaimEmphasis | null };
interface PlanCommitRequest {
  requestId: string;
  projectId: string;
  planId: string;
  baseRevision: number;
  mutations: PlanMutation[];

```

OutlineSession 是唯一计划修改入口，不复用 DeckMutation。所有 patch 必须非空且只包含白名单；ID、paperId、revision、时间与确认信息由应用控制。新增章节可先以零预算空章保存草稿；只允许删除空章，含页章节须同批先移动或删除其页面，不能隐式丢页。章节移动带着整个页面块移动；页移动的 afterSlideId 必须属于目标章节，null 表示该章首位；章节移动的 null 表示开头。不存在目标、自身后移、重复 ID 或非法引用拒绝。预算与页面是两个显式输入：任何页面 mutation 都不隐式改预算，`set-slide-budget` 也不生成或删除页面；差额可保存在 draft 中，但会显示并阻止确认。

设置 omit 必须在同一批次移除该 Claim 引用并修复受影响页；传入 null 删除对应稀疏 entry，使该 Claim 回到缺省 brief；不隐式删除科学内容。草稿允许留叙事问题，结构/引用校验始终执行。内容操作提交后 revision 加 1、更新时间、转 draft 并清除 confirmedAt。确认是独立于 PlanMutation 的 OutlineSession command：运行完整叙事校验、要求用户确认警告，再设置 status、confirmedAt 并增加 revision；已确认计划再次请求确认不重复提交或启动任务。

提交先在副本原子应用，再由 outlineRepository 的一次事务重读 Project 与计划，检查 planId/baseRevision、论文归属、有效 requestId 和第 4 节候选基准；写入成功后才更新内存。并发修改、取消和保存失败不改稳定计划。修改确认计划立即取消旧 build，提交事务也拒绝其旧结果；刷新不自动 build。

计划 Undo/Redo 沿用有限会话内容快照，不跨刷新；恢复内容时 revision 仍加 1、回到 draft，不恢复旧确认或旧生成权限。确认本身不作为可恢复的生成授权快照。计划成功消费或项目关闭后清空快照，不创建计划历史树。

## 3. PDF、布局与 PPTX

PDF.js 只负责文本、页信息、按需渲染和裁图。页面 width/height 使用 scale=1 且应用原页旋转的 viewport 尺寸。初始分析使用适当分辨率图片，最终图源按需高分辨率裁出，完成后释放页面 Canvas。

布局输入是 Slide、固定主题和图像宽高比；输出一份 ComputedSlideLayout，包含标题框、元素框、来源标签框及文字排版参数。框使用归一化幻灯片坐标；HTML/SVG 转成显示尺寸，PptxGenJS 转成 PPT 单位，两端不独立计算第二套几何。

六种布局分别容纳：标题与可选副标题、文字/列表、一个大图、一个图加辅助文字、两个图、3–4 个 Panel。来源标签始终可读；仅有 1–2 个 Panel 时使用单图或双图布局。输出超过布局容量时调整布局或拆页，不隐去元素。

删除元素后，仅在原布局不再适用时按剩余内容回退：无图使用 text-only；一图有辅助文字时使用 figure-text，否则 figure-full；两图使用 two-figures。手工空页允许 text-only 的空文字/空元素集合。布局调整并入同一修改批次，在最终校验前完成；涉及 layoutId 变更时使用包含该页的 slides scope，不扩展到其他页。不调用模型，不因回退隐藏其他元素或清除仍被引用的来源。

只完整渲染当前 Slide，缩略图降采样。图片等比 contain，裁切通过 cropOverride 明确完成，不用隐式 cover 截掉证据。文字使用固定主题的统一字号、行高和长度预算；明显溢出给出提示，不追求 Web 与 PowerPoint 逐像素相同。

PPTX 导出是对已保存 Deck 的只读操作：未保存草稿先保存成功，再捕获 Deck 内容快照及其 ID/revision，确认非零页并通过引用、叙事、布局和资源检查，警告由用户确认；全部必需图片按该快照的引用和裁图从原 PDF 生成，再生成下载 Blob，使用后释放 URL。期间不重新读取正在变化的 Current，不混入新编辑，普通编辑不使这次导出失效；项目关闭、删除导致请求失效或必需资源缺失时停止并提示，不下载部分成果，也不持久化 PPTX 或临时导出文件。

## 4. 存储、生成与迁移

IndexedDB 同时支持结构化数据和 Blob，首版不需要两套存储协调。[MDN：IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)

使用一个带 smartJC 命名空间的数据库，保留现有七个 store；各模块 repository 封装持久化映射与事务，不建设通用 repository 基类或第二套存储。

| Object store | 内容 |
|---|---|
| projects | Project 与最近访问位置 |
| papers | Paper 的最近完整阶段状态 |
| assets | 原 PDF Blob，键由 Project.pdfAssetId 引用 |
| plans | 按 projectId 保存唯一待消费的 PlanRecord：首次计划或候选重生成计划，含 DeckPlan v2 与基准 |
| decks | 当前 Deck 与唯一上一版 |
| history | 按项目保存有限可见消息、已提交修改摘要和修改标识；不存撤销快照 |
| settings | 独立模型设置及 API Key，不归属于项目 |

页面、缩略图、裁图位图和 Blob URL 仅在内存中有限缓存，按需淘汰；资源缓存键包含来源、有效裁图和渲染尺寸，不能复用过时裁图。Undo/Redo 各最多保留 20 个内容快照，可见历史最多保留 100 条；这些上限是实现常量，不写入领域类型。打开项目只把近期相关对话带入模型上下文。

创建 Project、空 Paper 与原 PDF Blob 在同一事务提交；失败不留下可打开的半项目。删除项目同时删除其 Paper、原 PDF、计划、两个 Deck 及历史，不触碰 settings。应用更新不会执行项目清理。

### checkpoint 与三个生成用例

| Checkpoint | 同步持久化的完整产物 | 默认 UI | 下一动作 |
|---|---|---|---|
| project-created | Project、原 PDF、空 Paper | 准备/进度 | 解析 PDF |
| pdf-parsed | 页、文本与文字来源 | 进度 | 分析 Figure/Panel |
| figures-ready | Figure/Panel 与 Source | 进度 | 理解论文 |
| paper-ready | studyProfile、Claim、Evidence、story、preferences.strategyId | Paper Understanding | 用户显式选择生成大纲 |
| deck-plan-ready | DeckPlan v2，含 draft/confirmed | 学术大纲 | 用户确认后生成 Deck |
| deck-ready | Current Deck v2，删除已消费计划 | 幻灯片 | 编辑、检查、导出 |

应用层固定为三个显式用例，不保留自动跨越 Paper Understanding 的组合准备入口：

```text
preparePaper()
→ paper-ready
→ Paper Understanding
→ 用户显式选择生成大纲
→ prepareOutline()
→ deck-plan-ready
→ Outline
→ confirm
→ buildPresentation()
→ deck-ready
```

`preparePaper()` 从最近完整的论文准备 checkpoint 继续解析、图源和理解，保存 `paper-ready` 后必须结束。`prepareOutline()` 只在用户显式发起时规划 DeckPlan：首次规划保存 `deck-plan-ready`，重生成则保存候选而保持项目为 `deck-ready`；两者都停在 Outline 等待编辑和确认。`buildPresentation()` 只接受已确认计划，启动时重读并绑定 projectId、paperId、pdfAssetId、planId、revision、status 与有效任务；生成后在事务内再次核对同一确认版本，通过构建契约校验后才写 Current 并清理计划。已确认但未生成时刷新仍留在大纲，须显式继续。

plan 被编辑、版本变化、项目删除、取消或项目切换都使旧 build 无法提交。生成失败保留 confirmed plan，可重试或返回修改；编辑即 draft。执行过程不持久化半页或模型循环，不新增仅表示 UI 状态的 checkpoint。重生成同样调用 `prepareOutline()` 与 `buildPresentation()`，通过 PlanRecord.mode 区分候选事务，不另建 planning/build pipeline；具体版本切换见第 5 节。

规划模型返回非法结果时最多允许一次 one-shot repair，且仅修复机器可确定的 schema、无效 ID、section 引用、Claim/Source/Figure/Panel 引用、布局兼容和确定性结构一致性问题。background quality、narrative strength、critical discussion quality、ending quality 与 slide allocation judgement 不自动修复；它们作为 Outline 中可定位的 error/warning 交给用户处理。repair 仍失败时保留上一完整 checkpoint 或候选计划，不进入循环重试。

阶段在内存中构建和校验，完成后以一次 IndexedDB readwrite 事务保存产物并推进 checkpoint。阶段启动时捕获 projectId、paperId、pdfAssetId 和前置 checkpoint；提交事务内重新读取 Project，确认项目仍存在、论文关联和前置 checkpoint 未变，且当前任务仍有效，再写入产物。另一标签页已推进阶段或项目已被删除时拒绝旧结果；不能回退检查点或重新创建被删除项目。只更新本阶段负责的项目字段，保留事务中读到的最新名称和其他无关字段。

等待模型、PDF 渲染或网络时不能保持数据库事务打开。单张图识别失败允许记录提示并保留其他完整图源；figures-ready 表示候选页已处理，未找到图的结果可为空，不伪造来源。

恢复时核对 checkpoint 对应的产物和必要原 PDF；缺失或非法时说明原因，不静默伪造 Ready 或清空稳定成果。取消只停止当前任务并丢弃未提交阶段，最后完整阶段保留。继续由用户触发，重做未完成阶段，不重新跑已完成阶段，也不逐页保存半成品。

运行态只在内存按操作管理进度、AbortController 和有效任务标识。每次完成回调都检查任务是否仍有效；取消、项目关闭或操作替换使旧回调失效。提交事务实际写入前再次检查任务；取消发生且事务尚未完成时 abort，事务完成后按已提交结果处理。此规则同样适用于 AI 修改和整套重生成，不只在模型返回时检查一次。持久化 checkpoint 和产物决定可恢复状态，UI 的 generating/exporting 等状态不作为长期真值。

### 临时计划、重新分析与恢复

```ts
type DeckPointer = {
  deckId: string;
  revision: number;
};
type GenerationBase = {
  current: DeckPointer;
  previous?: DeckPointer;
};
type PlanRecord = {
  recordVersion: 1;
  projectId: string;
  plan: DeckPlan;
  preferences: Preferences;
} & (
  | { mode: "initial" }
  | { mode: "regeneration"; base: GenerationBase }
);
```

PlanRecord 是 plans store 的持久化封套，不是新的领域版本树；`recordVersion` 只版本化该封套，`schemaVersion` 专用于 DeckPlan、Deck 等领域对象。每个项目最多一条，preferences 保存此次生成的要求和策略；初次规划原子写计划与 checkpoint，重生成只写候选记录，不回退 deck-ready 或修改 Current 偏好。base 在候选规划开始时捕获并保存 `base.current.revision`，同时记录 Current/Previous 指针；保存候选、计划修改、确认和 build 提交都复核基准。用户放弃才删除候选；取消、失败或刷新保留最后完整计划，半成品丢弃。previous 指针整体存在或缺省，不能只保存其中一个字段。

候选存在期间 Current 仍可正常查看和编辑，不以 UI 锁定实现一致性。每次读取、确认或 build 候选时比较 Current 的 ID/revision 与 base；Current revision 一旦变化，候选即为 stale。stale 候选可查看，但不得编辑、确认或 build，也不能自动重绑定到新 revision；用户只能 discard 后重新规划。候选与 Current 必须在界面上明确区分，原 PDF、Paper 和 Current/Previous 在成功切换前保持不变。

重新分析仅重新运行必要的论文理解，复用完整解析/图源。尚无 Deck 时先取消当前 build/规划任务，在内存准备替代 Paper；以一笔事务核对开始时的 checkpoint、原 Paper 快照和原计划 ID/revision 后替换 Paper、删除失效计划并停在 paper-ready，用户查看新的 Paper Understanding 后再显式调用 `prepareOutline()`。失败/取消保留原分析和计划。没有完整 figures-ready 时先按正常 workflow 补齐，不能跳过前置阶段。

已有 Deck 的重新分析使用产品文档的独立新项目入口：同一原 PDF Blob 内容及完整解析/图源可复用，分配新的 Project/Paper/asset ID，不保留原 Claim/Evidence/story/strategy 或原计划；新项目先停在 figures-ready，完成理解后停在 paper-ready，仍由用户显式生成大纲。来源与图身份可保留原局部 ID，因为引用限定在所属 Paper；不建立跨项目可变引用或新旧分析版本树。原项目及其两个 Deck 完全保留，失败可返回原项目。禁止在原 Paper 上重写科学 ID 使旧 Deck 悬空。

### v1 → v2 迁移

M9 实现纯函数 `migrateDeckV1()` 与 `migratePlanV1()`，复用固定 fixture；不能清空 IndexedDB。已有 v2 重读幂等，不重复生成 ID。读取迁移先在内存完成结构与引用检查，再在一次事务复核原记录未变、原子写入；失败保留原数据，提示重试或使用兼容版本，不伪装为成功。

- v1 Deck 的连续 Slide.kind 段确定性归并：title→opening、background→background、question→question、method→study-design、result→results、summary→synthesis、discussion→discussion、conclusion→takeaways、custom→custom。同 kind 的不连续段仍各成一章；不按 Figure 或标题关键词猜科学结构。章节 ID 用 deckId 与原段首 slideId 的稳定编码派生，在当前 Deck 内保证唯一。
- 为各页补 sectionId，章节 title/purpose 采用对应职责的中性说明。Slide.purpose 缺省、不猜测新科学目的；保持 Deck/页面/元素 ID、页序、所有内容、Claim/Source/Figure 引用、cropOverride、时间与 revision；schemaVersion 改为 2。零页 Deck 迁成 sections/slides 均空。
- Current 和 Previous 都迁移，指针与恢复语义不变。缺基础学术结构的旧稿仍可打开，缺项显示为叙事问题，不能通过插入虚构背景、方法或结论“修复”。Unknown version 或原引用损坏给可恢复错误，保留原始数据。
- v1 deck-plan-ready 计划若页面身份、内容类别和引用均可无歧义映射，按连续 kind 补 sections/budget，旧 message 保留，purpose 用中性页职责，缺 message 留空待编辑；补稳定 plan ID、revision=0、status=draft、时间，claimEmphasis 初始化为空数组，因此所有 Claim 缺省为 brief。不把旧计划视为用户已确认；缺语义成为可编辑叙事错误。
- 无法安全映射时，仅废弃临时 plan 并回到 paper-ready，等待用户显式重新规划；保留 PDF、Paper 和任何稳定 Deck。若已有 Current，checkpoint 仍保留 deck-ready，并走候选重新规划，不能把稳定 Deck 隐藏成未生成。
- 保留七个 store 和 keyPath 时无需仅因对象 schemaVersion 变化提升数据库版本；实际 store/index 变化才提升 IndexedDB 版本并处理旧标签页阻塞。PlanRecord 封套同样需显式转换，不能只改 TypeScript 而直接强转旧数据。

```ts
}
```

Agent 唯一写意图工具为 `deck_propose_revision`，参数由 ApplyRevisionArgs 的 Zod 白名单派生；只生成内存 RevisionProposal，不调用 repository 或写 IndexedDB。绑定值由应用捕获，模型不能改写。

```ts
interface RevisionProposal extends ApplyRevisionArgs {
  requestId: string;
  projectId: string;
  deckId: string;
  baseRevision: number;
  affectedSlideIds: string[];
  createdAt: number;
}
```

请求开始绑定 requestId、projectId、deckId、baseRevision、scope 与选择；section scope 展开为该基准章节的稳定页面集合，新增页必须留在该章。明确页码优先于选择，解析后的实际范围在 UI 展示；Agent 自行扩大范围一律拒绝。一次请求最多一个有效 proposal，重复写调用拒绝；已应用 requestId 以 RevisionRecord.id 去重。所有 AI 修改先显示摘要、影响页与差异，用户点击应用后才进入同一个 DeckSession 提交流程。取消、后续 Agent 失败或手工草稿均丢弃候选，没有后台静默提交。

add/move-slide 的 afterSlideId=null 表示放在目标章第一位，否则锚点必须是该章现有页；move-slide 显式给 targetSectionId，add-slide 使用 slide.sectionId。跨章移动需 scope 同时覆盖原/目标范围，章节数组顺序始终是展开页序的依据；章节 claimIds 随页面引用同步计算，删去章内最后一页时同步移除该空章，均纳入同批撤销。对空 Deck 新增页时由领域入口创建唯一 custom 章并给页面绑定，派生结构纳入同一 Undo。add-element 追加到元素序列。replace-element 必须保留已有元素 ID。目标不存在、重复 ID、移动到自身之后或越过 scope 的操作拒绝。增删/拆并页的 scope 使用受影响原页集合及本批新页，作用范围需与用户意图一致，不用通用 JSON Patch 或任意坐标更新。

### 选择、上下文与提交

发起请求时把明确页码按当前顺序解析为稳定 slideId。显式目标 > 当前 UI 选择 > 近期对话上下文；“这页”直接取当前显示页。多处重复出现的 Figure 如无法由用户范围和选择消歧，先询问，不随机挑一处。

默认上下文为用户请求、选择、目标页、必要相邻页、相关 Claim/Evidence/Source 和生成偏好。涉及叙事或内容取舍时带入所选策略，普通文字微调和问答不重复带入全部策略；策略不能扩大用户指定的修改范围。仅全局请求带入完整 Deck；不默认带入整篇 PDF。读取工具集合为 paper_get_overview、paper_get_claims、paper_get_figure、outline_get_structure、deck_get_slides，全部限定当前项目：分别读取问题/设计/发现，Claim–Evidence–Source，图/Panel/caption/来源，章节及页职责，指定页/章节的 Deck 内容。deck-ready 的 outline_get_structure 从 Current Deck 读取最终章节和页 purpose/message，不要求已删除计划；生成前读当前有效计划。工具参数从实际 Zod Schema 派生，不在 Prompt 另写一套协议。

提交顺序固定为：

1. 基于请求捕获的 Current 克隆工作副本，应用整批修改。
2. 运行结构、引用、scope、叙事和布局校验，确认任务未取消；提案生成时模拟一次，用户应用时基于相同版本再次核对。
3. 打开一次 IndexedDB 事务，重新读取 Project.currentDeckId 与 Deck.revision，检查仍与请求绑定值相同，并拒绝已提交的 requestId。
4. 版本号加 1，原子保存新 Deck、Project.updatedAt 和 RevisionRecord/可见修改摘要；全部写入成功才确认提交。
5. 事务完成后替换内存 Current，更新撤销栈并刷新受影响页。过期响应丢弃并提示用户基于当前内容重试，不自动进入无限重规划。

M1–M6 已验证的 DeckSession 语义继续沿用；M10 更换 Agent runtime 时不另建专用持久化通道。UI 手工编辑调用同一提交函数，用户文字输入、裁图和重排都只形成一个逻辑操作。

手工编辑首次产生内容草稿时，就使待提交 AI 修改的任务标识失效并触发取消，不能只依赖保存后 revision 的变化。草稿期间其他写操作、Undo/Redo、导出、版本切换和应用内离开项目先结束编辑并等待草稿保存；保存失败则暂停后续操作。只浏览或选择元素不视为内容修改。

保存失败保留待保存草稿并显示未保存，稳定 Deck、版本号、历史及撤销栈不前进。用户重试也需重新校验版本，不能用草稿覆盖其他已提交内容。多个标签页不承诺实时同步，提交时的数据库版本检查仍会拒绝旧写入；用户可重新打开最新项目。

### Undo/Redo

会话快照只包含 Deck 的 title、language、sections 和 slides，不含 revision、时间戳、PDF 或位图。Undo/Redo 同样经过版本核对和原子保存，恢复内容但 revision 继续加 1；保存失败不弹出对应快照。Undo 后的新编辑清空 Redo；关闭项目或切换整套版本后清空两栈。

### 整套重生成与上一版

重生成通过 `prepareOutline()` 复用已保存 Paper 和新要求，先持久化 candidate draft plan，停在可编辑大纲，确认后交给同一 `buildPresentation()`；Project.checkpoint 保持 deck-ready。候选记录、刷新和失效规则见第 4 节；不另建第二条 planning/build 流程。

candidate 存在不禁止 Current 编辑。候选保存 `base.current.revision`；任何 Current 提交都按正常 DeckSession 流程进行，并使旧基准候选成为 stale。stale candidate 可查看但不得编辑、确认或 build，用户只能 discard 后重新规划。候选规划、确认和 build 的事务都检查有效任务、Current/Previous 指针及 revision、candidate planId/revision/status；其他标签页修改、计划编辑、取消或删除同样阻止旧结果提交。

全部成功后一个事务保存新 ID 的 Deck（初始 revision=0），原 Current 成为 Previous，切换 Current，保存候选偏好，删除已消费计划和被替代的更早 Previous。失败保留原指针、偏好和最后完整候选计划，不提前覆盖 Previous。候选只保存一份，不保留计划快照树。

恢复上一版时原子交换 Current/Previous，并将成为 Current 的 Deck.revision 加 1、更新时间；失效旧任务并清空会话 Undo/Redo。重复恢复可切回另一版。原项目不提供 PDF 重新关联；重新分析按第 4 节的隔离规则进行，不能破坏 Current/Previous 的 Paper 证据链。

### 交互式 Agent 运行边界（M10）

采用 `@earendil-works/pi-agent-core` 的 Agent 承担多轮消息、工具执行与结束判断。目标使用 subscribe() 事件、abort()、beforeToolCall、afterToolCall、shouldStopAfterTurn 和工具执行模式；具体签名与可用性在 M10 核对所锁版本的官方包文档和声明，M7 不声称 API 已运行验证。缺必要能力时记录阻塞或使用该 runtime 已支持的等价 hook，不回填自写通用 for/while Agent turn loop。

- 提问模式只注册上述读取工具；修改模式额外注册唯一 deck_propose_revision。模式由 UI 显式给定，不用额外 LLM 调用或正则猜测。
- createDeckAgent 组合模型配置、工具与上下文；target/resolveTarget 解析目标；tools 模块聚合名称、Schema、实现和可读 label；revision/validateProposal 与 applyProposal 分别验证、通过应用用例提交。
- 写工具采用 sequential execution；beforeToolCall 核对模式、scope、基准 revision、任务和本轮写次数。afterToolCall 在成功形成提案后结束不必要循环；shouldStopAfterTurn 约束有限轮次、工具次数和上下文预算。工具只读内存快照或调用只读 service，不直接使用 repository/IndexedDB。
- agent_start/agent_end 映射运行状态；message_update 展示助手文本；tool_execution_start/update/end 显示“读取当前章节”“查看 Figure 3B”“拟定修改”“验证布局与来源”等状态，Abort 统一显示已取消。
- 取消、手工草稿、项目/Deck 切换、revision 变化立即失效任务及提案；失效提案无强制应用入口，应用失败不改 Current、Undo 或历史。所有修改仍是一条 RevisionRecord 和一次 Undo。
- 不展示隐藏推理、原始工具 JSON、Key 或 provider 错误体；只持久化有限可见对话和已提交摘要，由 conversationRepository 处理。Agent 运行消息与 proposal 为会话内状态，刷新后不恢复待应用权限。
- 浏览器不引入 Node/SQLite session backend，不注册 bash、任意文件写入、代码执行或通用 MCP 工具。固定 PDF/分析/规划/生成/导出 workflow 不进入 Agent loop。

## 6. 校验与失败处理

Zod 校验输入形状与字段白名单；普通函数校验跨对象关系。二者覆盖实际数据风险，不构建通用校验平台。

| 阻止提交/导出的错误 | 允许提交但需要提示或内容复查 |
|---|---|
| ID 重复、非法元素/布局、非法或越界 bbox | 标题偏长、信息拥挤、图较小、重复表达 |
| Source/Claim/Evidence 不存在，引用其他 Paper | 用户自建页无科学 Claim、次要故事点缺失 |
| Figure/Panel 归属错误，图源 bbox 缺失 | 因果措辞疑虑、论文解释不确定 |
| 越过修改范围、过期/重复请求、无效任务 | 图源识别不完整、需要用户手动裁图 |
| 布局无法容纳元素，导出必需资源缺失 | 无法纯代码判定的科学和视觉质量问题 |

### 叙事校验与编辑兼容

```ts
interface NarrativeIssue {
  code: string;
  severity: "error" | "warning";
  message: string;
  sectionId?: string;
  slideId?: string;
  elementId?: string;
  claimId?: string;
}
// 两个薄入口；布局、资源与 build contract 检查独立运行。
declare function validatePlanNarrative(
  plan: DeckPlan,
  paper: Paper
): NarrativeIssue[];
declare function validateDeckNarrative(
  deck: Deck,
  paper: Paper
): NarrativeIssue[];
```

两个入口可复用普通的 deterministic helper，但不建立 validator framework，也不使用 `DeckPlan | Deck` 联合入口。Plan 入口负责确认前的计划叙事和预算规则；Deck 入口负责构建后及编辑后的实际叙事。二者都不检查构建是否忠实复制确认计划。

基础骨架为开场 → 背景/知识空白 → 问题 → 必要设计 → 结果 → 综合收尾；策略只调整骨架内的结果组织，不取消结构约束。问题可以在 background 章中由 question 页明确承担，不能仅靠章标题猜测；设计是否必要由 Paper.studyProfile.designSummary 或 story.studyDesign 的非空事实确定。最后一个非 custom Section 必须是 synthesis 或 takeaways；limitations 与 discussion 可出现在最终综合之前，但不得单独作为最后收尾。

| 硬错误：阻止确认、正式生成提交和导出 | 可解释警告：允许确认继续 |
|---|---|
| 第一章不是 opening 或第一页不是 title；缺背景或缺研究问题职责 | background 页超过总页数 25% |
| Paper 需要设计而没有 study-design 章或 method 页；结果排在问题/必要设计前 | result 页少于总页数 50% |
| 无 results 章或 result 页；最后一个非 custom Section 不是 synthesis 或 takeaways | 缺 limitations 或 Journal Club 批判讨论 |
| result 页无有效 Claim 或 take-home；计划 result 页另须非空 purpose；被结果页引用的 Claim 无 Evidence/Source | 宽泛/标签式结果标题、空/宽泛 Take-home 提示 |
| section、Slide、元素 ID 重复；引用的 section/Claim/Figure/Panel/Source 不存在或不属于当前 Paper | 无目的重复结论或 Figure、单页 Panel 太多 |
| 页不按章节连续排序；预算与实际页数不一致；omit Claim 仍被引用 | 章节无 transitionToNext、重点 Claim 页数不足 |

ID/引用等结构错误由公共校验函数执行并由应用组合展示，不另写矛盾规则。预算与 omit 规则仅检查 Plan；章节预算在 draft 中可与实际页数不一致并显示差额，确认时必须相等且每个保留章节至少一页；没有隐式豁免。错误与警告均提供稳定 code 和对应章节/页/元素位置；全局问题定位缺失职责及可编辑入口。

警告采用有限普通函数：比例按实际页计数；标题仅用空值、与 Figure 标签相同、有限通用标签等透明条件提示，不能自动证明是否为科学结论句；重复按相同 message 或图源集合且缺少不同 purpose/message 提示。Panel 容量使用既有布局预算，缺过渡/局限按字段或 kind 判定；focus entry 对应的 Claim 默认至少分配两张 result 页，否则提示重点不足。Deck 不持有已消费计划的 focus 偏好，重点分配只在 Plan 校验，Deck 检查只依据其实际内容。无法确定的因果、物种/组别/终点问题标记人工复核，不建复杂关键词科研判定或模型评分器。

保存计划 draft 只要求结构与引用合法，叙事错误保留并可定位；confirmed 计划与新生成 Deck 必须无硬错误。已有非空 Deck 的正常提交同样执行叙事门槛，不允许删除必要结构后仍宣称有效；需要重组时使用同批 mutation 保持结构，或回候选大纲规划。

保留既有编辑兼容边界：手工 custom 空页无需伪造 Claim/来源；从零页新增 custom 页属于草稿恢复，可暂存缺失的基础叙事职责并逐步修复，不能把 result 页缺证据作为草稿豁免。用户明确删空 Deck 可保存且保留 Undo，但零页不能导出或作为自动生成结果。迁移不会因旧稿不符合新叙事而拒绝打开；旧稿的修复提交及 Undo/Redo 允许保留或恢复已有叙事缺陷，但不得新增非历史缺陷，按稳定 issue code+定位比较提交前后及会话快照。结构/引用和事务校验始终不豁免；历史错误持续显示并阻止导出，直到修复。所有豁免由领域提交上下文决定，模型工具不能设置跳过校验参数。

结果页引用的每个 Claim 必须有至少一个 Evidence，Evidence 至少有一个有效 Source。字段合法不代表科学正确：措辞约束放在生成/修改 Prompt 中，保留来源查看与必要警示；不以关键词判断充当科研证明，不强制额外模型复审。

### Build contract 校验

```ts
interface BuildContractIssue {
  code: "built-deck-plan-mismatch";
  message: string;
  slideId?: string;
  field?: "id" | "order" | "section" | "kind" | "layout"
    | "claim" | "source" | "figure";
}
declare function validateBuiltDeckAgainstPlan(
  deck: Deck,
  confirmedPlan: DeckPlan
): BuildContractIssue[];
```

该纯函数专门验证 Build 没有改变 confirmed Plan 的 Slide ID、顺序、section、kind、layout、Claim、Source 与 Figure/Panel selection。它在 build 提交事务前运行，任何 mismatch 都拒绝提交并保留 confirmed Plan 供重试或返回 Outline；title、purpose、message 等生成内容仍按第 2 节的复制/填充契约处理。此检查不属于 Narrative validation，不参与叙事 error/warning，也不建立通用验证框架。

错误只需携带 stage、code、message 与可执行恢复建议。区分 PDF 解析/缺失、模型认证/限流/额度/网络/无效输出、来源/布局、导出、存储额度/写入失败。模型失败不改稳定产物，用户修正设置或网络后重试当前阶段；资源缺失保留可读数据并禁用依赖资源的操作。

## 7. 模型与 GitHub Pages/PWA

### 模型边界

固定候选为 DeepSeek deepseek-v4-flash-vision-exp 和 GLM glm-5.3-flash。候选不是已验证支持列表：M0 核对官方端点、模型 ID、Vision、结构化结果/工具调用、Streaming、Abort 和真实浏览器 CORS，生产界面仅显示通过验证的候选。至少一个可用才进入后续主线，不能用 Node 请求成功替代浏览器验证。

供应商通信复用 Pi AI；固定 workflow 的单次结构化输出保留薄封装，交互式工具循环由第 5 节的 Agent Core 承担，不重复实现通用 SDK 或 Agent runtime。模型设置只有固定候选、Key、连接检查和清除 Key；不存在自定义 Base URL、任意模型或混合路由。所有模型请求使用当前配置，运行中先完成或取消任务再切换。

Key 存在 settings，与项目生命周期分开。Key 不进入模型上下文、history、错误日志、构建变量或导出；供应商请求只发送必要文本与图片。论文和模型内容以文本/受控元素渲染，不执行其中的脚本、HTML 或工具指令。

浏览器直连不成立的候选不启用，也不为其引入代理或后台服务；若全部失败，M0 记录阻塞原因，不能把纯静态部署能力写成已通过。

### 研究叙事策略与提示词

M3–M5 已接入公共规则、五个研究策略和五个阶段提示词。M9 更新 plan/generate 与研究策略以匹配确认计划和 v2 Schema，M10 更新交互助手指导；M7 不修改提示词。职责如下：

| 文件约定 | 职责 |
|---|---|
| `prompts/common.md` | 统一维护来源、科学措辞和用户要求优先等公共生成/修改规则 |
| `prompts/research/<strategyId>.md` | 一种研究叙事策略的适用情况、叙事建议、证据重点和内容取舍 |
| `prompts/stages/<stage>.md` | 实际模型调用阶段的任务说明；不因研究类型复制阶段提示词 |

首批策略为 `general`、`mechanistic`、`omics`、`clinical`、`translational`，最后一项覆盖转化/混合研究。文件名是不重复的稳定 ID；YAML 头信息只含必填字符串 name、description，正文使用 Markdown。增加策略只需新增文件并构建，不维护第二份手写注册表或重复的 JSON 配置。以下仅示意 `omics.md` 的格式，正文实施时遵守产品第 4 节的基础骨架：

```markdown
---
name: 组学与生物信息学
description: 适用于以高通量数据分析和生物学发现为主的研究
---

## 叙事建议
研究问题 → 样本与数据 → 主要发现 → 验证 → 生物学解释。
在基础学术骨架内按论文证据调整结果组织，不要求每部分独立成页。

## 证据重点
围绕主要结论组织 Figure/Panel，说明发现及其验证依据。

## 内容取舍
方法仅保留理解结论所需的信息，避免按分析工具步骤逐项汇报。
```

通过 Vite `import.meta.glob` 配合 `query: '?raw'`、`import: 'default'`、`eager: true` 将文件作为字符串随应用构建分发；由应用读取 YAML 头信息和正文，不能将正文执行为脚本或模板表达式。[Vite Glob Import](https://vite.dev/guide/features#glob-import) 只检查所需文件存在、ID 唯一、头信息格式及 name/description/正文非空，且必须有 `general`。构建检查与应用加载复用同一解析/校验函数；无效配置在发布前阻止构建，不能仅靠浏览器运行时抛错代替，不另建配置框架。

首次论文理解调用带入公共规则、该阶段任务、内置策略目录及其简短正文，在已有调用中完成理解并返回一个 strategyId；应用校验其为可用策略后，与 Paper 和 paper-ready 检查点一同保存到 Project.preferences。不为分类另开模型调用；无法确定策略时选 `general`，不使用类型分支或多策略组合执行器。

规划和生成只带入一个所选策略及当前阶段所需上下文。用户明确的叙事要求优先于策略默认建议，但不能突破证据、来源、数据结构、布局或修改权限；策略不包含工具协议、Schema、事务逻辑和布局坐标，不能覆盖基础骨架、确认版本、`validatePlanNarrative()` / `validateDeckNarrative()` 的硬规则或 build contract。稳定规则由领域 Schema 和确定性校验保证，不能只写进 Prompt。公共规则只在 common.md 维护；运行时数据作为上下文附加，不写入提示词文件。首版不引入模板继承、远程配置或应用内提示词编辑器。

整套重生成复用已保存 Paper；用户要求改变叙事方式时，在原有 DeckPlan 调用中结合策略目录和正文选择策略并形成计划，不重做论文分析。候选 strategyId 随生成偏好保存在 PlanRecord，计划确认后才 build，成功切换 Current 时一同提交，失败不改已有偏好。局部 AI 修改按当次要求处理，不因此改写项目的默认策略；preferences 表示后续生成默认值，不承担各 Deck 的完整提示词历史。

提示词随 Git 管理，修改后重新构建发布；已打开页面在用户接受应用更新前继续使用原构建。更新只影响后续请求，已保存 Paper、DeckPlan 和 Deck 不重写；续跑仍重做未完成阶段，使用当前构建的提示词，不回退检查点。若存量 strategyId 已无对应文件，在下一次相关请求中提示并使用 `general`，下一次生成成功提交时保存实际 ID；单纯查看或恢复上一版不触发重新生成。不持久化提示词快照，不承诺跨应用版本逐字复现生成结果。

### 静态托管与离线

GitHub Pages 托管静态构建产物，不能承担应用的模型代理或任务执行。[GitHub Pages 说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

采用 Vite 构建，通过 GitHub Actions 安装锁定依赖、构建并发布 dist。部署参数来自实际仓库配置，项目站点 base 为 /<仓库名>/，不能硬编码根路径。[Vite GitHub Pages 部署指南](https://vite.dev/guide/static-deploy.html#github-pages)

- 导航使用 Hash 路由，如 /<仓库名>/#/project/<id>，不依赖服务端 rewrite；刷新仍请求项目入口 HTML。
- JS/CSS、图标、字体、PDF.js worker 及所需 PDF 资源均随构建分发，遵循同一 base，不依赖运行时 CDN。
- Manifest 的 start_url 与 scope、Service Worker 的脚本和注册范围均在项目子路径。Manifest 范围不等同于 Service Worker 范围，二者分别正确配置。[Manifest scope](https://developer.mozilla.org/docs/Web/Progressive_web_apps/Manifest/Reference/scope)、[Service Worker 注册](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register)
- Service Worker 按完整构建清单缓存带应用命名空间的版本化静态资源，包含离线预览、PDF 裁图和 PPTX 导出所需的延迟加载模块，以及 PDF.js 的 cmaps、standard_fonts 和 wasm；每个文件按构建时 SHA-256 校验，全部缓存成功后才标记离线就绪。不缓存模型 API、Key 或项目数据。
- 请求浏览器持久化存储但不以获批为前提；离线能力在所需静态资源缓存完成后生效。
- 首次缓存安装失败可在原页面联网重试；补齐旧构建缓存时不得混入新构建文件。更新采用等待用户确认刷新，不强制激活并重载正在编辑/生成的页面。仅在空闲且保存完成时允许更新；存在其他同应用标签页时提示先关闭，随后由用户再次更新。保留最近一个旧构建的静态缓存用于旧资源读取，清理范围只包含更早的应用静态缓存，不能清理 IndexedDB 项目。
- M9 按第 4 节迁移 Plan/Deck v1→v2；其他对象版本保持不变，不引入通用迁移框架。遇到无法识别的版本提示不兼容并保留数据，不能静默重置数据库。

主分支为 `main`，沿用 M0–M6 已验证的 GitHub Pages 工作流，验收后仅推送 main，不改发布配置。浏览器、模型及 Pages 验证状态和工作记录链接由 [执行计划](执行计划.md) 管理，详细证据写入 `docs/spec/` 的对应里程碑记录，不在本文重复建立验收矩阵。
