# smartJC 架构文档

> 版本：MVP v0.3 · 2026-09-05
> 状态：本文为唯一设计契约；各部分的实际实现状态和验证结果以执行计划及对应工作记录为准。
> 用户行为以 [产品文档](产品文档.md) 为准；实施顺序及测试边界只维护在 [执行计划](执行计划.md)。

## 1. 技术边界与术语

应用是 GitHub Pages 上的静态 PWA，所有项目处理、存储和 PPTX 导出均在浏览器执行，仅模型请求访问用户选择的供应商。

| 术语 | 唯一含义 |
|---|---|
| Project | 一份固定论文及其生成、编辑成果的本地工作单元 |
| Paper | 解析内容、图源与论文理解结果；是 Deck 的证据基础 |
| SourceReference | 原 PDF 中一个可定位来源，是来源页码与原始 bbox 的唯一持有者 |
| Figure / Panel | 论文原图或子图的身份及语义，通过 sourceId 定位 |
| Deck / Slide | 用户编辑的结构化演示文稿及单页；当前 Deck 是编辑真值 |
| DeckPlan | 首次生成时用于确定每页目的和图源的阶段产物，不是另一份可编辑 Deck |
| ResearchStrategy | 可配置的研究叙事指导，以 strategyId 选择；不等同于论文研究类型或独立工作流 |
| Revision | 一次用户编辑请求对应的一批原子修改，也是一次 Undo 单位 |
| Checkpoint | 首次生成已经完整持久化的阶段，不是实时进度或后台任务 |
| Current / Working / Previous | 当前已保存 Deck、未提交内存工作副本、整套重生成前保留的唯一上一版 |

前端目标技术栈为 React + TypeScript + Vite + Tailwind CSS。从 M2 开始使用 React，先迁移 M1 已有编辑器，再实现 M2 的项目管理、PDF 来源查看与裁图，具体交付顺序见执行计划。其余技术组合为 Pi AI/Core 的必要调用能力、Zod、PDF.js、HTML/SVG、PptxGenJS 和 IndexedDB。现有依赖沿用已验证版本；React 及配套依赖在迁移时核对实际版本和官方兼容要求，验证后更新锁文件，不将技术选型视为已安装或已验证。

界面统一使用已接入 Vite 的 Tailwind CSS 4。页面布局、间距、字体、颜色、边框、响应式及 hover/focus/disabled/选中态均使用工具类；颜色与字体等公共主题值集中在 `src/style.css` 的 `@theme` 中，同类控件复用完整的工具类字符串。类名必须是构建时可扫描的完整字符串，不动态拼接工具类片段。

`src/style.css` 只保留 Tailwind 导入、主题声明和确有必要的全局基础规则；优先使用 Tailwind Preflight，不重复手写 reset，不用组件选择器或成片 `@apply` 重建另一套样式。PDF/Deck 的运行时坐标与尺寸由共享几何计算后通过内联 style 或 CSS 变量传入，固定视觉样式仍使用工具类。幻灯片文字按预览容器比例显示，不随浏览器视口宽度独立缩放；不改变第 3 节的共享几何和 PPTX 导出契约。

逻辑依赖为 UI → 应用协调函数 → 数据契约；PDF、存储、模型与导出使用必要的薄封装。协调函数只管理顺序、取消和提交，布局不进入模型层，供应商协议不进入 UI。按当前阶段创建文件，不预建服务类体系、注册中心、插件接口或多层目录。

### React 界面边界

React 负责页面、组件和交互状态；选中项、对话框和未提交输入草稿由组件管理，已提交 Project/Paper/Deck 仍通过现有协调与提交函数读取、修改和保存。组件展示提交后的数据，不另建一份可独立写入的 Deck 真值或第二套 Undo/Redo；数据契约、布局、存储、PDF 与导出模块保持普通 TypeScript，不反向依赖 React。

迁移保留现有 Tailwind 主题与工具类，重复控件通过小型 React 组件复用。文字编辑使用稳定的 Slide/Element ID 作为组件标识，输入期间保留草稿、焦点、光标和中文输入法组合状态，避免重新渲染覆盖正在编辑的 DOM；在既定编辑结束时机调用同一提交函数，保持一次编辑一次 Undo。会话、PDF 渲染资源和异步任务的创建与清理不得因组件重新渲染而重复执行；取消、项目切换和卸载沿用现有有效任务检查。

本次选型采用 React 的组件与状态能力，继续使用 Vite 静态构建；不配套引入 Next.js、服务端渲染、全局状态管理库或大型组件库。页面导航沿用第 7 节的 Hash 路由约定。

## 2. 唯一数据契约

对象使用稳定、不含位置语义的字符串 ID；页码仅用于 PDF 定位，幻灯片序号仅用于显示。ID 创建后不会随重排变化。时间为毫秒时间戳，长期对象的首版 schemaVersion 为 1。

### 项目与来源

```ts
type Checkpoint =
  | "project-created" | "pdf-parsed" | "figures-ready"
  | "paper-ready" | "deck-plan-ready" | "deck-ready";
type BBox = { x: number; y: number; width: number; height: number };
type Preferences = {
  instruction: string; language?: string; targetSlides?: number;
  strategyId?: string;
};
interface Project {
  schemaVersion: 1;
  id: string; name: string; nameIsCustom?: boolean; paperId: string; pdfAssetId: string;
  currentDeckId?: string; previousDeckId?: string;
  checkpoint: Checkpoint; preferences: Preferences;
  lastOpenedSlideId?: string;
  createdAt: number; updatedAt: number;
}
interface SourceReference {
  id: string;
  kind: "text" | "figure" | "panel" | "caption";
  pageNumber: number;
  bbox?: BBox;
  textQuote?: string;
}
interface FigurePanel { id: string; label?: string; sourceId: string; description?: string }
interface FigureRef {
  id: string; label?: string; caption?: string; sourceId: string;
  description?: string; panels: FigurePanel[];
}
```

用户重命名时在同一事务设置 nameIsCustom=true；解析或理解得到论文标题时，仅在该字段不为 true 时补充项目名称。论文原标题始终保存在 Paper.metadata.title，不随项目重命名变化。

来源集中放在 Paper.sources，Figure/Panel 不复制 pageNumber 或 bbox。figure/panel 类型的 Source 必须有 bbox。Source 不反向保存 figureId/panelId，反向查找由现有关系计算。

pageNumber 从 1 开始。BBox 使用 PDF.js 按原页旋转方向渲染后的整页坐标系，原点为左上角，x/y/width/height 均相对整页归一化；不是相对 Figure 或 Panel 的局部坐标。要求所有值有限，0 <= x,y < 1，width,height > 0，x+width <= 1 且 y+height <= 1。预览、模型页面图片和高分辨率裁图使用相同方向和坐标换算。

### 论文理解

```ts
type ClaimStrength = "descriptive" | "associative" | "supportive" | "causal";
interface Claim {
  id: string; text: string; strength: ClaimStrength;
  importance: "primary" | "secondary"; evidenceIds: string[];
}
interface Evidence { id: string; kind: string; summary: string; sourceIds: string[] }
interface StoryPoint { text: string; claimIds: string[]; sourceIds: string[] }
type StoryTopic = "background" | "knowledgeGap" | "question" | "studyDesign"
  | "mainFindings" | "novelty" | "limitations" | "conclusion";
interface Paper {
  schemaVersion: 1; id: string;
  metadata: { title?: string; authors?: string[]; journal?: string; year?: number; doi?: string };
  pages: { pageNumber: number; width: number; height: number; text: string }[];
  sources: SourceReference[];
  figures: FigureRef[];
  studyProfile?: { type: string; designSummary: string; sourceIds: string[] };
  story?: Record<StoryTopic, StoryPoint[]>;
  claims: Claim[]; evidences: Evidence[];
}
```

未到相应阶段的集合可以为空；paper-ready 要求理解结果及其引用完整。无法从论文得到的故事点保持空数组，不补造事实。研究设计摘要包含理解结果所需的样本、组别、模态或终点，不另建实体本体或按研究类型拆 Schema。

studyProfile.type 是基于论文的简短研究类型描述，不是提示词路由枚举。Project.preferences.strategyId 保存选中的叙事策略，取值来自第 7 节的策略文件；首次选择前可缺省，首次提交 paper-ready 时必须保存有效值。新增策略不修改 Paper Schema 或 TypeScript 枚举。Paper.story 的固定字段用于保存理解结果，不规定汇报章节或幻灯片顺序；实际顺序由 DeckPlan 决定。

Claim → Evidence → Source 是证据链的持久化方向，不重复存 supportsClaimIds、Evidence.figureIds 等可推导的反向关系。Evidence.kind 使用简短证据类型描述，仅供生成上下文，不作为自动科学强度证明。Paper.story 全部使用 StoryPoint，删除纯 string[] 版本。

PDF.js 提取页文字，模型分批分析候选图页，再基于文本与图源构建论文理解。模型输出先校验并由应用分配/映射 ID，再合并到阶段工作副本，不能一次要求模型生成整个完整 Paper。首版不保存字符级几何或第二套全文副本；文字来源至少可回到页和必要短引用。

### 演示文稿与计划

```ts
type LayoutId = "title" | "text-only" | "figure-full" | "figure-text" | "two-figures" | "panel-grid";
type SlideKind = "title" | "background" | "question" | "method" | "result"
  | "summary" | "discussion" | "conclusion" | "custom";
type SlideElement =
  | { id: string; type: "text"; text: string }
  | { id: string; type: "bullet-list"; items: string[] }
  | { id: string; type: "figure"; figureId: string; panelId?: string; cropOverride?: BBox }
  | { id: string; type: "citation"; sourceIds: string[] };
interface Slide {
  id: string; kind: SlideKind; title: string; message?: string;
  layoutId: LayoutId; elements: SlideElement[];
  claimIds: string[]; sourceIds: string[];
}
interface Deck {
  schemaVersion: 1; id: string; paperId: string;
  revision: number; title: string; language: string; slides: Slide[];
  createdAt: number; updatedAt: number;
}
interface DeckPlan {
  schemaVersion: 1; paperId: string; title: string; language: string;
  slides: (Pick<Slide, "id" | "kind" | "title" | "message" | "layoutId" | "claimIds" | "sourceIds"> & {
    figures: { figureId: string; panelId?: string }[];
  })[];
}
```

Slide.kind 是内容类别，用于“压缩背景”等操作，不对应额外布局或 Section 树。一个 Figure 元素仅引用整图或一个 Panel，多 Panel 使用多个元素。panelId 必须属于该 figureId，Panel 与所属 Figure 的 Source 必须位于同一 PDF 页；元素来源从 Figure/Panel 推导，不重复写 sourceIds。

cropOverride 仍是原 PDF 整页坐标：它可用于纠正当前元素的误裁，页码始终取该 Figure/Panel 的 Source，不允许借裁图跳到另一页。有效显示区域为 cropOverride 或原 Source.bbox。Source Preview 可同时显示两者；删除覆盖值恢复默认裁图。更换引用对象时清除旧覆盖值，单纯换布局必须保留。

一个固定学术主题配置同时供预览和导出使用，不在 Deck 中预留 themeId、自定义样式、notes、lockedByUser 或任意元素坐标。DeckPlan 只在 deck-plan-ready 时供续跑使用；首次 Deck 完成后删除该计划记录，之后的大纲从当前 Slide 读取，不维护双份状态。

DeckPlan 和自动生成完成的 Deck 至少有一页；手工或 AI 删除可使已有 Deck.slides 为空，零页是有效编辑状态，导出时单独拒绝。删空不清除 currentDeckId、不回退 deck-ready；清除失效的 lastOpenedSlideId 和元素选择。新增手工页允许空标题、空文字和空来源，不为占位提示伪造 Claim/Source；重新选择页时优先有效的原选择，再选相邻页或第一项，零页时不创建虚假 slideId。

## 3. PDF、布局与 PPTX

PDF.js 只负责文本、页信息、按需渲染和裁图。页面 width/height 使用 scale=1 且应用原页旋转的 viewport 尺寸。初始分析使用适当分辨率图片，最终图源按需高分辨率裁出，完成后释放页面 Canvas。

布局输入是 Slide、固定主题和图像宽高比；输出一份 ComputedSlideLayout，包含标题框、元素框、来源标签框及文字排版参数。框使用归一化幻灯片坐标；HTML/SVG 转成显示尺寸，PptxGenJS 转成 PPT 单位，两端不独立计算第二套几何。

六种布局分别容纳：标题与可选副标题、文字/列表、一个大图、一个图加辅助文字、两个图、3–4 个 Panel。来源标签始终可读；仅有 1–2 个 Panel 时使用单图或双图布局。输出超过布局容量时调整布局或拆页，不隐去元素。

删除元素后，仅在原布局不再适用时按剩余内容回退：无图使用 text-only；一图有辅助文字时使用 figure-text，否则 figure-full；两图使用 two-figures。手工空页允许 text-only 的空文字/空元素集合。布局调整并入同一修改批次，在最终校验前完成；涉及 layoutId 变更时使用包含该页的 slides scope，不扩展到其他页。不调用模型，不因回退隐藏其他元素或清除仍被引用的来源。

只完整渲染当前 Slide，缩略图降采样。图片等比 contain，裁切通过 cropOverride 明确完成，不用隐式 cover 截掉证据。文字使用固定主题的统一字号、行高和长度预算；明显溢出给出提示，不追求 Web 与 PowerPoint 逐像素相同。

PPTX 导出是对已保存 Deck 的只读操作：未保存草稿先保存成功，再捕获 Deck 内容快照及其 ID/revision，确认非零页并验证引用和布局；全部必需图片按该快照的引用和裁图从原 PDF 生成，再生成下载 Blob，使用后释放 URL。期间不重新读取正在变化的 Current，不混入新编辑，普通编辑不使这次导出失效；项目关闭、删除导致请求失效或必需资源缺失时停止并提示，不下载部分成果，也不持久化 PPTX 或临时导出文件。

## 4. 存储与首次生成

IndexedDB 同时支持结构化数据和 Blob，首版不需要两套存储协调。[MDN：IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)

使用一个带 smartJC 命名空间的数据库，最小存储分工如下；应用封装常用读写函数即可，不再为每种对象建立 repository 类体系。

| Object store | 内容 |
|---|---|
| projects | Project 与最近访问位置 |
| papers | Paper 的最近完整阶段状态 |
| assets | 原 PDF Blob，键由 Project.pdfAssetId 引用 |
| plans | 按 projectId 保存尚未完成首次生成的 DeckPlan |
| decks | 当前 Deck 与唯一上一版 |
| history | 按项目保存有限可见消息、已提交修改摘要和修改标识；不存撤销快照 |
| settings | 独立模型设置及 API Key，不归属于项目 |

页面、缩略图、裁图位图和 Blob URL 仅在内存中有限缓存，按需淘汰；资源缓存键包含来源、有效裁图和渲染尺寸，不能复用过时裁图。Undo/Redo 各最多保留 20 个内容快照，可见历史最多保留 100 条；这些上限是实现常量，不写入领域类型。打开项目只把近期相关对话带入模型上下文。

创建 Project、空 Paper 与原 PDF Blob 在同一事务提交；失败不留下可打开的半项目。删除项目同时删除其 Paper、原 PDF、计划、两个 Deck 及历史，不触碰 settings。应用更新不会执行项目清理。

首次生成阶段唯一顺序：

| Checkpoint | 同步持久化的完整产物 | 下一步 |
|---|---|---|
| project-created | Project + 原 PDF + 空 Paper | 解析 PDF |
| pdf-parsed | 页信息、文本及文字来源候选 | 分析 Figure/Panel |
| figures-ready | Figure/Panel、对应 Source 与描述 | 论文理解和证据链 |
| paper-ready | studyProfile、Claim、Evidence、Paper.story + Project.preferences.strategyId | 规划 Deck |
| deck-plan-ready | DeckPlan | 生成完整 Working Deck |
| deck-ready | Current Deck、删除临时计划 | 编辑器 |

阶段在内存中构建和校验，完成后以一次 IndexedDB readwrite 事务保存产物并推进 checkpoint。阶段启动时捕获 projectId、paperId、pdfAssetId 和前置 checkpoint；提交事务内重新读取 Project，确认项目仍存在、论文关联和前置 checkpoint 未变，且当前任务仍有效，再写入产物。另一标签页已推进阶段或项目已被删除时拒绝旧结果；不能回退检查点或重新创建被删除项目。只更新本阶段负责的项目字段，保留事务中读到的最新名称和其他无关字段。

等待模型、PDF 渲染或网络时不能保持数据库事务打开。单张图识别失败允许记录提示并保留其他完整图源；figures-ready 表示候选页已处理，未找到图的结果可为空，不伪造来源。

恢复时核对 checkpoint 对应的产物和必要原 PDF；缺失或非法时说明原因，不静默伪造 Ready 或清空稳定成果。取消只停止当前任务并丢弃未提交阶段，最后完整阶段保留。继续由用户触发，重做未完成阶段，不重新跑已完成阶段，也不逐页保存半成品。

运行态只在内存按操作管理进度、AbortController 和有效任务标识。每次完成回调都检查任务是否仍有效；取消、项目关闭或操作替换使旧回调失效。提交事务实际写入前再次检查任务；取消发生且事务尚未完成时 abort，事务完成后按已提交结果处理。此规则同样适用于 AI 修改和整套重生成，不只在模型返回时检查一次。持久化 checkpoint 和产物决定可恢复状态，UI 的 generating/exporting 等状态不作为长期真值。

## 5. 修改、撤销与版本

### 受控修改入口

```ts
type RevisionScope =
  | { type: "element"; slideId: string; elementId: string }
  | { type: "slides"; slideIds: string[] }
  | { type: "deck" };
type DeckMutation =
  | { type: "add-slide"; slide: Slide; afterSlideId: string | null }
  | { type: "delete-slide"; slideId: string }
  | { type: "move-slide"; slideId: string; afterSlideId: string | null }
  | { type: "update-slide"; slideId: string; changes: Partial<Pick<Slide, "kind" | "title" | "message" | "layoutId" | "claimIds" | "sourceIds">> }
  | { type: "add-element"; slideId: string; element: SlideElement }
  | { type: "replace-element"; slideId: string; element: SlideElement }
  | { type: "delete-element"; slideId: string; elementId: string }
  | { type: "set-language"; language: string };
interface ApplyRevisionArgs { scope: RevisionScope; mutations: DeckMutation[]; summary: string }
interface RevisionRecord {
  id: string; projectId: string; deckId: string;
  baseRevision: number; committedRevision: number;
  scope: RevisionScope; affectedSlideIds: string[]; summary: string; createdAt: number;
}
```

Agent 唯一写工具为 deck.apply_revision，参数使用 ApplyRevisionArgs。应用在发起请求时绑定 requestId、当前 projectId、deckId 和 baseRevision，不接受模型改写这些值。RevisionRecord.id 使用该 requestId，已提交的请求不能再次提交。

工具仅暂存一个经过校验的修改候选；同一请求重复写调用拒绝，Agent 回合正常结束且任务仍有效时才提交。问答/审核回合不开放写工具。取消或后续执行失败丢弃候选，不出现工具已写入但用户请求整体失败的半状态。

afterSlideId=null 表示放在第一位，否则放在指定现有页之后；add-element 追加到元素序列。replace-element 必须保留已有元素 ID。目标不存在、重复 ID、移动到自身之后或越过 scope 的操作拒绝。增删/拆并页的 scope 使用受影响原页集合及本批新页，作用范围需与用户意图一致，不用通用 JSON Patch 或任意坐标更新。

### 选择、上下文与提交

发起请求时把明确页码按当前顺序解析为稳定 slideId。显式目标 > 当前 UI 选择 > 近期对话上下文；“这页”直接取当前显示页。多处重复出现的 Figure 如无法由用户范围和选择消歧，先询问，不随机挑一处。

默认上下文为用户请求、选择、目标页、必要相邻页、相关 Claim/Evidence/Source 和生成偏好。涉及叙事或内容取舍时带入所选策略，普通文字微调和问答不重复带入全部策略；策略不能扩大用户指定的修改范围。仅全局请求带入完整 Deck；不默认带入整篇 PDF。按需保留 paper.get（概要）、paper.get_page、paper.get_figure、paper.get_claim、deck.get 读工具，全部限定当前项目。工具参数从实际 Zod Schema 派生，不在 Prompt 另写一套协议。

提交顺序固定为：

1. 基于请求捕获的 Current 克隆工作副本，应用整批修改。
2. 运行结构、引用、scope 和布局校验，确认任务未取消。
3. 打开一次 IndexedDB 事务，重新读取 Project.currentDeckId 与 Deck.revision，检查仍与请求绑定值相同，并拒绝已提交的 requestId。
4. 版本号加 1，原子保存新 Deck、Project.updatedAt 和 RevisionRecord/可见修改摘要；全部写入成功才确认提交。
5. 事务完成后替换内存 Current，更新撤销栈并刷新受影响页。过期响应丢弃并提示用户基于当前内容重试，不自动进入无限重规划。

M1 在内存验证同一提交语义，M2 接入 IndexedDB；到 M5 不另建 Agent 专用持久化通道。UI 手工编辑调用同一提交函数，用户文字输入、裁图和重排都只形成一个逻辑操作。

手工编辑首次产生内容草稿时，就使待提交 AI 修改的任务标识失效并触发取消，不能只依赖保存后 revision 的变化。草稿期间其他写操作、Undo/Redo、导出、版本切换和应用内离开项目先结束编辑并等待草稿保存；保存失败则暂停后续操作。只浏览或选择元素不视为内容修改。

保存失败保留待保存草稿并显示未保存，稳定 Deck、版本号、历史及撤销栈不前进。用户重试也需重新校验版本，不能用草稿覆盖其他已提交内容。多个标签页不承诺实时同步，提交时的数据库版本检查仍会拒绝旧写入；用户可重新打开最新项目。

### Undo/Redo

会话快照只包含 Deck 的 title、language 和 slides，不含 revision、时间戳、PDF 或位图。Undo/Redo 同样经过版本核对和原子保存，恢复内容但 revision 继续加 1；保存失败不弹出对应快照。Undo 后的新编辑清空 Redo；关闭项目或切换整套版本后清空两栈。

### 整套重生成与上一版

重生成复用已保存 Paper，从新计划开始在内存构建新 Deck；不重做论文分析，不修改首次生成的 checkpoint。其未完成工作不持久化，重开后保留原 Current，需要用户重新发起重生成。

生成期间当前 Deck 可查看，但禁用同项目编辑和重复重生成。提交仍检查有效任务、基准 Deck ID 和 revision，以防其他标签页改变成果。

成功时在一个事务中保存新 ID 的 Deck（初始 revision=0），将原 Current 指向 Previous，切换 Current，保存此次生成偏好，清理被替代的更早 Previous。失败或取消不修改任何现有版本指针，不提前覆盖 Previous。

恢复上一版时原子交换 Current/Previous，并将成为 Current 的 Deck.revision 加 1、更新时间；失效旧任务并清空会话 Undo/Redo。重复恢复可切回另一版。不提供重新分析 Paper 或 PDF 重新关联，避免首版维护旧 Deck 到新论文分析的引用迁移。

## 6. 校验与失败处理

Zod 校验输入形状与字段白名单；普通函数校验跨对象关系。二者覆盖实际数据风险，不构建通用校验平台。

| 阻止提交/导出的错误 | 允许提交但需要提示或内容复查 |
|---|---|
| ID 重复、非法元素/布局、非法或越界 bbox | 标题偏长、信息拥挤、图较小、重复表达 |
| Source/Claim/Evidence 不存在，引用其他 Paper | 用户自建页无科学 Claim、次要故事点缺失 |
| Figure/Panel 归属错误，图源 bbox 缺失 | 因果措辞疑虑、论文解释不确定 |
| 越过修改范围、过期/重复请求、无效任务 | 图源识别不完整、需要用户手动裁图 |
| 布局无法容纳元素，导出必需资源缺失 | 无法纯代码判定的科学和视觉质量问题 |

主要 Claim 在 paper-ready 必须有至少一个 Evidence，Evidence 至少有一个有效 Source。字段合法不代表科学正确：措辞约束放在生成/修改 Prompt 中，保留来源查看与必要警示；不以关键词判断充当科研证明，不强制额外模型复审。

错误只需携带 stage、code、message 与可执行恢复建议。区分 PDF 解析/缺失、模型认证/限流/额度/网络/无效输出、来源/布局、导出、存储额度/写入失败。模型失败不改稳定产物，用户修正设置或网络后重试当前阶段；资源缺失保留可读数据并禁用依赖资源的操作。

## 7. 模型与 GitHub Pages/PWA

### 模型边界

固定候选为 DeepSeek deepseek-v4-flash-vision-exp 和 GLM glm-5.3-flash。候选不是已验证支持列表：M0 核对官方端点、模型 ID、Vision、结构化结果/工具调用、Streaming、Abort 和真实浏览器 CORS，生产界面仅显示通过验证的候选。至少一个可用才进入后续主线，不能用 Node 请求成功替代浏览器验证。

优先复用 Pi AI/Core 已有的供应商通信与工具循环，只补必要预设或薄封装，不重复实现一套通用 OpenAI-compatible SDK。模型设置只有固定候选、Key、连接检查和清除 Key；不存在自定义 Base URL、任意模型或混合路由。所有模型请求使用当前配置，运行中先完成或取消任务再切换。

Key 存在 settings，与项目生命周期分开。Key 不进入模型上下文、history、错误日志、构建变量或导出；供应商请求只发送必要文本与图片。论文和模型内容以文本/受控元素渲染，不执行其中的脚本、HTML 或工具指令。

浏览器直连不成立的候选不启用，也不为其引入代理或后台服务；若全部失败，M0 记录阻塞原因，不能把纯静态部署能力写成已通过。

### 研究叙事策略与提示词

提示词按以下职责维护，文件在 M3/M4 按实际调用需要创建；M3 已实现公共规则、五个研究策略及图页分析/论文理解阶段，后续阶段随实际调用补齐。

| 文件约定 | 职责 |
|---|---|
| `prompts/common.md` | 统一维护来源、科学措辞和用户要求优先等公共生成/修改规则 |
| `prompts/research/<strategyId>.md` | 一种研究叙事策略的适用情况、叙事建议、证据重点和内容取舍 |
| `prompts/stages/<stage>.md` | 实际模型调用阶段的任务说明；不因研究类型复制阶段提示词 |

首批策略为 `general`、`mechanistic`、`omics`、`clinical`、`translational`，最后一项覆盖转化/混合研究。文件名是不重复的稳定 ID；YAML 头信息只含必填字符串 name、description，正文使用 Markdown。增加策略只需新增文件并构建，不维护第二份手写注册表或重复的 JSON 配置。以下仅示意 `omics.md` 的格式，实际内容由 M3 根据产品范围编写：

```markdown
---
name: 组学与生物信息学
description: 适用于以高通量数据分析和生物学发现为主的研究
---

## 叙事建议
研究问题 → 样本与数据 → 主要发现 → 验证 → 生物学解释。
按论文证据调整，不要求每部分独立成页。

## 证据重点
围绕主要结论组织 Figure/Panel，说明发现及其验证依据。

## 内容取舍
方法仅保留理解结论所需的信息，避免按分析工具步骤逐项汇报。
```

通过 Vite `import.meta.glob` 配合 `query: '?raw'`、`import: 'default'`、`eager: true` 将文件作为字符串随应用构建分发；由应用读取 YAML 头信息和正文，不能将正文执行为脚本或模板表达式。[Vite Glob Import](https://vite.dev/guide/features#glob-import) 只检查所需文件存在、ID 唯一、头信息格式及 name/description/正文非空，且必须有 `general`。构建检查与应用加载复用同一解析/校验函数；无效配置在发布前阻止构建，不能仅靠浏览器运行时抛错代替，不另建配置框架。

首次论文理解调用带入公共规则、该阶段任务、内置策略目录及其简短正文，在已有调用中完成理解并返回一个 strategyId；应用校验其为可用策略后，与 Paper 和 paper-ready 检查点一同保存到 Project.preferences。不为分类另开模型调用；无法确定策略时选 `general`，不使用类型分支或多策略组合执行器。

规划和生成只带入一个所选策略及当前阶段所需上下文。用户明确的叙事要求优先于策略默认建议，但不能突破证据、来源、数据结构、布局或修改权限；策略不包含工具协议、Schema、事务逻辑和布局坐标。公共规则只在 common.md 维护；运行时数据作为上下文附加，不写入提示词文件。首版不引入模板继承、远程配置或应用内提示词编辑器。

整套重生成复用已保存 Paper；用户要求改变叙事方式时，在原有 DeckPlan 调用中结合策略目录和正文选择策略并形成计划，不重做论文分析。候选 strategyId 随生成偏好保留在工作副本，成功切换 Current 时一同提交，失败不改已有偏好。局部 AI 修改按当次要求处理，不因此改写项目的默认策略；preferences 表示后续生成默认值，不承担各 Deck 的完整提示词历史。

提示词随 Git 管理，修改后重新构建发布；已打开页面在用户接受应用更新前继续使用原构建。更新只影响后续请求，已保存 Paper、DeckPlan 和 Deck 不重写；续跑仍重做未完成阶段，使用当前构建的提示词，不回退检查点。若存量 strategyId 已无对应文件，在下一次相关请求中提示并使用 `general`，下一次生成成功提交时保存实际 ID；单纯查看或恢复上一版不触发重新生成。不持久化提示词快照，不承诺跨应用版本逐字复现生成结果。

### 静态托管与离线

GitHub Pages 托管静态构建产物，不能承担应用的模型代理或任务执行。[GitHub Pages 说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

采用 Vite 构建，通过 GitHub Actions 安装锁定依赖、构建并发布 dist。部署参数来自实际仓库配置，项目站点 base 为 /<仓库名>/，不能硬编码根路径。[Vite GitHub Pages 部署指南](https://vite.dev/guide/static-deploy.html#github-pages)

- 导航使用 Hash 路由，如 /<仓库名>/#/project/<id>，不依赖服务端 rewrite；刷新仍请求项目入口 HTML。
- JS/CSS、图标、字体、PDF.js worker 及所需 PDF 资源均随构建分发，遵循同一 base，不依赖运行时 CDN。
- Manifest 的 start_url 与 scope、Service Worker 的脚本和注册范围均在项目子路径。Manifest 范围不等同于 Service Worker 范围，二者分别正确配置。[Manifest scope](https://developer.mozilla.org/docs/Web/Progressive_web_apps/Manifest/Reference/scope)、[Service Worker 注册](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register)
- Service Worker 只缓存带应用命名空间的版本化静态资源，包含离线预览、PDF 裁图和 PPTX 导出所需的延迟加载模块；不缓存模型 API、Key 或项目数据。
- 请求浏览器持久化存储但不以获批为前提；离线能力在所需静态资源缓存完成后生效。
- 更新采用等待用户确认刷新，不强制激活并重载正在编辑/生成的页面。仅在空闲且保存完成时允许更新，清理范围只包含旧版应用静态缓存，不能清理 IndexedDB 项目。
- 首版 schemaVersion=1，不预建迁移框架；未来真实结构变化时才写必要迁移。遇到无法识别的版本提示不兼容，不能静默重置数据库。

主分支为 `main`；部署主机、仓库名和发布触发分支在实际配置远程及 M0 时确认，主分支约定不代表已经配置自动发布。浏览器、模型及 Pages 验证状态和工作记录链接由 [执行计划](执行计划.md) 管理，详细证据写入 `docs/spec/` 的对应里程碑记录，不在本文重复建立验收矩阵。
