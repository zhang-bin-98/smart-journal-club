# 模型、提示词与静态部署

> 模型接入与配置已在 M14 实施，其他 v0.5 目标仍按阶段推进；当前状态见 [执行目录](../execution/README.md)。

## 7. 模型与 GitHub Pages/PWA

### 模型边界

v0.5 目标统一使用通用 Responses API：一套全局 Base URL、模型 ID、API Key、思考强度、可选 Token 容量、模型并发及超时配置，不再固定 DeepSeek/GLM 白名单，也不增加协议切换、自动 Chat Completions 回退或混合路由。历史 M0 只验证旧 DeepSeek Chat Completions 路线，不能证明任意 Responses 地址或模型可用；M14 运行代码已迁入通用 Responses 接入，不沿用历史接入证据作为新能力结论。

设置字段以[数据模型](数据模型.md)为唯一契约，UI 见[模型配置](../ui/模型配置.md)。应用配置用例拥有记录 Schema、纯归一化/校验及保存/检查协调，UI 仅提交草稿；模型适配器负责从已归一化配置映射供应商请求，存储适配器负责持久化，不各自维护配置规则。统一 URL 归一化保留服务路径，最终 POST 到根地址 + /responses；接受尾斜杠与已粘贴的 /responses，去重只处理末尾完整路径段；仅 HTTP(S)，拒绝 userinfo/query/fragment，不把 Key 放 URL。浏览器直连的 CORS/TLS/混合内容限制按实际连接错误提示，不新增应用代理或后台。

供应商通信继续优先复用 Pi AI 的 Responses 适配器，固定 workflow 保留单次调用薄封装，交互式循环沿 Agent Core；不得假设现有 SDK 接线会原样保留所有强度值。实现时验证“服务默认”真正省略 reasoning.effort，手选值准确传入、不被 SDK 默认或截断逻辑改写；若已装适配器不能满足，先在既有边界落实必要薄适配，不复制 Agent loop。结构化 workflow 继续声明唯一结果工具并由应用校验工具名称、参数和业务 Schema；请求使用自动工具选择，不为强制工具调用静默关闭思考模式。原生结构化格式单独通过能力检查验证。已核对的 DeepSeek 正式端点展示 none/low/high/max，其他服务展示待验证候选，详细兼容说明见 [DeepSeek Responses](https://api-docs.deepseek.com/zh-cn/api/create-response/)。对应格式与模型相关档位依据：[OpenAI reasoning 指南](https://developers.openai.com/api/docs/guides/reasoning)。第三方声称兼容不等于能力已验证。

用户填写的上下文窗口进入 SDK 模型描述，并约束发送前的输入与输出估算；不会作为供应商请求字段发送。填写最大输出后，结构化生成和 Agent 请求统一使用该值，不再被工作流原有常量截小；连接/能力检查仍使用小预算且不超过配置上限。输出预算包含思考与最终结果，不强制生成到上限。文本、工具/结构化 Schema 与图片沿既有保守估算，超过窗口时拒绝该请求，不自动截短来源或历史；计数函数由容量规划与适配器共用，并计入实际提示词和工具封装；通用 Responses 端点未声明统一 tokenizer，当前文本长度除以二、每图 4096 为近似估算，不是精确计数或已验证模型容量。估算误差仍可能导致服务拒绝过长上下文，不能用固定字符硬上限替代用户容量。请求体不另设统一 8 MiB 拒绝门槛，服务实际请求大小限制按错误响应处理。默认常量由应用配置用例持有，经 composition 注入适配器，保持适配器只读应用类型的依赖边界。

连接检查和应用能力检查分开，使用当前配置草稿与固定小素材，不包含项目论文；后者逐项核对图片、工具调用、结构化结果和流式返回，取消能力在运行适配器验收。测试结果绑定配置身份/请求 epoch；字段变化或取消使其失效。测试经过全局 API 调度，不能绕过共享并发或服务真实限流，也不自动保存 Key。允许先保存未测试配置，但不得展示能力已通过；必要能力失败不以文字成功掩盖。

所有模型请求捕获同一已保存配置；运行任务先完成或取消才允许修改或清除。配置变化只影响后续请求，不改写论文/文稿，不自动重跑；中断后继续使用当前配置重做未完成部分。保存与清除经应用命令原子提交，失败保留旧配置及输入。Key 独立保存在 settings，不进入论文、history、日志、导出或构建变量；结果不含秘密回显。供应商请求只发送必要文本与图片；论文和模型内容以文本/受控元素渲染，不执行其中的脚本、HTML 或工具指令。

旧固定模型设置不能凭旧 Base URL 自动转为已验证 Responses 配置；迁移保留旧配置用于恢复，独立引导用户填写新地址/模型并选择默认强度，不自动发送请求或清空项目。旧密钥不得无提示复制到另一个新主机。M14 保存新配置时在 settings 同事务保留旧记录；清除 Key 同时清除当前记录和旧备份的凭据。保存与清除复核页面捕获的配置基准，冲突拒绝覆盖，重新打开配置页读取最新值；项目成果不参与该事务。真实接入及迁移证据见 [M14 工作记录](../spec/M14.md)。

### 研究叙事策略与提示词

现有公共规则、五个研究策略和五个阶段提示词是 v0.4 实现基线。M13 不修改 Prompt；v0.5 在实际实施阶段更新全文理解、Figure 局部切分、大纲/讲稿、页面规划与生成任务，只为真实调用增加或拆分提示词。职责如下：

| 文件约定 | 职责 |
|---|---|
| `prompts/common.md` | 统一维护来源、科学措辞和用户要求优先等公共生成/修改规则 |
| `prompts/research/<strategyId>.md` | 一种研究叙事策略的适用情况、叙事建议、证据重点和内容取舍 |
| `prompts/stages/<stage>.md` | 实际模型调用阶段的任务说明；不因研究类型复制阶段提示词 |

首批策略为 `general`、`mechanistic`、`omics`、`clinical`、`translational`，最后一项覆盖转化/混合研究。文件名是不重复的稳定 ID；YAML 头信息只含必填字符串 name、description，正文使用 Markdown。增加策略只需新增文件并构建，不维护第二份手写注册表或重复的 JSON 配置。以下仅示意 `omics.md` 的格式，正文实施时遵守[生成与视觉规则](../product/生成与视觉规则.md)的主线/补充与证据原则：

```markdown
---
name: 组学与生物信息学
description: 适用于以高通量数据分析和生物学发现为主的研究
---

## 叙事建议
研究问题 → 样本与数据 → 主要发现 → 验证 → 生物学解释。
在基础学术骨架内按论文证据调整结果组织，不要求每部分独立成页。

## 证据重点
围绕主要结论组织 Figure/Panel，说明发现及其验证依据。

## 内容取舍
方法仅保留理解结论所需的信息，避免按分析工具步骤逐项汇报。
```

通过 Vite `import.meta.glob` 配合 `query: '?raw'`、`import: 'default'`、`eager: true` 将文件作为字符串随应用构建分发；由应用读取 YAML 头信息和正文，不能将正文执行为脚本或模板表达式。[Vite Glob Import](https://vite.dev/guide/features#glob-import) 只检查所需文件存在、ID 唯一、头信息格式及 name/description/正文非空，且必须有 `general`。构建检查与应用加载复用同一解析/校验函数；无效配置在发布前阻止构建，不能仅靠浏览器运行时抛错代替，不另建配置框架。

首次论文理解调用带入公共规则、全文与图源、该阶段任务及策略目录，在已有调用中选择默认 strategyId 作为软性参考；应用校验后与完整论文阶段一同保存。研究设计和证据性质是论文事实；strategyId 不是研究类型枚举、工作流路由或必选模板，不能限制混合研究的章节组织。策略与用户汇报要求不限制全文证据提取范围，不能先按 PPT 重点过滤发现。不为分类另开模型调用；无法确定策略时选 `general`，不使用类型分支或多策略组合执行器。

大纲/演讲稿、页面规划和生成带入一个参考策略、相关原文片段与实际图证据。具体故事在大纲/讲稿阶段由发现、证据关系与已保存汇报要求形成，用户修改章节与实际讲述，不确认分类标签；不能为符合策略而补造机制、验证或缺失证据。按来源读取必要上下文，不能用省略全文的结构摘要作为后续唯一事实依据。用户明确的叙事要求优先于策略默认建议，但不能突破证据、来源、数据结构、布局或修改权限；策略不包含工具协议、Schema、事务逻辑和布局坐标，不能覆盖图核对、基准版本、`validatePlanNarrative()` / `validateDeckNarrative()` 的硬规则或 build contract。稳定规则由领域 Schema 和确定性校验保证，不能只写进 Prompt。公共规则只在 common.md 维护；运行时数据作为上下文附加，不写入提示词文件。首版不引入模板继承、远程配置或应用内提示词编辑器。

整套重生成复用已保存 Paper；用户要求改变叙事方式时，在大纲/讲稿调用中结合策略目录和正文选择策略并形成计划，不重做全文分析。候选 strategyId 保存在 PlanRecord.generationPreferences，base.projectPreferences 保留开始时的项目偏好供冲突检查。完成大纲/讲稿后仍停在 outline-ready，用户进入幻灯片步骤后才规划页面；该步骤内通过 deck-plan-ready 校验继续 Build。成功应用并切换 Current 时一同提交实际生成偏好，失败不改已有偏好；不得因候选策略与旧默认值不同将其误判为过期。局部 AI 修改按当次要求处理，不因此改写项目的默认策略；preferences 表示后续生成默认值，不承担各 Deck 的完整提示词历史。

提示词随 Git 管理，修改后重新构建发布；已打开页面在用户接受应用更新前继续使用原构建。更新只影响后续请求，已保存 Paper、DeckPlan 和 Deck 不重写；续跑仍重做未完成阶段，使用当前构建的提示词，不回退检查点。若存量 strategyId 已无对应文件，在下一次相关请求中提示并使用 `general`，下一次生成成功提交时保存实际 ID；单纯查看或恢复上一版不触发重新生成。不持久化提示词快照，不承诺跨应用版本逐字复现生成结果。

### 静态托管与离线

GitHub Pages 托管静态构建产物，不能承担应用的模型代理或任务执行。[GitHub Pages 说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

采用 Vite 构建，通过 GitHub Actions 安装锁定依赖、构建并发布 dist。部署参数来自实际仓库配置，项目站点 base 为 /<仓库名>/，不能硬编码根路径。[Vite GitHub Pages 部署指南](https://vite.dev/guide/static-deploy.html#github-pages)

- 导航使用 Hash 路由，如 /<仓库名>/#/project/<id>，不依赖服务端 rewrite；刷新仍请求项目入口 HTML。
- JS/CSS、图标、字体、PDF.js worker 及所需 PDF 资源均随构建分发，遵循同一 base，不依赖运行时 CDN。
- Manifest 的 start_url 与 scope、Service Worker 的脚本和注册范围均在项目子路径。Manifest 范围不等同于 Service Worker 范围，二者分别正确配置。[Manifest scope](https://developer.mozilla.org/docs/Web/Progressive_web_apps/Manifest/Reference/scope)、[Service Worker 注册](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register)
- Service Worker 按完整构建清单缓存带应用命名空间的版本化静态资源，包含离线预览、PDF 裁图和 PPTX 导出所需的延迟加载模块，以及 PDF.js 的 cmaps、standard_fonts 和 wasm；每个文件按构建时 SHA-256 校验，全部缓存成功后才标记离线就绪。不缓存模型 API、Key 或项目数据。
- 请求浏览器持久化存储但不以获批为前提；离线能力在所需静态资源缓存完成后生效。
- 首次缓存安装失败可在原页面联网重试；补齐旧构建缓存时不得混入新构建文件。更新采用等待用户确认刷新，不强制激活并重载正在编辑/生成的页面。仅在空闲且保存完成时允许更新；存在其他同应用标签页时提示先关闭，随后由用户再次更新。保留最近一个旧构建的静态缓存用于旧资源读取，清理范围只包含更早的应用静态缓存，不能清理 IndexedDB 项目。
- v0.5 按[工作流与存储](工作流与存储.md)迁移对象与 PlanRecord，复用 M9 的旧稿迁移路径，不引入通用迁移框架。遇到无法识别的版本提示不兼容并保留数据，不能静默重置数据库。

主分支为 `main`，沿用已有 GitHub Pages 工作流，验收后仅推送 main，不改发布配置。M13 仅推送文档，触发现有工作流不等于新功能已部署。浏览器、模型及 Pages 验证状态和工作记录链接由 [执行计划](../execution/README.md) 管理，详细证据写入 `docs/spec/` 的对应里程碑记录，不在本文重复建立验收矩阵。
