## 最终设计

### 1. 领域结构与 ownership

- Narrative 不单独持久化；学术叙事由 DeckPlan v2 的 Section、PlannedSlide、purpose、message、Claim/Evidence/Figure 映射表达。
- Section 保持单层；DeckPlan 在确认前是结构真值，成功 build 并消费计划后由 `Deck.sections + Slide.sectionId` 成为结构真值。
- `message` 唯一表示 take-home，和 title 分离；purpose 表示章节或页面承担的叙事职责。
- DeckPlan / Section Schema 与 Plan narrative validation 归 `modules/outline`；Deck narrative validation 可通过 deck 的薄入口组合同一组普通 deterministic helper，不建立框架。
- `DeckPlan → buildDeck → Deck` 是唯一 Build 边界。Build 不负责重新规划，regeneration 复用同一 planning/build 用例。

### 2. Claim emphasis 与 slideBudget

```ts
type ClaimEmphasis = "focus" | "omit";
```

claimEmphasis 是稀疏覆盖：没有 entry 的 Claim 缺省为 brief；设置 null 删除 entry 并回到 brief。DeckPlan 不另设 Claim 层级，不从 Paper.claims.importance 推导 emphasis，也不改写 Paper.claims 的重要性字段。

slideBudget 表示章节目标页数，不是实际页数的派生值：

- draft 允许预算与实际页数不同；Outline 显示 mismatch。
- 修改 slideBudget 不自动新增或删除 Slide。
- 新增、删除、移动 Slide 不自动修改 slideBudget。
- confirmed 时每个保留章节的预算必须与实际页数一致，且至少有一页。

### 3. Planning 与暂停状态机

正式 application API 和产品状态机为：

```text
preparePaper()
→ paper-ready
→ Paper Understanding
→ 用户显式选择生成大纲
→ prepareOutline()
→ deck-plan-ready
→ Outline
→ confirm
→ buildPresentation()
→ deck-ready
```

`preparePaper()` 只完成解析、图源和论文理解，提交 `paper-ready` 后停止；不保留从 `paper-ready` 自动规划的组合入口。`prepareOutline()` 只有在用户显式发起后才规划并停止在 Outline。confirm 是独立于 PlanMutation 的 command；`buildPresentation()` 只接受同一 confirmed plan ID/revision。保留现有 checkpoint 名称，不为 Paper Understanding 或 Outline 的 UI 状态新增 checkpoint。

### 4. Narrative validation

对外只保留两个明确的薄入口：

```ts
validatePlanNarrative(plan, paper)
validateDeckNarrative(deck, paper)
```

内部允许共享普通 deterministic helper，但不使用 `DeckPlan | Deck` 联合入口。Plan 入口处理确认前计划叙事、预算与 omit 规则；Deck 入口处理构建后和编辑后的实际叙事。

`ending-required` 的唯一规则是：最后一个非 custom Section 必须为 synthesis 或 takeaways。limitations 和 discussion 可出现在最终综合之前，但不能单独作为最后收尾。

规划输出最多允许一次 one-shot LLM repair，并且只处理机器可确定的问题：

- schema 与无效 ID；
- section reference；
- Claim / Source / Figure / Panel reference；
- layout compatibility；
- deterministic structural consistency。

repair 不处理 background quality、narrative strength、critical discussion quality、ending quality 或 slide allocation judgement。这些问题作为 Outline 中可定位的 error/warning，由用户处理；repair 失败不进入循环重试。

### 5. 独立 Build contract

构建忠实性完全独立于 Narrative validation：

```ts
validateBuiltDeckAgainstPlan(deck, confirmedPlan)
```

该 validator 专门检查 Build 未改变 confirmed Plan 的：

- Slide ID；
- 顺序；
- section；
- kind；
- layout；
- Claim；
- Source；
- Figure / Panel selection。

任何 mismatch 都拒绝 Deck 提交并保留 confirmed Plan。成功 build 后才在同一事务写入 Deck、推进状态并删除已消费的 PlanRecord。

### 6. PlanRecord、兼容与恢复

```ts
type DeckPointer = {
  deckId: string;
  revision: number;
};

type GenerationBase = {
  current: DeckPointer;
  previous?: DeckPointer;
};

type PlanRecord = {
  recordVersion: 1;
  projectId: string;
  plan: DeckPlan;
  preferences: Preferences;
} & (
  | { mode: "initial" }
  | { mode: "regeneration"; base: GenerationBase }
);
```

`recordVersion` 只版本化持久化封套；`schemaVersion` 专用于 DeckPlan、Deck 等领域对象。每项目最多保存一条待消费计划；刷新恢复最后完整 draft/confirmed/candidate，运行中的半成品不保存。

旧 Deck/Plan 使用 lazy deterministic migration：Current 与 Previous 都迁移，已是 v2 时幂等；可无歧义映射的旧 plan 转为 draft，claimEmphasis 为空因此所有 Claim 缺省 brief；无法安全迁移时只废弃临时 plan 并重新规划，保留 PDF、Paper 和稳定 Deck。仅对象契约变化不自动触发 IndexedDB 版本升级；store/index 变化才升级数据库。

### 7. Regeneration candidate

regeneration 调用同一 `prepareOutline()` 和 `buildPresentation()`，不维护第二条 pipeline。candidate 保存 `base.current.revision` 及 Current/Previous 指针；candidate 存在期间 Current 仍可正常编辑，不使用 UI 锁定保证一致性。

Current ID/revision 变化后 candidate 立即成为 stale。stale candidate：

- 可以查看；
- 不得编辑；
- 不得 confirm；
- 不得 build；
- 不会自动重绑定到新 Current；
- 用户只能 discard 后重新规划。

成功 build 才原子保存新 Deck、把原 Current 变为 Previous、切换 Current、保存候选偏好、删除已消费计划与被替代的更早 Previous。失败、取消或过期不改变稳定版本。

### 8. UI/controller readiness

项目 controller 承担 Paper Understanding、Outline 和 Continue build 的异步状态，不把 workflow、校验、事务或 IndexedDB 写回 JSX。OutlineSession 是唯一计划内容提交入口，支持：

- Outline state；
- Confirm outline；
- Edit / Reorder section；
- Change slide budget；
- 页面增删、移动及 purpose/message 编辑；
- Claim emphasis 与 Figure/Panel selection；
- Continue build。

UI 必须显示预算 mismatch、叙事 error/warning、candidate/stale 状态和保存失败。已有 Deck 的默认大纲仍展示 Current 的最终结构；进入 regeneration candidate 时与 Current 清楚区分。

## 保持不变的决策

## M9.2：Pure Migration（已完成）

按用户授权只为旧版 persisted Deck / DeckPlan 提供确定性、幂等、事务安全的 v1 → v2 惰性迁移；PlanRecord、叙事校验、Planning v2、生成状态机、OutlineSession、UI 与提示词均未开始。迁移优先级为：不破坏旧数据 > 确定性 > 可恢复 > 覆盖率；不能安全推断的数据宁可拒绝或回退重新规划。

### 失败与恢复行为

- 未来版本（>2 或无 schemaVersion）：`UnsupportedSchemaVersionError`，零写入，数据原样保留等待兼容应用。
- 稳定 Deck 损坏（legacy 解析失败或迁移后结构/引用校验失败）：可恢复错误，整批零写入（Current 不会被提前写回），修复数据后可重新打开。
- `deck-plan-ready` 的 v1 临时计划无法安全迁移（legacy 解析失败或引用校验失败）：同一事务内删除该计划并把 checkpoint 原子回退为 `paper-ready`；PDF、Paper、图源与 Project 其余字段不变，用户可显式重新规划。已是 v2 的计划损坏照常报错，不删除当前格式数据。

## M9.3：Narrative Validator（已完成）

按用户授权实现 DeckPlan v2 / Deck v2 的确定性学术叙事校验；Planning Prompt、one-shot repair、PlanRecord、OutlineSession、生成状态机、UI 与 persistence 均未开始、未修改。

### 两个入口与 issue 契约

- `src/modules/outline/validateNarrative.ts`（新增）导出 `validatePlanNarrative(plan, paper)` 与 `validateDeckNarrative(deck, paper)`，均返回 `NarrativeValidation = { errors: NarrativeIssue[]; warnings: NarrativeIssue[] }`；`NarrativeIssue` 按架构第 6 节携带 `code / severity / message / sectionId? / slideId? / elementId? / claimId? / figureId?`，severity 同时保留在条目上（架构声明）并按桶返回（本轮任务书确认的结果结构）。不使用 `DeckPlan | Deck` 联合入口。
- `src/modules/outline/narrativeRules.ts`（新增）为两个入口共享的普通确定性 helper：`planNarrativeView()` / `deckNarrativeView()` 把各自领域对象提取为同一只读 `NarrativeView`（sections 含可选 slideBudget、slides 含 figures/purpose?/message?），全部规则只作用于该视图；无 registry/rule class/framework。依据架构第 1 节模块树（"Plan/Deck 叙事校验"归 outline），Deck 入口放在 outline，不产生 deck → outline 依赖。

### Error codes（24 个，全部可定位）

结构骨架：`empty-plan`（confirmed 计划或 Deck 零页；draft 空计划不报）、`opening-required`（首章 opening 且首页 title）、`background-required` / `question-required` / `study-design-required`（首个 results 前需承担对应职责的 Section 或 Slide；question 可由 background 章内 question 页承担；设计职责仅在 `studyProfile.designSummary` 或 `story.studyDesign` 存在非空事实时要求）、`invalid-section-order`（opening 重复、前置职责出现在结果之后、最终 synthesis/takeaways 之后再现 results）、`results-required`（需 results 章且 result 页）、`ending-required`（最后一个非 custom 章必须为 synthesis 或 takeaways，limitations/discussion 不得单独收尾）。

结构引用：`unknown-section`、`duplicate-id`、`noncontiguous-section-slides`——与 validateDeck/validatePlan 同族不变量的可定位版本，按任务书在叙事入口返回 NarrativeIssue 供 Outline 定位，不替代基础校验的阻断职责。

内容职责：`result-claim-required`（结果页至少引用一个当前 Paper 的有效 Claim）、`result-purpose-required`（仅计划：结果页 purpose 非空）、`content-message-required`（title 与 custom 页豁免，其余内容页需非空 message）。

引用与证据链（基于真实 Paper schema：`Claim.evidenceIds → Evidence → Evidence.sourceIds → SourceReference`）：`unknown-claim`（页面引用与 claimEmphasis 引用都检查）、`unknown-source`、`unknown-figure`、`unknown-panel`、`claim-evidence-source-mismatch`（结果页每个 Claim 的证据来源与 `slide.sourceIds` 无交集）、`figure-source-mismatch`（Figure/Panel 的 Source 必须落在 `slide.sourceIds`）、`invalid-layout-figure-count`（复用 `layoutRules.layoutCapacity`，签名放宽为 `Pick<Slide, 'layoutId' | 'elements'>`，计划侧用仅含 figure 的元素集合套用同一契约，不建第二套映射）。

计划专属：`budget-mismatch`（仅 confirmed；draft 差额由 Outline UI 派生显示，不产生 issue）、`empty-confirmed-section`（仅 confirmed）、`omit-claim-referenced`（omit Claim 仍被任一 PlannedSlide 引用，按页定位）。不引入 primary/major Claim 层级。

### Warning codes（10 个）

`background-heavy`（background 页 / 总页数 > 25%）、`results-light`（result 页 / 总页数 < 50%）、`critical-discussion-missing`（无 limitations 且无 discussion 章）、`transition-missing`（非末尾章节缺 transitionToNext）、`generic-result-title`（有限标签集 + 窄 regex：空/result(s)/结果/主要结果/研究发现/主要发现/fig(ure) N/图 N）、`duplicate-message`（trim + 折叠空白 + 小写后完全一致）、`repeated-evidence-without-distinct-purpose`（Claim 集合、Figure 集合、message、purpose 规范化后全部一致，集合排序后比较）、`many-panels`（恰好 4 个 figure 且布局合法时提示；超过 4 个由布局容量报 error）、`focus-underallocated`（仅计划：focus Claim 少于两页结果承载）、`weak-ending`（收尾页与前一页 message 规范化后相同）。全部为透明条件，无 NLP/模型判断。

### 确定性与错误语义

输出顺序固定为：结构引用 → 骨架 → 内容 → 引用/证据 → 计划专属 → warnings，每条规则内部按 sections/slides/claim/figure 数组顺序迭代，不使用无序集合输出。同一输入两次校验 JSON 完全一致（测试断言）。错误语义为"可保存 draft、未来 confirm/build 应拒绝"：本轮未接入任何 persistence、confirm 门槛或 UI；Deck 入口只依据 Deck 实际内容，不含计划预算/focus 偏好，也不检查 build 忠实性。
