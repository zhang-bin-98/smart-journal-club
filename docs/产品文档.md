# Paper2PPT 产品文档

> 版本：MVP PRD v0.2  
> 状态：产品范围已基本确定，进入交互细化阶段  
> 定位：基于 Pi Agent 的科研论文自动生成 PPT 的纯前端 PWA，同时作为 Web Pi Agent 的垂直切片 MVP。

---

## 1. 产品概述

Paper2PPT 是一个面向**生物医学原创研究论文（Original Research Article）**汇报场景的本地优先 PWA。

用户上传一篇科研论文 PDF 后，系统自动完成：

1. PDF 解析；
2. 论文结构和核心内容理解；
3. Figure / Panel 识别与提取；
4. 汇报逻辑和 PPT 大纲规划；
5. 幻灯片内容生成与自动排版；
6. 浏览器内预览；
7. 根据用户自然语言意见继续调整；
8. 导出标准 `.pptx` 文件。

产品的核心体验不是“一键生成后结束”，而是：

> **先自动生成一套可用的科研汇报 PPT，再通过 Agent 持续修改。**

---

# 2. 产品定位

## 2.1 核心定位

Paper2PPT 不是通用 Agent，也不是网页版 PowerPoint。

它是一个：

> **Workflow-first、Agent-assisted 的科研 PPT 生成工具。**

工作流固定，Agent 主要处理需要理解、判断、取舍和修改的部分。

---

## 2.2 与 Web Pi Agent 的关系

Paper2PPT 同时承担一个工程验证目标：

> 作为 Web Pi Agent 的垂直切片 MVP，验证 Agent、Tool Calling、结构化 Artifact、本地持久化和用户反馈驱动修改等核心模式。

优先完成垂直产品，不提前建设完整通用 Agent 平台。

未来只有真正稳定、明确可复用的组件，才抽象回 Web Pi Core。

---

# 2.3 论文范围

首版只针对：

> **生物医学原创研究论文（Biomedical Original Research Article）**

产品围绕生物医学论文常见的信息结构优化：

```text
Scientific Background
→ Knowledge Gap
→ Research Question / Hypothesis
→ Study Design
→ Experiment / Cohort / Omics Analysis
→ Main Findings
→ Mechanistic / Validation Evidence
→ Biological / Clinical Interpretation
→ Limitations
→ Conclusion
```

因此产品可以针对生物医学领域建立更强的默认判断，例如：

- 区分实验组 / 对照组；
- 理解 cohort、sample、tissue、cell type；
- 识别实验设计和验证链；
- 理解单细胞、空间组学、多组学等常见分析流程；
- 理解 phenotype、pathway、mechanism、biomarker、endpoint 等常见研究对象；
- 优先维护 Figure / Panel 与科学 Claim 的证据关系。

首版**不考虑综述型文章**，也不为综述建立独立工作流。

---

# 3. MVP 核心目标

MVP 只验证一个完整场景：

> **上传一篇科研论文 PDF → 自动生成一套 10–20 页科研汇报 PPT → 用户通过自然语言和少量直接编辑进行调整 → 导出 PPTX。**

MVP 成功的判断标准不是“功能很多”，而是：

- 生成结果基本可用；
- Figure 使用正确；
- 汇报逻辑连贯；
- 用户修改成本低；
- 修改不会频繁破坏其他 Slide；
- 导出的 PPTX 可以继续编辑。

---

# 4. 目标用户

第一阶段主要面向生物医学领域的：

- 硕士生；
- 博士生；
- 博士后；
- 科研人员；
- 需要做 Journal Club、组会、文献汇报的人。

首版重点覆盖：

- 基础生物医学研究；
- 机制研究；
- 细胞 / 动物实验；
- 单细胞、空间组学、多组学等生物信息研究；
- 转化医学研究；
- 临床研究型论文。

---

# 5. 核心使用场景

## 5.1 Journal Club

用户需要快速把一篇论文整理成：

- 背景；
- 科学问题；
- 方法；
- 主要结果；
- 创新点；
- 局限性；
- 结论。

---

## 5.2 组会文献汇报

重点展示：

- Figure；
- Panel；
- 结果逻辑；
- 作者如何从一个结果推进到下一个结果。

---

## 5.3 快速阅读后制作 PPT

用户不想先完整读完论文再自己做 PPT。

Paper2PPT 负责提供第一版结构，用户再基于自己的理解进行修正。

---

# 6. 核心用户价值

## 6.1 降低机械整理成本

减少：

- 复制论文文字；
- 手工截 Figure；
- 拆 Figure Panel；
- 整理大纲；
- 新建幻灯片；
- 摆放图片；
- 编写结果页标题；
- 根据意见反复调整结构。

---

## 6.2 保留科研汇报逻辑

产品不只是“总结论文”，而是生成适合讲述的 Deck：

- 为什么这个问题重要；
- 作者提出了什么问题；
- 如何验证；
- 每张 Figure 回答什么问题；
- Figure 之间如何连接；
- 最后得出了什么结论。

---

## 6.3 支持持续修改

例如：

- “背景压缩成两页。”
- “Figure 3 只留 B、C 两个 panel。”
- “把 Figure 4 拆成两页。”
- “结果页标题都改成结论句。”
- “增加一页研究设计流程图。”
- “结论部分再突出一下创新点。”

系统只修改受影响部分，不重新生成整个项目。

---

# 7. 产品原则

## 7.1 Workflow First

主流程固定：

```text
上传 PDF
  ↓
解析论文
  ↓
理解论文
  ↓
识别 Figure
  ↓
规划大纲
  ↓
生成 Deck
  ↓
预览
  ↓
用户修改
  ↓
导出 PPTX
```

Agent 不自由探索整个任务。

---

## 7.2 默认一路自动生成

这是 MVP 的明确产品决策。

### 不采用

```text
上传
→ 生成大纲
→ 强制等待用户确认
→ 生成 PPT
```

### 采用

```text
上传
→ 自动完成全部分析
→ 自动生成完整 PPT
→ 用户直接看结果
→ 再修改
```

大纲仍然存在于内部结构中，但不是强制交互关卡。

如果用户想看，可以：

- 在 Agent 中询问；
- 后续增加 Outline View。

---

## 7.3 Structured First

核心中间状态：

```text
PDF
 ↓
Paper AST
 ↓
Deck AST
 ↓
PPTX
```

Agent 修改结构化状态，而不是直接修改 PPTX。

---

## 7.4 Local First

- PDF 默认保留在浏览器；
- 项目状态保存在浏览器；
- 用户使用自己的 API Key；
- PPTX 在浏览器中生成；
- 项目自身不建设文件上传后端。

---

## 7.5 少交互

系统应优先自动完成能可靠自动完成的事情。

不应该频繁询问：

- “是否继续？”
- “是否确认？”
- “是否使用这个 Figure？”
- “是否接受这个大纲？”

只有真正需要用户判断、无法自动恢复或可能造成明显数据损失时才需要确认。

---

## 7.6 Agent 修改默认直接执行

用户通过自然语言提出修改后：

```text
用户请求
→ Agent 判断
→ 修改 Deck
→ 自动刷新
→ 告诉用户改了什么
```

不默认：

```text
Agent 提议修改
→ 用户再次确认
→ 才执行
```

通过：

- Undo；
- Redo；
- 修改摘要；

提供可控性。

---

## 7.7 模板优先

Agent 选择：

- Slide 类型；
- Layout；
- 内容；
- Figure；

而不是自由设计所有坐标。

---

## 7.8 不过度设计

MVP 不提前扩展为：

- 通用 Agent；
- PowerPoint Clone；
- 在线办公平台；
- 多模型平台；
- 云端协作平台。

---

# 10. 创建项目

## 10.1 上传

支持：

- Drag & Drop；
- 文件选择。

第一版仅支持：

```text
.pdf
```

---

## 10.2 上传后的项目创建

系统立即：

1. 创建本地 Project；
2. 保存 PDF；
3. 尝试读取 metadata / 第一页；
4. 自动识别标题；
5. 显示轻量生成入口。

---

## 10.3 生成要求

不使用复杂表单。

只提供一个自然语言输入框：

```text
你希望怎么汇报这篇论文？（可选）

例如：
“中文，15页左右，重点讲结果和创新点”
```

按钮：

```text
[ 生成 PPT ]
```

---

## 10.4 默认生成策略

如果用户完全不填写要求：

- 默认生成适合科研组会 / Journal Club 的 PPT；
- 默认目标约 12–16 页；
- 背景适度；
- 重点突出主要 Figure；
- 方法只保留理解结果必要的信息；
- 结果页标题优先采用结论句；
- 最后包含总结 / 创新点 / 局限性。

输出语言的默认策略在 MVP 开发前需要最终确定。

# 11. 自动生成阶段

## 11.1 页面目标

让用户知道：

- 系统正在工作；
- 当前大概做到哪里；
- 是否出错；
- 可以取消。

不暴露大量底层 Agent Tool Call。

---

## 11.2 高层进度

UI 显示：

```text
正在制作 PPT

✓ 解析论文
✓ 理解研究内容
● 分析 Figures
○ 规划汇报结构
○ 制作幻灯片
```

阶段名称保持用户语言，不展示内部函数名。

---

## 11.3 工作流阶段

建议：

```text
1. 解析论文
2. 理解研究内容
3. 分析 Figures
4. 规划汇报结构
5. 制作幻灯片
6. 完成
```

不需要把内部每一个 API 请求都变成用户进度项。

---

## 11.4 用户操作

生成阶段允许：

```text
[ 取消 ]
```

可选：

```text
[ 返回首页 ]
```

但返回首页不应自动中断，只要当前实现能够安全保持任务状态。

MVP 若暂时无法可靠后台保持，则返回首页前提示会中断当前生成。

---

## 11.5 自动进入编辑器

生成完成后：

```text
Generating
→ Project Editor
```

不再增加：

```text
“生成完成，是否查看？”
```

这种额外确认。

---

# 12. 自动生成质量策略

## 12.1 PPT 不是论文全文摘要

系统应优先：

- 讲故事；
- 选择重点；
- 使用 Figure；
- 控制每页信息量。

不追求把所有内容塞进去。

---

## 12.2 Slide 标题

结果页优先使用结论句，例如：

推荐：

```text
Aging activates inflammatory signaling in endothelial cells
```

不推荐：

```text
Results 3
```

---

## 12.3 单页内容

默认：

- 一个核心 message；
- 一组相关 Figure / Panel；
- 少量辅助文字。

避免：

- 大段正文；
- 一页多个无关结论；
- Figure 太小；
- 文字覆盖 Figure。

---

## 12.4 Figure 使用

默认优先使用论文原 Figure。

如果一张 Figure 信息过多：

- 选择部分 Panel；
- 拆分成多页；
- 保留原 Figure / Panel 来源。

# 18. Agent Chat

Agent 是“编辑助手”，不是开发者控制台。

不展示复杂：

## 18.2 输入示例

```text
“背景太多了，压成两页。”

“Figure 3 只保留 B 和 C。”

“这一页文字太多。”

“再增加一页创新点总结。”
```

# 19. Agent 修改行为

## 19.1 默认直接执行

```text
用户请求
 ↓
Agent
 ↓
修改
 ↓
刷新 Slide
 ↓
返回修改摘要
```

---

## 19.2 修改完成反馈

推荐：

```text
已完成调整

✓ 合并第 2–3 页背景
✓ 重写第 6 页标题
✓ 将 Figure 4 拆成两页

共修改 4 页

[ 撤销 ]
```

---

## 19.3 不展示

MVP 默认不展示：

```text
Called tool deck.patch_slide(...)
```

这些属于调试信息。

---

## 19.4 Agent 修改范围

Agent 应尽量最小化影响范围。

例如用户：

> “第 7 页标题改得更明确一些。”

默认只修改：

```text
slide-07.title
```

而不是重新规划整个 Deck。

---

# 20. Undo / Redo

这是 Agent 直接执行修改的关键保护机制。

必须至少支持：

```text
Undo
Redo
```

一次 Agent 请求导致的多个 Deck Mutation 应尽可能作为一个逻辑操作撤销。

例如：

```text
“把 Figure 4 拆成两页”
```

产生多个内部修改，但用户点击一次 Undo 应恢复到请求之前。

---

# 21. Add Slide

用户可以：

```text
[ + Add Slide ]
```

MVP 可先创建一个：

```text
blank / text-only
```

Slide。

之后用户：

- 手动填写；
- 或告诉 Agent “把这一页补成方法总结”。

不需要第一版实现大型 Template Picker。

---

# 22. Delete

删除 Slide：

可以直接执行，但应该：

- 支持 Undo；
- 或提供短暂 Toast Undo。

不需要每次弹确认对话框。

删除整个项目则需要确认。

```text

```

后续如果需要，可增加 Outline Drawer。

```text

```

但 UI 可以后置。

- 每页讲解备注；
- Figure 解读；
- 过渡语；

# 47. 已确认的产品决策

当前已经确认：

1. Paper2PPT 是 Web Pi Agent 的垂直切片 MVP；
2. 产品本质是固定 Workflow，而不是开放式 Agent；
3. 纯前端 PWA；
4. Agent 驱动论文理解和 Deck 修改；
5. 使用 Paper AST / Deck AST；
6. Agent 不直接生成 PPTX；
7. PDF Figure MVP 使用页面渲染 + crop；
8. 第一版只支持少量固定模型；
9. DeepSeek 只使用 `deepseek-v4-flash-vision-exp`；
10. GLM 使用 `glm-5.3-flash`；
11. 模型走 OpenAI-compatible adapter；
12. 不做 Shell / MCP / Plugin Marketplace；
13. **生成大纲后不强制暂停确认，默认一路生成完整 PPT；**
14. **Agent 修改默认直接执行，通过 Undo / Redo 提供可恢复性；**
15. **默认输出语言：有用户要求则遵从，否则使用论文主要语言；**
16. **Source Preview 为 P0 必须功能；**
17. **Drag / Resize 不阻塞首个 MVP；**
18. **首版仅针对生物医学原创研究论文优化，不支持 Review 工作流；**
19. **项目按稳定 Checkpoint 自动保存，中断后从最近完成阶段继续；**
20. **切换 Provider 不自动重新分析论文或重建 Deck；**
21. **Regenerate Deck 不原地覆盖当前版本，成功后再切换，并保留上一 Major Snapshot。**

# 48. 已确认的交互细节

## 48.1 默认输出语言

采用以下规则：

> **用户在生成要求中明确指定语言时，优先遵从用户要求；如果用户没有指定，则默认使用论文主要语言。**

MVP 不额外增加“中文 / English”选择框，避免增加创建项目时的表单复杂度。

---

## 48.2 Source Preview

Source Preview 正式列为 **P0 必须功能**。

原因：

- 科研场景需要可追溯性；
- 用户需要确认 Figure、结论和引用是否来自正确位置；
- Figure 自动裁剪存在误差时，Source Preview 也是修正入口；
- 这是 Paper2PPT 区别于普通 AI PPT 生成器的重要能力。

首版至少应支持：

```text
Figure / Citation
→ 查看来源
→ 打开 PDF 原页
→ 高亮对应区域
→ 查看 Figure label / Caption / 来源文本
```

---

## 48.3 Drag / Resize

Drag / Resize **不作为首个 MVP 的阻塞项**。

首版优先保证：

```text
Layout 自动排版
+ 文本编辑
+ Slide reorder
+ Figure crop
+ Agent 修改
```

只有实际试用证明模板排版不足以覆盖主要需求时，再将自由拖动和尺寸调整提升优先级。

# 50. 自动生成策略

自动生成的目标不是把论文按章节机械拆成幻灯片，而是：

> **根据论文的科学问题、证据链和主要 Figure，生成一套适合口头汇报的科学故事。**

生成策略必须优先保证：

1. 故事线清楚；
2. 每页只有一个主要信息；
3. Figure 足够大、可读；
4. 主要结论有来源；
5. 不为了凑页数重复内容；
6. 不为了“好看”创造论文中不存在的信息。

---

# 51. 默认 Deck 目标

如果用户没有指定页数，MVP 默认生成：

```text
约 12–16 页
```

默认适用于：

```text
15–25 分钟 Journal Club / 组会文献汇报
```

这是目标范围，不是硬编码固定页数。

系统应根据论文复杂度自动调整。

例如：

```text
结构简单、主要结果少
→ 10–12 页

常规研究论文
→ 12–16 页

Figure 较多、结果链较长
→ 16–20 页
```

MVP 默认不主动生成超过约 20 页的 Deck，除非用户明确要求。

---

# 52. 用户生成要求的优先级

创建项目时的自然语言要求高于默认策略。

例如：

```text
“中文，10页以内，只讲核心结果”
```

系统应主动压缩：

- 背景；
- 方法；
- 次要 Figure；
- Discussion。

例如：

```text
“20页左右，方法讲详细一点”
```

系统可以增加：

- Study Design；
- Experimental Workflow；
- Computational Pipeline；
- 关键方法解释。

---

## 52.1 可从自然语言识别的偏好

MVP 不做复杂表单，但 Agent 应从生成要求中尽量识别：

```text
语言
目标页数
汇报时长
听众水平
重点部分
希望弱化的部分
汇报用途
视觉风格
```

例如：

```text
“给实验室组会讲，中文，15页左右，重点解释Figure和创新点”
```

可以映射为：

```text
language = zh
audience = research-group
targetSlides ≈ 15
focus = figures + novelty
presentationType = journal-club
```

这些信息属于内部生成偏好，不要求用户看到参数面板。

---

# 53. 默认受众假设

如果用户没有指定听众：

> 默认假设听众具有相关科研背景，但没有读过这篇论文。

因此：

- 不需要从教科书最基础概念开始；
- 需要解释论文特有问题；
- 方法只讲理解结果所需要的部分；
- 专业术语可以保留；
- Figure 应提供必要的阅读提示。

---

# 54. 默认故事结构

常规原创研究论文优先采用：

```text
Title
 ↓
Background
 ↓
Knowledge Gap / Problem
 ↓
Research Question / Hypothesis
 ↓
Study Design / Key Methods
 ↓
Main Result 1
 ↓
Main Result 2
 ↓
Main Result 3
 ↓
...
 ↓
Integrated Model / Summary
 ↓
Novelty / Limitations / Conclusion
```

不要求机械对应论文原始：

```text
Introduction
Methods
Results
Discussion
```

章节顺序。

---

# 55. 默认页数分配

以约 14 页 Deck 为例，可参考：

```text
Title                         1
Background                    1–2
Knowledge Gap / Question      1
Study Design / Methods        1–2
Main Results                  6–8
Summary / Model               1
Novelty / Limitations         1
Conclusion                    1
```

这只是默认预算。

真正页数应优先服从：

```text
论文科学故事
+
主要 Figure 数量
+
用户要求
```

---

# 56. 结果部分优先原则

科研汇报的核心通常是 Results。

默认情况下，结果部分应该占整套 Deck 的最大比例。

如果用户没有特殊要求：

> **优先保留结果，优先压缩背景和方法。**

当页数不足时，内容压缩顺序建议为：

```text
次要背景
→ 非关键方法细节
→ 次要结果
→ Discussion 延伸
```

核心结果和关键 Figure 应最后才被压缩。

---

# 57. One Slide, One Message

默认遵循：

> **一页一个主要科学信息。**

每个结果页应能够用一句话回答：

```text
“这一页想让听众记住什么？”
```

这个句子通常应该直接成为：

```text
Slide.title
或
Slide.message
```

例如：

不推荐：

```text
Figure 3
```

推荐：

```text
Aging induces an inflammatory endothelial state
```

---

# 58. Slide 标题策略

## 58.1 Title Slide

包含：

- 论文标题；
- 作者；
- 期刊；
- 年份。

可适当缩短过长标题，但不能改变原意。

---

## 58.2 Background / Method

可以使用主题型标题：

```text
Cellular aging reshapes the vascular microenvironment
```

---

## 58.3 Result Slide

优先使用：

> **结论句 / Take-home Message**

而不是：

```text
Result 1
Figure 2
RNA-seq results
```

---

## 58.4 Conclusion Slide

标题应尽量表达论文最终回答，而不是简单写：

```text
Conclusion
```

如果版式需要，也可以保留 Section Label，再配主要结论。

---

# 59. Figure 选择原则

系统不应默认把论文所有 Figure 都放进 PPT。

Figure 选择优先级：

```text
支持核心结论的 Figure
>
支撑关键因果链 / 证据链的 Figure
>
体现论文创新性的 Figure
>
解释核心方法所必需的 Figure
>
补充性 / 验证性 Figure
```

---

## 59.1 优先保留

- Main Figure；
- 支撑主要 claim 的 Panel；
- 体现创新技术或关键机制的 Panel；
- 用于连接两个主要结果的证据。

---

## 59.2 默认弱化

除非对理解论文必要，否则减少：

- 大量 QC；
- 重复验证；
- 次要 Supplementary Figure；
- 与核心故事关系较弱的亚组；
- 非关键参数调优；
- 冗余 control。

---

# 60. Figure 与 Slide 的映射

系统应根据“科学信息单位”而不是 Figure 编号决定 Slide。

因此：

```text
Figure 2
```

不一定等于：

```text
1 Slide
```

可能是：

```text
Figure 2A–C → Slide 1
Figure 2D–F → Slide 2
```

也可能：

```text
Figure 2 + Figure 3A
→ 同一 Slide
```

前提是它们共同支撑同一个明确 message。

---

# 61. Whole Figure 与 Panel 的选择

## 61.1 优先使用整张 Figure 的情况

- Figure 本身结构简单；
- Panel 数量较少；
- 所有 Panel 都服务于同一个结论；
- 放进 Slide 后仍然可读；
- 听众需要理解完整实验链条。

---

## 61.2 优先拆 Panel 的情况

- Figure Panel 很多；
- 整图缩小后无法阅读；
- 只有部分 Panel 与当前 message 有关；
- Figure 内包含两个或多个独立结论；
- 当前汇报只需要其中部分证据。

---

# 62. Figure 拆页规则

建议拆成多页的情况：

```text
一张 Figure 包含多个主要结论

或

关键 Panel 太多，单页无法保持可读性

或

实验逻辑存在明确的“观察 → 验证 → 机制”过程
```

例如：

```text
Slide A
观察到 phenotype

Slide B
验证 pathway

Slide C
mechanistic experiment
```

而不是把所有 Panel 缩成一张看不清的大图。

---

# 63. Figure 合并规则

默认可以在同一 Slide 合并多个来源 Figure，但需要同时满足：

1. 支持同一个 message；
2. 视觉上仍然可读；
3. 来源标识清楚；
4. 不造成实验关系误解。

如果无法满足，宁可拆成两页。

---

# 64. Figure 科研完整性规则

Figure crop 和重排不能改变科研含义。

系统不得：

- 拉伸 Figure 改变比例；
- 去掉理解结果必需的坐标轴；
- 去掉关键图例；
- 去掉必要的组别名称；
- 去掉统计显著性信息；
- 通过裁剪制造不同于原论文的比较关系。

如果必须裁掉部分图例，应确保 Slide 上仍能解释对应颜色 / 组别。

---

# 65. Panel Label

裁剪单个 Panel 时，优先保留原始：

```text
A
B
C
...
```

标签。

如果原标签不在 crop 范围内：

- 可以在 Slide 上补充 `Fig. 3B` 来源标签；
- 但不能让用户误以为它是论文中新定义的 Panel。

---

# 66. Figure Caption 的处理

不直接把论文长 Caption 整段复制进 Slide。

Slide 中优先展示：

```text
短 Figure Label
+
简短解释
+
Source
```

完整 Caption 在：

```text
Source Preview
```

中查看。

---

# 67. Figure Source 格式

MVP 每个 Figure 元素都保留：

```text
Figure ID
Panel ID
PDF Page
bbox
Caption
```

展示层至少可以提供类似：

```text
Source: Fig. 3B, p.8
```

具体视觉格式由 Theme 决定。

---

# 68. 方法部分生成策略

方法页的目标不是复述 Methods，而是帮助听众理解：

> “作者是怎么回答这个问题的？”

优先生成：

- Study Design；
- Cohort / Sample；
- Experimental Workflow；
- Data Modality；
- Key Analytical Pipeline；
- 关键实验验证方式。

---

## 68.1 默认不展开

除非用户要求，否则不详细展示：

- 试剂品牌；
- 软件次版本；
- 每个参数；
- 常规实验步骤；
- 次要统计细节。

---

# 69. 方法流程图

如果论文的实验 / 分析流程适合结构化表达，系统可以生成：

```text
Samples
→ Experiment
→ Data
→ Analysis
→ Validation
```

形式的简单流程图。

MVP 的方法流程图应由：

- 文本；
- Shape；
- Arrow；

组成。

不依赖额外生成式图片模型。

---

# 70. 结果 Figure 不进行“AI 重画”

MVP 不把论文结果图重新生成成新的数据图。

原则：

> **结果证据优先使用论文原 Figure / Panel。**

可以做：

- crop；
- 排版；
- 放大；
- 组合；
- 加简短文字解释；
- 加箭头 / 框作为视觉提示。

但不重新绘制数据导致潜在数值偏差。

---

# 71. 视觉标注

后续可以允许轻量标注：

```text
Arrow
Box
Highlight
```

用于指出 Figure 中的重点。

但标注不能：

- 遮挡数据；
- 暗示论文未支持的结论；
- 改变原 Figure 内容。

如果首版实现压力较大，可以后置。

---

# 72. Background 生成策略

背景页只保留理解论文问题所必要的信息。

默认最多约：

```text
1–3 页
```

除非用户明确要求做教学型汇报。

推荐结构：

```text
Known
 ↓
Unknown / Gap
 ↓
Question
```

避免做成文献综述。

---

# 73. Knowledge Gap

如果论文有明确的研究空白，建议单独强调：

```text
What is known?
What is missing?
What does this study ask?
```

这通常比单纯介绍背景更适合科研汇报。

---

# 74. Conclusion / Summary

最后部分应回答：

```text
作者最终发现了什么？
这项工作为什么重要？
有哪些关键限制？
```

默认不只是重复 Results 标题。

---

# 75. 创新点

系统可以自动总结：

- Conceptual novelty；
- Methodological novelty；
- Dataset / resource novelty；
- Mechanistic novelty；
- Translational relevance。

但必须基于论文内容。

如果论文没有明确支持某种创新：

> 不为了让 PPT “更厉害”而虚构创新点。

---

# 76. Limitations

默认可以生成一页或与 Summary 合并。

Limitations 的来源优先：

1. 论文作者 Discussion 中明确承认的限制；
2. 从研究设计直接可判断、且表述谨慎的限制。

必须避免把 Agent 的主观批评写成论文既定事实。

对于推断性批评，可使用：

```text
Possible limitation
Potential concern
```

等明确措辞。

---

# 77. 生物医学研究型论文适配

MVP 明确只针对：

> **生物医学原创研究论文（Biomedical Original Research Article）**

首版产品策略不是“尽量兼容所有论文类型”，而是针对生物医学研究论文做深度优化。

不把以下类型纳入首版支持范围：

- Narrative Review；
- Systematic Review；
- Meta-analysis；
- Perspective；
- Commentary；
- Editorial；
- Guideline；
- Consensus；
- 纯病例报告。

如果用户上传这类文章，产品可以识别并提示：

> 当前版本主要针对生物医学原创研究论文优化，这类文章暂不属于首版支持范围。

首版不为 Review 单独设计主题归纳、文献聚类或综述型 Deck 工作流。

---

## 77.1 基础 / 机制实验研究

重点：

```text
Background
Question
Experiment
Results
Mechanism
Conclusion
```

---

## 77.2 生物信息 / 多组学研究

重点：

```text
Cohort / Samples
Data Modalities
Analysis Workflow
Main Biological Findings
Validation
Conclusion
```

避免把所有 QC / pipeline 参数都放入 PPT。

---

## 77.3 临床研究

重点：

```text
Population
Study Design
Endpoints
Main Outcomes
Subgroup / Safety
Limitations
Conclusion
```

---

## 77.4 方法 / 工具论文

允许提高方法与 Benchmark 占比：

```text
Problem
Existing Limitations
New Method
Workflow
Benchmark
Application
Conclusion
```

---

## 77.5 转化医学研究

重点：

```text
Clinical / Biological Problem
Study Design
Patient / Sample Cohort
Experimental / Omics Evidence
Mechanistic Validation
Clinical Relevance
Limitations
Conclusion
```

对于同时包含患者队列、组学分析和实验验证的论文，应尽量保持：

```text
Clinical Observation
→ Molecular Finding
→ Mechanistic Evidence
→ Translational Implication
```

这一证据链。

---

# 78. Supplementary Figure

MVP 不主动搜索额外 Supplementary 文件。

如果 Supplementary Figure 已经包含在当前 PDF 中：

- 可以分析；
- 但默认优先级低于 Main Figure。

只有当它：

- 支撑关键结论；
- Main Figure 无法完整说明；
- 用户明确要求；

时才优先进入 Deck。

---

# 79. 生成前的 Paper Understanding

在正式创建 Slide 前，系统应先形成一个内部“论文故事模型”。

至少理解：

```text
研究背景
核心问题
研究对象
研究设计
主要实验 / 分析
关键 Claim
Claim 对应 Evidence
关键 Figure / Panel
作者结论
创新点
局限性
```

这一步用于避免：

> 按 PDF 页码顺序机械做 PPT。

---

# 80. Claim–Evidence 关系

主要结果应尽量建立：

```text
Claim
 ↕
Evidence
 ↕
Figure / Panel / Source
```

Deck 生成时优先从 Claim 出发决定：

```text
这一页讲什么
→ 用什么 Figure
```

而不是：

```text
看到 Figure
→ 随便生成一页
```

---

# 81. Slide Planning

正式渲染前应存在内部 Slide Plan。

每页至少包含：

```text
slide type
message
title
selected evidence
selected figure / panels
layout
```

例如：

```text
Type: Result
Message: Aging increases endothelial inflammatory signaling
Evidence: Claim-05
Figure: Fig.3B, Fig.3D
Layout: figure-left-text-right
```

用户不需要在首次生成中确认这个 Plan。

---

# 82. 内容长度规则

默认应主动限制文字。

建议产品行为：

### Title

尽量：

```text
1–2 行
```

### Result 页辅助文字

优先：

```text
1–3 个短点
```

### 大段解释

放到：

- Agent Chat；
- Source Preview；
- 未来 Speaker Notes。

而不是全部塞到 Slide。

---

# 83. Slide 拥挤判断

生成完成前，应检查：

- 标题是否过长；
- 正文是否过多；
- Figure 是否过小；
- 多个 Figure 是否拥挤；
- Caption 是否占用过多空间。

如果存在明显拥挤：

优先：

```text
拆页
>
删减非核心文字
>
换 Layout
>
减少 Figure
```

而不是无限缩小字体。

---

# 84. 最小可读性原则

系统不应为了塞下内容而无限缩小：

- 字体；
- Figure；
- Label。

如果一页无法清晰表达，应拆成多页。

具体最小字号由 Theme / Layout 实现层统一控制。

产品规则只要求：

> **可读性优先于单页信息密度。**

---

# 85. 自动质量检查

Deck 初次生成完成后，在展示给用户前应进行一次自动检查。

至少检查：

```text
是否存在标题页
是否交代科学问题
是否覆盖主要结果
是否有明显重复 Slide
是否存在空 Slide
是否存在无来源的主要 Figure
是否存在明显拥挤
是否存在语言混乱
是否遗漏论文主要结论
```

---

# 86. 科研事实检查

对于重要 Claim：

系统应尽量确认：

```text
Claim
→ Paper Source
```

如果无法找到足够来源：

- 不应强行作为确定事实写入；
- 可以降低表述强度；
- 或删除该内容。

---

# 87. 禁止幻觉的产品规则

Paper2PPT 不应：

- 编造实验；
- 编造样本量；
- 编造统计结果；
- 编造 Figure；
- 编造作者结论；
- 编造机制；
- 编造引用。

当模型不确定时：

> 宁可少写，也不要补齐不存在的信息。

---

# 88. AI 推断与论文结论的区分

如果需要加入 Agent 自己的分析，应明确区分：

```text
Paper conclusion
```

与：

```text
AI interpretation
```

MVP 默认 PPT 主体优先使用论文内容。

AI 的额外批判和延伸更适合：

- Agent Chat；
- Limitations；
- Discussion；

并明确语气。

---

# 89. 语言一致性

同一 Deck 默认使用一种主要语言。

用户要求中文时：

- 标题；
- 正文；
- Summary；

使用中文。

论文中的：

- 基因名；
- 蛋白名；
- 软件名；
- pathway；
- 专业缩写；

不强制翻译。

Figure 原图中的英文保持原样。

---

# 90. 术语一致性

同一概念在整个 Deck 中应尽量使用一致术语。

例如不应在不同 Slide 无原因切换：

```text
endothelial cell
vascular endothelial cell
EC
```

如果首次定义缩写：

```text
endothelial cells (ECs)
```

之后可以统一使用：

```text
ECs
```

---

# 91. 初次生成完成时的呈现

用户第一次进入 Editor 时，系统可以给一个非常简短的摘要：

```text
已生成 15 页 PPT

- 2 页背景
- 2 页研究设计
- 8 页主要结果
- 3 页总结与讨论

使用 6 个主要 Figures
```

并提供：

```text
“告诉我你想怎么调整。”
```

不需要展示完整内部 planning log。

---

# 92. 用户修改后的再平衡

当用户做较大范围修改，例如：

```text
“把背景全部压成一页”
```

Agent 可以自动重新检查：

- 页码顺序；
- Section 过渡；
- 总页数；
- 是否产生空白；
- 是否出现重复。

但不应该借机重新改写用户没有要求的所有结果页。

---

# 93. 全局修改

明确属于全局操作的请求，例如：

```text
“所有结果页标题改成结论句”
“整体压到12页”
“全部改成中文”
```

Agent 可以批量修改。

修改完成后必须给出摘要，例如：

```text
已修改 9 页
```

并支持一次 Undo。

---

# 94. 局部修改

局部请求：

```text
“第7页太挤了”
“Figure 3B 再放大一些”
```

Agent 默认只读取和修改必要上下文。

产品行为上应体现：

> **局部请求 → 局部变化。**

---

# 95. Regenerate 的产品语义

需要区分：

### Modify

在当前 Deck 基础上修改。

### Regenerate Slide

重新生成当前 Slide 的内容 / 布局。

### Regenerate Deck

重新规划整套 Deck。

MVP UI 不一定全部暴露按钮，但 Agent 必须理解三者不同。

默认用户的自然语言请求应优先解释为：

```text
Modify
```

而不是整套重新生成。

---

# 96. 首版生成策略验收

选择一篇结构正常、包含多张 Figure 的原创科研论文。

系统生成结果至少应满足：

1. 背景不占据 Deck 大部分篇幅；
2. 能识别论文主要科学问题；
3. 主要结果占最大比例；
4. 至少覆盖论文最主要的 Claim；
5. 核心 Claim 有对应 Figure / Source；
6. 复杂 Figure 能合理拆 Panel；
7. Figure 在 Slide 上基本可读；
8. Result Slide 标题以结论句为主；
9. 不出现明显重复 Slide；
10. 不出现明显编造的实验或结论；
11. 最后有清晰 Summary / Conclusion；
12. 用户可以继续通过 Agent 修改结构。

---

# 96.1 生物医学领域专项验收

除通用生成质量外，首版还应重点验证系统能否正确处理生物医学论文中的：

1. 实验组 / 对照组关系；
2. 样本、组织、细胞类型和 cohort；
3. 主要 phenotype；
4. 关键实验设计；
5. Figure Panel 与结论之间的证据关系；
6. “发现 → 验证 → 机制”类结果链；
7. 单细胞 / 空间组学 / 多组学分析中的主要生物学结论；
8. 临床论文中的 population、endpoint、outcome；
9. 作者明确提出的 biological / clinical implication；
10. 作者明确承认的 limitations。

对于无法可靠判断的生物医学术语、实验关系或机制，不应自行补全。

---

# 97. 当前生成策略的核心原则

可以浓缩成：

```text
先理解论文
→ 找到 Claim–Evidence
→ 规划故事
→ 分配 Slide Budget
→ 选择 Figure / Panel
→ 一页一个 Message
→ 自动检查
→ 展示完整 Deck
```

而不是：

```text
按 PDF 页面
→ 摘几句话
→ 截图
→ 拼成 PPT
```

这应该成为 Paper2PPT 最重要的产品差异之一。

---

# 98. 生物医学论文的默认故事模板

Paper2PPT 不应对所有生物医学原创研究论文使用同一套固定 Slide 顺序。

首版至少应识别以下四类研究结构：

```text
A. 基础 / 机制实验型
B. 组学 / 生物信息型
C. 临床研究型
D. 转化 / 混合型
```

这些不是用户必须选择的“模板类型”，而是系统内部的生成策略。

默认流程：

```text
解析论文
→ 判断研究结构
→ 选择默认 Story Template
→ 根据实际论文内容调整
→ 生成 Deck
```

不应强迫一篇论文完全符合某个模板。

---

# 99. 论文类型自动判断

系统应根据全文、Methods、Results、Figure 和 metadata 自动判断论文主要研究结构。

判断信号可以包括：

```text
实验模型
患者队列
动物实验
细胞实验
单细胞
空间组学
bulk omics
多组学
临床 endpoint
生存分析
机制验证
干预实验
外部验证队列
```

最终内部可产生：

```text
primaryStudyType
secondaryStudyTypes
```

例如：

```text
primaryStudyType = omics
secondaryStudyTypes = [mechanistic, translational]
```

因为真实生物医学论文经常是混合结构。

---

# 100. 不要求用户手动选论文类型

MVP 创建项目时不增加：

```text
[ 机制研究 ]
[ 生信研究 ]
[ 临床研究 ]
```

这种额外表单。

原因：

- 增加用户判断成本；
- 很多论文本身是混合型；
- 系统已经需要理解论文结构；
- 自动判断错误后可以通过 Agent 修正。

例如用户可以说：

```text
“这篇文章重点不是机制，主要讲单细胞图谱。”
```

系统据此调整 Deck。

---

# 101. A 类：基础 / 机制实验型论文

典型研究包括：

- 分子机制；
- 细胞实验；
- 动物模型；
- 基因敲除 / 过表达；
- 药物干预；
- signaling pathway；
- phenotype + mechanism；
- rescue experiment。

默认故事线：

```text
Title
 ↓
Biological Background
 ↓
Knowledge Gap
 ↓
Hypothesis / Question
 ↓
Experimental Strategy
 ↓
Phenotype / Observation
 ↓
Key Molecular Change
 ↓
Mechanistic Evidence
 ↓
Perturbation / Rescue
 ↓
In vivo / Independent Validation
 ↓
Working Model
 ↓
Novelty / Limitations
 ↓
Conclusion
```

---

# 102. 机制型论文的结果排序

如果论文结果本身形成：

```text
现象
→ 关联
→ 机制
→ 因果验证
```

PPT 应尽量保留这个证据升级过程。

例如：

```text
Slide 1
Disease model shows phenotype X

Slide 2
Gene Y is associated with phenotype X

Slide 3
Gene Y regulates pathway Z

Slide 4
Perturbing Y changes phenotype X

Slide 5
Rescue experiment supports causality
```

不应只按照 Figure 1、Figure 2、Figure 3 的编号机械排序。

---

# 103. 机制型论文的 Figure 优先级

优先：

1. 核心 phenotype；
2. 关键 perturbation；
3. rescue / reversal；
4. mechanism；
5. in vivo validation；
6. 最终 working model。

默认弱化：

- 重复性的 expression validation；
- 不改变主要结论的补充 western blot；
- 仅用于说明实验质量的 Panel；
- 与主机制链关系弱的探索性结果。

---

# 104. 常见实验 Figure 的处理

## 104.1 Microscopy / IF / IHC

如果包含：

```text
control vs treatment
```

或多组比较，应尽量：

- 保留组名；
- 保留 scale bar；
- 保留必要染色通道；
- 同页放相关定量图。

推荐：

```text
代表图
+
quantification
```

而不是只放漂亮的显微图片。

---

## 104.2 Western Blot

应优先保留：

- 关键 target；
- loading control；
- 必要组别；
- 对应定量结果。

不能为了节省空间裁掉导致实验无法判断的 loading control。

---

## 104.3 Flow Cytometry

若结果依赖 gating：

- 需要保留理解结论必要的 gate / axis；
- 不应该只截百分比数字。

复杂 gating strategy 可以放方法页或 Source Preview，不一定全部放结果页。

---

## 104.4 动物实验

应优先交代：

```text
Model
Intervention
Group
Time
Endpoint
```

结果页再展示：

- phenotype；
- survival；
- pathology；
- molecular validation。

---

# 105. 机制工作模型

如果论文最后提供机制示意图：

- 优先使用作者原始模型图；
- 可以作为 Summary / Working Model 页核心视觉。

如果论文没有模型图：

MVP 可以用简单 Shape / Arrow 生成**文字型关系图**，但必须基于论文已支持的关系。

例如：

```text
Factor A
→ Pathway B
→ Phenotype C
```

不能擅自补充未验证中间机制。

---

# 106. B 类：组学 / 生物信息型论文

典型包括：

- scRNA-seq；
- snRNA-seq；
- scATAC-seq；
- spatial transcriptomics；
- spatial omics；
- bulk RNA-seq；
- proteomics；
- metabolomics；
- multi-omics；
- large-scale atlas；
- computational biology。

默认故事线：

```text
Title
 ↓
Biological Question
 ↓
Cohort / Samples / Data Modality
 ↓
Analysis Overview
 ↓
Global Landscape
 ↓
Key Cell Type / State / Feature
 ↓
Differential Change
 ↓
Pathway / Regulatory Program
 ↓
Cell–Cell / Spatial / Multi-omics Relationship
 ↓
Validation / External Evidence
 ↓
Biological Interpretation
 ↓
Novelty / Limitations
 ↓

```

# 107. 组学论文不应变成“分析流程汇报”

系统必须避免：

```text
QC
→ PCA
→ UMAP
→ DEG
→ Enrichment
→ CellChat
→ Trajectory
```

这种按工具顺序做 PPT。

正确逻辑应该是：

```text
科学问题
→ 数据如何回答
→ 主要生物学发现
→ 每个分析只作为证据
```

工具不是故事主角。

---

# 108. 组学论文的方法页

方法页重点说明：

```text
样本
组别
模态
核心流程
关键整合 / 分析策略
验证方式
```

例如单细胞研究：

```text
Samples
→ single-cell profiling
→ cell annotation
→ differential state analysis
→ pathway / interaction analysis
→ validation
```

不默认展示：

- 每个软件版本；
- 每个参数；
- 每个 QC threshold；
- 每个 R 包。

除非用户明确要求“方法讲详细一点”。

---

# 109. 组学论文的结果优先级

优先级通常为：

1. 全局变化是什么；
2. 哪个 cell type / state 最关键；
3. 发生了什么 biological program；
4. 与 disease / aging / treatment 的关系；
5. 是否存在 spatial / regulatory / interaction evidence；
6. 是否有独立实验或队列验证。

---

# 110. UMAP / t-SNE / Embedding Figure

Embedding 图不能单独作为结论。

如果 Slide 使用 UMAP，应明确它支持什么：

```text
cell identity
cell-state shift
group-specific distribution
trajectory
spatial mapping
```

优先与以下一种信息搭配：

- annotation；
- proportion；
- marker；
- differential score；
- condition comparison。

不建议只放一张 UMAP 并写：

```text
Single-cell landscape
```

而没有具体 message。

---

# 111. Volcano / Heatmap / DEG

不应把大量基因名塞进 Slide。

优先：

```text
关键趋势
+
少量代表基因
+
与生物学问题相关的 pathway
```

Heatmap 如果字太小：

- 可以裁取关键区域；
- 或选择作者已经突出显示的 cluster；
- 或只用于 Source Preview。

---

# 112. Pathway / Enrichment

不应该把 30 个 pathway 条目直接搬到 PPT。

应优先选择：

- 与主要 claim 直接相关；
- 多个分析共同支持；
- 作者重点讨论；
- 后续有实验验证；

的 pathway。

Slide 中通常保留：

```text
3–6 个关键 pathway
```

即可。

---

# 113. Cell–Cell Communication

CellChat / CellPhoneDB / NicheNet 等结果应围绕：

```text
Which cells?
Which signal?
What biological implication?
```

来讲。

避免展示过于复杂、无法阅读的全局网络图。

优先：

- 关键 sender；
- 关键 receiver；
- 关键 ligand–receptor；
- 与 phenotype 的关系。

---

# 114. Trajectory / Pseudotime

如果轨迹是关键结果，应明确：

```text
起点
→ 变化方向
→ 状态转换
→ 关键基因 / pathway
```

不能把 pseudotime 直接描述为真实时间或因果关系，除非论文有相应证据。

---

# 115. Spatial Omics

空间组学结果优先保持：

```text
组织空间上下文
+
分子 / 细胞信号
```

避免只展示脱离组织位置的统计图。

优先考虑同页组合：

```text
Tissue image / spatial map
+
quantification / feature plot
```

---

# 116. Multi-omics

多组学论文的核心不是“模态越多越好”，而是：

> 不同模态共同支持什么结论？

PPT 应优先展示跨模态一致性或互补证据，例如：

```text
RNA
+
ATAC
→ regulatory program

Proteomics
+
Metabolomics
→ pathway alteration
```

避免一页介绍一个模态，最后没有整合逻辑。

---

# 117. Atlas 型研究

如果论文主要是 atlas / resource：

重点可以是：

```text
Dataset Scope
→ Global Landscape
→ New Cell / State
→ Spatial / Developmental Pattern
→ Biological Insight
→ Resource Value
```

这类论文不必强行套：

```text
Hypothesis → Causal Mechanism
```

---

# 118. C 类：临床研究型论文

典型包括：

- prospective cohort；
- retrospective cohort；
- clinical trial；
- biomarker study；
- diagnostic study；
- prognostic study；
- treatment outcome study。

默认故事线：

```text
Title
 ↓
Clinical Problem
 ↓
Study Question
 ↓
Population / Cohort
 ↓
Study Design
 ↓
Primary Endpoint / Outcome
 ↓
Main Result
 ↓
Secondary / Subgroup Result
 ↓
Validation / Sensitivity Analysis
 ↓
Clinical Interpretation
 ↓
Limitations
 ↓
Conclusion
```

---

# 119. 临床研究必须优先交代的信息

在结果之前，用户应能理解：

```text
Who?
What intervention / exposure?
Compared with what?
What endpoint?
How long?
```

因此方法页不能只写“Methods”。

应尽量结构化呈现：

```text
Population
Groups
Exposure / Intervention
Endpoint
Follow-up
Analysis
```

---

# 120. 临床 Figure 的优先级

优先：

- Study flow；
- primary endpoint；
- Kaplan–Meier；
- Forest plot；
- ROC / diagnostic performance；
- clinically meaningful subgroup；
- adverse events（如果是干预研究且重要）。

默认弱化：

- 大量次要 subgroup；
- 无临床解释的 exploratory analysis；
- 与主 endpoint 无关的复杂统计图。

---

# 121. Kaplan–Meier / Survival

Slide 应明确：

```text
比较对象
Endpoint
方向
效应大小 / 显著性（如果论文提供）
```

不能只写：

```text
Survival analysis
```

---

# 122. Forest Plot

如果 Forest plot 非常复杂：

- 可保留整体图；
- 对关键 subgroup 使用高亮框；
- 或裁取最重要部分。

不得通过裁剪隐藏明显不一致的关键 subgroup，而造成选择性呈现。

---

# 123. Biomarker / Diagnostic Study

默认故事线可调整为：

```text
Clinical Need
→ Biomarker Discovery
→ Association
→ Diagnostic / Prognostic Performance
→ Independent Validation
→ Added Clinical Value
→ Limitations
→ Conclusion
```

重点不只是 AUC 数字，而是：

```text
是否在独立队列验证？
是否优于现有方法？
是否增加临床价值？
```

---

# 124. Clinical Trial

如果检测到随机或干预试验，应重点展示：

```text
Trial Design
Population
Randomization / Groups
Primary Endpoint
Main Efficacy Result
Safety
Secondary Result
Limitations
Conclusion
```

不允许 Agent 因为“机制故事更好讲”而弱化主要临床 endpoint。

---

# 125. D 类：转化 / 混合型论文

这是生物医学论文中非常常见的结构：

```text
患者 / 人体观察
→ 组学发现
→ 实验机制
→ 动物 / 细胞验证
→ 临床意义
```

或：

```text
Computational Discovery
→ Experimental Validation
→ Mechanism
→ Clinical Cohort Validation
```

这类论文不应强制分成“临床部分”“生信部分”“实验部分”三个孤立章节。

应围绕同一个 scientific claim 建立证据链。

---

# 126. 混合型论文的核心原则

优先按：

```text
Claim
→ Human Evidence
→ Omics Evidence
→ Experimental Evidence
→ Validation
```

组织。

而不是：

```text
Clinical Results
→ Omics Results
→ Wet-lab Results
```

如果后者破坏故事连续性。

---

# 127. 证据层级

对于一个关键 Claim，可以内部记录不同证据类型：

```text
observational
association
omics
spatial
perturbation
rescue
animal
clinical
external-validation
```

Deck Planning 可以优先选择具有互补性的证据。

例如：

```text
Observation
+
Perturbation
+
Rescue
```

通常比三个重复 expression Panel 更有说服力。

---

# 128. 因果措辞约束

生物医学 PPT 尤其需要控制因果语言。

如果论文只有：

```text
association / correlation
```

Slide 不应自动写成：

```text
X drives Y
X causes Y
```

优先使用：

```text
X is associated with Y
X correlates with Y
X is linked to Y
```

只有存在：

- perturbation；
- genetic manipulation；
- intervention；
- rescue；
- 其他充分因果证据；

时才提高因果措辞强度。

---

# 129. 生物医学实体一致性

Agent 应特别注意以下实体在 Deck 中保持一致：

```text
Species
Tissue
Cell type
Disease
Treatment
Gene
Protein
Pathway
Cohort
Group
Time point
Endpoint
```

例如：

- 人 / mouse 结果不能混写；
- gene expression 与 protein level 不应混为同一证据；
- cell proportion 与 gene expression 不应混为同一结论。

---

# 130. 实验组与对照组

系统应尽量识别并保持组别语义。

例如：

```text
WT vs KO
Vehicle vs Drug
Healthy vs Disease
Young vs Old
Responder vs Non-responder
```

Slide 不应为了简化而把这些组别重命名到失去原始含义。

---

# 131. 时间关系

涉及：

- time course；
- disease progression；
- treatment response；
- developmental trajectory；

时，应明确区分：

```text
真实实验时间
```

与：

```text
计算推断顺序
```

例如 pseudotime 不能默认当成真实 chronological time。

---

# 132. 多层证据合并

当一个 Slide 组合：

```text
microscopy
+
quantification
+
western blot
```

时，必须确保三者支持的是同一个 message。

否则拆页。

同页多证据的目标是：

> **增强一个结论，而不是增加信息密度。**

---

# 133. 统计信息

MVP 不需要重新计算统计结果。

对于 Figure 已经展示的：

- p-value；
- confidence interval；
- hazard ratio；
- fold change；
- error bar；

优先保留原图。

如果正文中提取关键数值写入 Slide：

必须来自明确 source。

不能让模型估算 Figure 中的精确数值。

---

# 134. 生物医学缩写

如果缩写不是领域极常见词，首次出现建议：

```text
full term (ABBR)
```

后续使用：

```text
ABBR
```

不需要在每页重复展开。

Figure 中已有缩写时，必要解释可以放：

- 简短 annotation；
- Speaker Notes（未来）；
- Agent Chat。

---

# 135. 基因 / 蛋白命名

尽量保持论文原始命名规范。

不要为了语言统一而翻译：

```text
TP53
NF-κB
IL-6
CD8+ T cells
```

等专业实体。

若 gene / protein 符号有大小写物种差异，不应由 Agent 随意规范化。

---

# 136. Figure 视觉优先级

生物医学论文 Figure 常常极其密集。

系统应优先保证：

```text
实验组别可见
轴标签可见
图例可理解
关键 Panel 足够大
```

如果无法做到：

> **宁可拆页，也不要把整张 Figure 缩得不可读。**

---

# 137. 生物医学 Slide 的默认信息层级

一个典型结果页推荐：

```text
结论句标题
↓
主要 Figure / Panel
↓
1–3 个解释性短点
↓
Source
```

而不是：

```text
长标题
+
大段论文原文
+
整张 Figure
+
完整 Caption
```

---

# 138. 生物医学论文自动分类的容错

如果系统对论文类型判断不确定：

不需要阻塞生成询问用户。

可以：

1. 选择最接近的混合策略；
2. 正常生成；
3. 在 Agent 中允许用户纠正。

例如：

```text
“这篇更像机制研究，不要按临床研究讲。”
```

Agent 重新调整 Story Plan。

---

# 139. 自动分类不影响底层 Paper AST

论文类型只是：

```text
Deck Planning Strategy
```

不是新的文件格式。

无论：

- mechanistic；
- omics；
- clinical；
- translational；

都使用同一套 Paper AST / Deck AST。

这能避免产品随着论文类型增加而分裂成多套系统。

---

# 140. 生物医学生成策略验收

首版应至少用三类真实论文测试：

```text
机制实验型
组学 / 生信型
临床 / 转化型
```

每类至少验证：

1. 是否识别正确主要研究问题；
2. 是否选择合理 Story Template；
3. 是否把 Results 放在核心位置；
4. 是否选择正确关键 Figure；
5. 是否正确拆分复杂 Panel；
6. 是否保持实验组 / 对照组；
7. 是否正确区分 observation 与 causality；
8. 是否保留重要统计 / 图例；
9. 是否避免把分析工具当作故事主线；
10. 是否可以通过 Agent 自然语言改变汇报重点。

---

# 141. 生物医学首版产品边界总结

Paper2PPT 首版不追求：

> “什么 PDF 都能做 PPT。”

而追求：

> **把生物医学原创研究论文，尤其是 Figure 驱动、证据链明确的研究文章，稳定转换成适合科研汇报的 PPT。**

因此首版允许在论文类型覆盖面上更窄，但必须在以下方面更深：

```text
Study Design
Claim–Evidence
Figure / Panel
Experimental Logic
Omics Interpretation
Clinical Endpoint
Mechanistic Evidence
Source Traceability
```

这也是 Paper2PPT 相比通用 AI PPT 工具最重要的领域差异。

---

# 142. Agent 修改交互原则

Paper2PPT 的 Agent 不是通用聊天机器人，而是：

> **围绕当前 Paper 和 Deck 工作的结构化编辑助手。**

用户输入自然语言后，Agent 首先判断：

1. 用户是在提问，还是要求修改；
2. 修改对象是什么；
3. 修改范围有多大；
4. 是内容修改、结构修改、Figure 修改，还是视觉修改；
5. 是否涉及科学含义变化；
6. 应调用哪些 Deck / Paper Tool；
7. 修改后需要检查哪些受影响部分。

---

# 143. “回答”与“修改”必须区分

不是所有用户消息都应直接改 Deck。

例如：

```text
“这篇文章最大的创新点是什么？”
```

默认行为：

```text
回答问题
```

不修改 Deck。

例如：

```text
“把这篇文章最大的创新点加到最后一页。”
```

默认行为：

```text
回答隐含在修改中
+
修改 Deck
```

---

## 143.1 修改意图的典型信号

例如：

```text
改
删
加
换
合并
拆开
缩短
放大
移动
重写
调整
重新组织
改成
做成
```

通常代表编辑请求。

---

## 143.2 纯讨论的典型信号

例如：

```text
为什么
解释一下
这是什么意思
你觉得
作者为什么
这个结果说明什么
```

通常优先回答，而不是修改。

---

# 144. 当前上下文优先

Agent 解析模糊指令时，应优先利用 UI 当前状态。

上下文优先级建议：

```text
当前选中的 Element
>
当前选中的 Slide
>
最近一次 Agent 修改对象
>
用户明确提及的 Slide / Figure
>
整个 Deck
```

例如用户选中了 Figure 3B 后说：

```text
“放大一点”
```

默认解释为：

```text
放大当前选中的 Figure
```

而不是重新询问“你指什么？”

---

# 145. “这页 / 当前页”

当用户说：

```text
“这页太挤了”
“当前页文字少一点”
“这一页换个布局”
```

默认目标：

```text
当前选中的 Slide
```

如果当前没有选中 Slide，则使用编辑器当前正在展示的 Slide。

---

# 146. “这张图 / 这个 Figure”

当用户说：

```text
“这张图裁得不对”
“这张图只留右半边”
“把这个 Figure 放大”
```

默认目标优先为：

1. 当前选中的 Figure Element；
2. 如果当前 Slide 只有一张 Figure，则使用该 Figure；
3. 如果当前 Slide 有多张 Figure 且没有选中对象，则 Agent 根据最近操作判断；
4. 仍然不明确时，再向用户询问。

目标不是“永远不问”，而是：

> **能通过当前 UI 状态合理解决的歧义，不额外打断用户。**

---

# 147. Slide 编号引用

用户可能说：

```text
“第7页”
“第七页”
“slide 7”
“第7张”
```

统一解释为当前 Deck 显示顺序中的第 7 个 Slide。

内部仍通过稳定：

```text
slideId
```

操作，避免 reorder 后对象错位。

---

# 148. Figure 编号引用

例如：

```text
“Fig. 3”
“Figure 3B”
“图3B”
```

优先映射到：

```text
Paper FigureRef / FigurePanel
```

而不是根据 Slide 中第几张图片猜测。

如果论文中 Figure label 无法可靠解析，可以结合：

- Caption；
- Page；
- 当前 Slide；
- FigureRef；

进行匹配。

---

# 149. 默认最小修改原则

这是 Revision Agent 最重要的产品规则之一。

> **用户要求局部修改时，只修改完成目标所必要的最小范围。**

例如：

```text
“第7页标题短一点。”
```

默认只修改：

```text
slide-07.title
```

不应该同时：

- 改正文；
- 换 Figure；
- 换 Layout；
- 改其他 Slide。

---

# 150. 允许联动修改的情况

如果局部修改会明显破坏页面完整性，可以做最小必要联动。

例如用户：

```text
“把第7页的 Figure 3B 删掉。”
```

删除后页面严重空洞，可以：

- 重新选择该页 Layout；
- 调整剩余 Figure 大小。

但不应该：

- 改变这一页的科学结论；
- 自动加入新的 Figure；
- 重写整个 Section；

除非确有必要。

---

# 151. 修改范围分级

Revision 请求可以内部划分为：

```text
Element
Slide
Section
Deck
```

---

## 151.1 Element-level

例如：

```text
“这张图放大”
“把这句话删掉”
```

只改一个元素。

---

## 151.2 Slide-level

例如：

```text
“这一页太挤了”
“第5页简洁一点”
```

允许调整当前 Slide：

- 内容；
- Layout；
- Figure 排列。

---

## 151.3 Section-level

例如：

```text
“背景部分压缩一下”
“方法部分再详细一些”
```

修改对应 Section 的多个 Slide。

---

## 151.4 Deck-level

例如：

```text
“整体压到12页”
“全部改成中文”
“所有结果页标题改成结论句”
```

允许修改整个 Deck。

---

# 152. 修改范围推断

如果用户没有明确范围：

优先选择**最小合理范围**。

例如：

```text
“标题都太长了”
```

“都”意味着全局或当前 Section 范围。

例如：

```text
“标题太长了”
```

如果正在看第 6 页，则默认当前页。

---

# 153. 当前 Selection 是 Agent Context 的一部分

Agent 请求上下文应包含：

```text
currentSlideId
selectedElementId
selectedFigureId
visibleSlideRange
lastMutation
```

这样自然语言可以利用 UI 状态。

例如：

```text
用户点击 Fig.4C
→ 说“换成A和C并排”
```

Agent 不需要用户重新描述“第几页哪个 Figure”。

---

# 154. 内容修改与视觉修改分离

Agent 应区分：

```text
Content Revision
```

和：

```text
Visual Revision
```

---

## 154.1 Content Revision

包括：

- 改标题；
- 精简文字；
- 添加结论；
- 删除某个信息；
- 改故事顺序；
- 调整 Figure 选择。

可能影响科学内容。

---

## 154.2 Visual Revision

包括：

- 换 Layout；
- Figure 放大；
- 调整占比；
- Theme；
- 间距；
- 对齐。

原则上不改变科学含义。

---

# 155. 模糊视觉指令

用户可能说：

```text
“这页好看一点”
“更简洁一点”
“学术一点”
“别这么挤”
```

Agent 不应该任意发挥成完全新的设计。

优先映射为可控操作。

---

## 155.1 “简洁一点”

默认优先：

```text
减少非核心文字
→ 减少 bullet
→ 增加留白
→ 保留核心 Figure
```

不默认删除关键证据。

---

## 155.2 “这页太挤”

默认优先：

```text
检查文本长度
→ 检查 Figure 数量
→ 尝试更合适 Layout
→ 必要时拆页
```

不通过无限缩小字体解决。

---

## 155.3 “图大一点”

优先：

```text
调整 Layout / Figure 占比
```

如果空间不足：

```text
减少辅助文字
```

仍然不足时：

```text
拆页
```

---

## 155.4 “学术一点”

默认理解为：

- 更少装饰；
- 更清晰信息层级；
- 更克制排版；
- 减少营销式措辞；
- 保留来源；
- 不增加没有科学价值的视觉元素。

不应该自动理解成某个具体期刊版权风格。

---

# 156. 科学内容修改应更保守

涉及科学含义时，Agent 的自由度应低于视觉调整。

例如：

```text
“把这一页的结论写得更强一点。”
```

Agent 不能为了“更强”而：

```text
association → causation
```

正确行为是：

- 在论文证据允许范围内优化表达；
- 如果用户要求超出证据，应保持原科学强度。

---

# 157. 用户要求与论文证据冲突

例如用户说：

```text
“这里写成 Gene X 导致疾病。”
```

但论文只有 correlation。

Agent 不应直接照做。

可以回复：

```text
论文目前主要支持相关性，直接写成“导致”会超过证据强度。
我可以改成“Gene X 与疾病进展相关”。
```

这种情况属于需要**拒绝不准确修改，但继续提供可接受替代**的场景。

---

# 158. 不允许 Agent 迎合错误事实

用户的编辑要求不能覆盖基本科研真实性规则。

不能：

- 修改样本量为不存在的数字；
- 改变实验组含义；
- 把不显著写成显著；
- 把 mouse 结果写成人体结果；
- 把预测写成实验验证；
- 把相关写成因果；
- 创造论文没有的 Figure。

这是产品可靠性的硬约束。

---

# 159. 删除内容的策略

用户明确说：

```text
“删掉”
```

应执行删除。

但如果删除会使 Slide 的 scientific message 无证据支撑，Agent 可以：

1. 删除指定内容；
2. 同时重新判断 Slide 是否仍成立；
3. 必要时提示用户：

```text
删除该 Panel 后，这一页的结论缺少直接证据。
```

不应悄悄换成另一条结论。

---

# 160. 添加内容的策略

用户说：

```text
“补充一下局限性。”
```

Agent 应优先从：

- Discussion；
- Limitations；
- Study design；

提取。

如果需要 Agent 自己推断：

必须用谨慎措辞，并区分于作者明确陈述。

---

# 161. “再详细一点”

这类指令必须结合当前对象。

如果当前是：

### Method Slide

可以增加：

- sample；
- group；
- workflow；
-关键步骤。

### Result Slide

可以增加：

- 1–2 个关键数值；
- Figure 解释；
- Evidence。

### Conclusion Slide

可以增加：

- novelty；
- implication；
- limitation。

不能统一处理成“加更多文字”。

---

# 162. “再短一点”

默认压缩顺序：

```text
重复信息
→ 修饰语
→ 次要解释
→ 次要 bullet
```

尽量保留：

```text
核心结论
+
关键证据
+
必要 group / entity
```

---

# 163. “重新做这一页”

解释为：

```text
Regenerate Slide
```

允许重新：

- 选择 Layout；
- 重写标题；
- 重组内容；
- 重新选择当前 message 对应 Figure。

但默认保持：

```text
Slide scientific purpose / message
```

如果用户想改变这一页讲什么，应明确通过修改内容或结构实现。

---

# 164. “重新生成”

如果用户没有指定对象：

- 在当前 Slide 明确处于焦点时，优先解释为 Regenerate Slide；
- 在项目级入口点击 Regenerate，则解释为 Regenerate Deck；
- 在 Agent Chat 中仍不明确时，应根据上下文谨慎判断。

整套 Deck 重建属于影响较大的操作，UI 中应与普通修改有明显区别。

---

# 165. “换一张图”

默认含义：

> 在不改变当前科学 message 的情况下，寻找更合适的论文原 Figure / Panel。

候选来源优先：

1. 同一 Claim 的其他 Panel；
2. 同一 Figure；
3. 论文中支持同一 Claim 的其他 Figure；
4. Supplementary（如果当前 PDF 中存在且必要）。

Agent 不应为了视觉变化换成科学含义不同的图片。

---

# 166. “加一张图”

Agent 应先问自己：

```text
当前 Slide 的 message 是否需要更多证据？
```

如果有合适 Figure，则添加。

如果没有：

> 不应为了版面丰满而随便加入无关 Figure。

---

# 167. “拆成两页”

拆页时应重新形成两个明确 message。

不应该只是：

```text
上半页 → Slide A
下半页 → Slide B
```

而应该：

```text
Evidence Group A
→ Message A

Evidence Group B
→ Message B
```

必要时重写两个标题。

---

# 168. “合并两页”

只有以下情况适合合并：

- 两页讲的是同一 scientific message；
- Figure 可以保持可读；
- 合并后没有明显信息过载。

如果两页实际上是：

```text
Observation
```

和：

```text
Mechanism
```

且都很重要，Agent 不应仅为了减少页数强行塞到一页。

可选择：

- 精简后合并；
- 或告诉用户合并会影响可读性，并采用最佳压缩方案。

---

# 169. “整体压到 N 页”

这是 Deck-level 结构任务。

建议内部步骤：

```text
计算当前页数
→ 给各 Section 分配新预算
→ 优先合并 / 删除低优先级内容
→ 保留核心 Claim
→ 重新检查故事连续性
→ 重新编号 / 渲染
```

压缩优先级继续遵循：

```text
次要背景
→ 非关键方法
→ 重复证据
→ 次要结果
```

---

# 170. “扩展到 N 页”

增加页数时不应该简单重复内容。

优先展开：

- 复杂 Figure；
- Study Design；
- 关键机制；
- Evidence；
- Validation；
- Limitations；
- Clinical / Biological interpretation。

---

# 171. 修改主题与内容要解耦

例如：

```text
“改成深色主题。”
```

只修改 Theme。

不应该顺便：

- 改标题；
- 改 Figure；
- 改页数；
- 改故事结构。

---

# 172. “像 Nature / Cell 风格”

用户可能用期刊名表达视觉偏好。

产品应把它理解为**抽象视觉特征**，例如：

- 简洁；
- 白底；
- 信息密度适中；
- Figure 优先；
- 克制配色；
- 学术排版。

不应声称复制某期刊的官方模板，也不需要追求一比一复刻。

---

# 173. Agent 的修改事务

一次用户请求可能触发多个底层 Tool Call。

例如：

```text
“把第5页拆成两页。”
```

可能包括：

```text
patch slide
add slide
move element
rewrite titles
```

这些应作为一个：

```text
Revision Transaction
```

提交。

---

# 174. Undo 的事务语义

用户点击一次 Undo：

> 应回退整个用户请求对应的修改。

而不是要求用户连续 Undo 四次底层 Tool Call。

例如：

```text
Request #24
“把 Figure 4 拆成两页”
```

对应一个 Undo Unit。

---

# 175. 修改前快照

执行 Revision 前至少记录：

```text
target scope
affected slideIds
deck revision id
```

必要时保存局部或完整 Deck snapshot。

确保 Agent 批量修改失败时能够：

```text
rollback
```

---

# 176. Revision 失败

如果 Agent 计划了多个修改，其中一步失败：

默认不应把 Deck 留在半完成状态。

优先：

```text
全部成功 → commit
任一步失败 → rollback
```

对于耗时较长、允许部分结果的操作可以例外，但 MVP 尽量保持事务性。

---

# 177. 修改摘要

每次实际修改 Deck 后，Agent 应返回简洁摘要。

例如：

```text
已调整第 6 页：

- 标题缩短为结论句
- 删除 2 条重复说明
- 放大 Figure 3B
```

---

## 177.1 全局修改摘要

例如：

```text
已将整套 PPT 压缩到 12 页：

- 背景从 3 页压缩为 1 页
- 方法从 2 页合并为 1 页
- 合并 2 组重复结果
- 保留全部 6 个核心结果
```

---

# 178. 不显示底层 Tool Log

默认用户不需要看到：

```text
deck.patch_slide(...)
deck.move_slide(...)
```

可以保留开发模式 / Debug 模式，但不属于普通产品体验。

---

# 179. Agent 修改后的自动检查

修改后只检查受影响范围及必要的邻接关系。

例如修改第 7 页：

```text
检查 Slide 7
+
必要时检查 Slide 6 / 8 的过渡
```

不每次重新分析整个论文和 Deck。

---

# 180. Section 连续性

当：

- 插入；
- 删除；
- 合并；
- 拆分；

Slide 后，应检查相邻 Slide 是否出现：

- 重复标题；
- 突然跳题；
- “如前页所示”但前页已不存在；
- 无意义 Section 分隔。

---

# 181. 修改后的 Source Integrity

涉及 Figure / Claim 修改后，应重新检查：

```text
Slide Claim
↔
SourceReference
```

避免出现：

> 文字已经改成另一个结论，但 Source 还是旧 Figure。

---

# 182. 修改后的语言一致性

如果用户只修改一句英文到中文，不代表整套 Deck 自动改语言。

但如果用户说：

```text
“全部改成中文”
```

则执行 Deck-level language normalization。

Figure 内原始英文不修改。

---

# 183. 修改后的术语一致性

Deck-level 内容修改后，应尽量保持实体命名一致。

例如用户把：

```text
Endothelial cells
```

改成：

```text
ECs
```

如果明确要求“全文统一”，才批量替换。

局部改写不默认修改其他 Slide。

---

# 184. 用户直接编辑与 Agent 的关系

用户手工修改 Deck 后：

> 手工修改结果就是新的真实状态。

Agent 后续必须以当前 Deck 为准。

不能因为初始生成时曾经是另一段文本，就在后续 Revision 中无意覆盖用户手工修改。

---

# 185. 用户锁定内容（后续可选）

MVP 可以暂不做显式 Lock UI。

但架构上建议预留未来能力：

```text
lockedByUser
```

用于表示：

> 这个元素是用户明确确认过的，Agent 做全局重写时尽量不要改。

首版如果不实现 Lock，则仍应优先保持用户最近的手工修改。

---

# 186. Agent 不应主动改用户没有要求的细节

例如用户说：

```text
“把第8页 Figure 放大。”
```

Agent 不应该觉得标题“不够好”就顺手改标题。

这类“顺手优化”会显著降低用户对 Agent 的控制感。

---

# 187. 允许主动修复的例外

只有当修改直接造成明显结构问题时，可以做必要修复。

例如：

```text
放大 Figure
→ 文字溢出
```

可以自动：

- 压缩非核心文字；
- 调整 Layout。

修改摘要中需要说明。

---

# 188. Agent 建议模式

当用户只是询问：

```text
“你觉得这套PPT哪里有问题？”
```

Agent 应：

```text
分析
→ 给建议
```

默认不修改。

如果用户接着说：

```text
“按你的建议改。”
```

再执行。

---

# 189. Review Deck 与 Edit Deck 是两种意图

内部可以区分：

```text
review
```

和：

```text
edit
```

### review

- 检查逻辑；
- 检查 Figure；
- 检查科学准确性；
- 给出建议。

### edit

- 直接修改 Deck。

这样可以避免“帮我看看”被误判成“帮我改”。

---

# 190. “检查一下”默认不改

例如：

```text
“检查一下有没有逻辑问题。”
“看看有没有哪页太挤。”
“帮我审核一下。”
```

默认：

```text
Review only
```

输出问题列表。

只有明确说：

```text
“顺便改掉”
```

才执行修改。

---

# 191. 审核结果应可以转为操作

例如 Agent 返回：

```text
发现 3 个问题：
1. 第 3 页与第 4 页背景重复
2. 第 8 页 Figure 太小
3. 第 12 页结论缺少来源
```

用户：

```text
“都改掉。”
```

Agent 应能利用上一轮 review context 执行，不要求用户重新描述。

---

# 192. 修改中的澄清策略

虽然产品强调少打断，但以下情况应该澄清：

1. 当前存在多个同样合理的目标；
2. 用户要求会明显改变科学含义；
3. 用户要求删除大量内容但目标页数 / 重点不明确；
4. 用户要求选择论文外部内容；
5. 操作不可合理推断且错误成本较高。

---

# 193. 不需要澄清的情况

以下情况可以直接根据当前上下文执行：

```text
“这页短一点”
“这张图放大”
“标题改成结论句”
“背景压缩成两页”
“删掉这一页”
```

前提是 UI 当前对象明确。

---

# 194. Agent 请求的输入上下文

Revision 时不要把整篇论文和全部 Deck 无脑塞给模型。

默认上下文：

```text
User Request
+
Current Selection
+
Target Slide / Section
+
Neighbor Slides（必要时）
+
Relevant Claim
+
Relevant Figure / Source
+
Deck-level Preferences
```

只有 Deck-level 请求才扩大范围。

---

# 195. Agent Revision 的内部计划

复杂修改可以先在内部形成：

```text
target
scope
intent
operations
validation
```

例如：

```text
User:
“背景压成一页，但不要删掉研究问题。”

Plan:
scope = background section
keep = research question
merge = slides 2–4
targetSlides = 1
```

计划不需要默认展示给用户。

---

# 196. Agent Tool 使用原则

Agent 应优先调用高层工具：

```text
deck.patch_slide
deck.add_slide
deck.delete_slide
deck.move_slide
paper.get_figure
```

不应该通过：

```text
raw JSON edit
```

或任意文件写入绕过领域校验。

---

# 197. 结果必须通过 Schema Validation

任何 Agent Mutation 在写入 Deck 前必须验证：

- Slide 是否合法；
- Layout 是否存在；
- FigureRef 是否存在；
- Element 类型是否允许；
- Source 是否可以解析。

验证失败：

```text
不 commit
```

---

# 198. Revision 的性能体验

局部修改应尽量快速。

产品上应避免：

```text
改一句标题
→ 重新分析整篇 PDF
→ 重新生成整套 Deck
```

Revision Agent 必须利用：

- Paper AST；
- Deck AST；
- 已有 Figure analysis；
- 当前 Context。

---

# 199. Agent 状态提示

修改过程中只需要简洁状态，例如：

```text
正在调整第 7 页…
```

Deck-level：

```text
正在重新整理整套 PPT…
```

不需要展示模型内部推理。

---

# 200. Agent 可取消

执行中的 Revision 可以取消。

如果尚未 commit：

```text
保持原 Deck
```

如果使用事务机制，则取消时 rollback。

---

# 201. 多轮修改上下文

Agent 应理解连续指令。

例如：

```text
用户：
“第8页只留A和C。”

Agent：
已完成。

用户：
“C再大一点。”

```

第二句默认指：

```text
刚刚第8页的 Figure C
```

无需用户再次完整指定。

---

# 202. 多轮上下文不能覆盖当前 UI

如果用户在上一轮修改第8页，但随后点击第12页，再说：

```text
“这页短一点。”
```

优先使用：

```text
当前 UI 第12页
```

而不是上一轮第8页。

即：

```text
Current Selection
>
Conversation Recency
```

---

# 203. Agent 对手工 Crop 的尊重

用户手工修正过 Figure bbox 后：

- 默认视为更可信；
- 全局 Regenerate / Theme 修改不应重新覆盖 bbox；
- 只有用户明确要求“重新裁图”才重新计算。

---

# 204. Agent 对用户文字修改的尊重

如果用户手工改了标题：

```text
“Age-associated EC dysfunction”
```

后续只是换 Theme 时，不应该重新生成标题。

只有内容级操作才允许修改。

---

# 205. 大范围 Regenerate 的保护

Regenerate Deck 可能覆盖大量用户修改。

因此虽然一般 Agent 修改不需要确认，但：

> **整套 Deck Regenerate 属于少数应该提供明确确认或版本保留的操作。**

推荐：

```text
重新生成整套 PPT？
当前版本会保留，可随时恢复。
```

这样不需要阻止用户，但避免误触造成大量工作丢失。

---

# 206. 版本保留

MVP 不需要复杂 Git-like Version System。

但对于：

```text
Regenerate Deck
```

建议至少保存：

```text
previousDeckSnapshot
```

允许：

```text
恢复上一版本
```

普通局部 Revision 继续使用 Undo / Redo。

---

# 207. Agent 修改安全边界总结

可以浓缩成：

```text
先判断是“问”还是“改”
→ 用当前 Selection 消除歧义
→ 选择最小修改范围
→ 科学内容保守，视觉调整灵活
→ 高层 Tool 修改
→ Schema / Source 校验
→ 一次请求一个 Revision Transaction
→ 自动保存
→ 返回修改摘要
→ 可一次 Undo
```

---

# 208. Agent 修改验收测试

首版至少覆盖以下自然语言测试：

### 当前页

```text
“这页太挤了”
```

预期：

- 只改当前页；
- 不改变科学含义；
- 页面更可读。

### 当前 Figure

```text
“这张图放大一点”
```

预期：

- 修改当前选中 Figure；
- 必要时调整 Layout；
- 不改其他 Slide。

### 局部内容

```text
“第7页标题改成结论句”
```

预期：

- 只改第7页标题；
- 结论强度不超过论文证据。

### Section

```text
“背景压缩成一页”
```

预期：

- 只重构 Background；
- 保留 research question；
- Results 基本不变。

### Deck

```text
“整体压到12页”
```

预期：

- 全局重新分配页数；
- 优先保留核心 Results；
- 修改摘要说明删减 / 合并范围。

### Figure

```text
“Figure 3只留B和D”
```

预期：

- 找到 Paper Figure 3；
- 只保留 B / D；
- 来源仍正确。

### Review

```text
“帮我看看这套PPT有什么问题”
```

预期：

- 只输出建议；
- 不修改 Deck。

### 科研准确性

```text
“把‘相关’改成‘导致’”
```

如果论文没有因果证据：

- 不执行错误强化；
- 给出科学上更准确的替代表达。

### Undo

完成复杂修改后：

```text
Undo
```

预期：

- 一次恢复到本轮用户请求之前。

---

# 209. Agent 交互的最终目标

Agent 的体验应该接近：

> **用户在和一个理解论文、理解当前 PPT、知道当前选中了什么的科研演示文稿助手交流。**

而不是：

> “用户每次都要重新告诉 Chatbot 文件名、页码、Figure 和所有上下文。”

这也是结构化 Deck + UI Selection + Pi Agent 相比普通“上传 PDF 聊天”方案的重要优势。

---

# 210. 项目生命周期

Paper2PPT 的 Project 是一个长期可恢复的本地工作单元，而不是一次性的“上传 → 生成 → 下载”任务。

一个 Project 从创建开始，应持续保存：

```text
Original PDF
Paper AST
Figure Analysis
Deck AST
Theme
Agent History
Revision History
Project Settings
Workflow State
```

用户关闭页面、刷新浏览器或稍后重新打开，都应尽量恢复到最近的稳定状态。

---

# 211. Project 与 Generation Session 分离

必须区分：

```text
Project
```

和：

```text
Generation Session
```

Project 是长期存在的。

Generation Session 只是一次：

- 初始生成；
- 重新分析；
- 重新生成 Deck；
- 大范围 Revision；

过程。

因此：

> **一次生成失败，不等于 Project 失败。**

已经完成的结果应继续保留。

---

# 212. Project 状态模型

产品层建议使用以下高层状态：

```text
New
Preparing
Generating
Ready
Revising
Exporting
Interrupted
Error
```

其中状态只是 UI 表现，不意味着所有内部流程都必须依赖单一状态机。

---

## 212.1 New

Project 已创建，PDF 已选中或正在保存，但尚未开始完整分析。

用户可以：

```text
填写生成要求
→ Generate
```

---

## 212.2 Preparing

包括：

- 读取 PDF；
- 获取页数；
- 提取基础 metadata；
- 建立项目本地文件。

---

## 212.3 Generating

系统正在执行首次生成流程。

UI 显示高层阶段：

```text
解析论文
理解研究内容
分析 Figures
规划汇报结构
制作幻灯片
```

---

## 212.4 Ready

已有可用 Deck。

用户可以：

- 浏览；
- 编辑；
- Agent 修改；
- 查看 Source；
- 导出。

这是 Project 最主要的长期状态。

---

## 212.5 Revising

正在执行一次 Agent Revision。

Deck 的上一个稳定版本仍然存在。

---

## 212.6 Exporting

正在生成 PPTX。

Exporting 不影响 Project 本身是否 Ready。

导出失败后仍然回到：

```text
Ready
```

---

## 212.7 Interrupted

某个生成 / 修改流程被：

- 用户取消；
- 页面关闭；
- 网络中断；
- 浏览器终止；

打断。

Project 本身保留。

重新打开后应提供恢复入口。

---

## 212.8 Error

当前流程遇到无法自动恢复的错误。

Error 必须附带：

```text
发生在哪一步
已经保存了什么
可以从哪里继续
```

而不是把整个 Project 标记为不可用。

---

# 213. Stable Checkpoint

长流程应按阶段保存稳定检查点。

建议至少包括：

```text
Checkpoint 0
Project Created

Checkpoint 1
PDF Parsed

Checkpoint 2
Paper AST Ready

Checkpoint 3
Figure Analysis Ready

Checkpoint 4
Deck Plan Ready

Checkpoint 5
Deck Ready
```

只有阶段成功完成后，才更新稳定 Checkpoint。

---

# 214. 为什么使用检查点

例如生成到：

```text
Figure Analysis
```

时 API Rate Limit。

用户重新打开项目后：

不应该：

```text
重新解析 PDF
→ 重新理解全文
→ 重新分析已经完成的 Figure
```

而应该从：

```text
最近稳定 Checkpoint
```

继续。

这样同时减少：

- 等待时间；
- API 成本；
- 重复模型调用；
- 因重新生成导致的不一致。

---

# 215. 自动保存规则

Paper2PPT 不把“保存”作为主要用户操作。

以下事件完成后自动保存：

```text
PDF 保存完成
Paper AST 更新
Figure Analysis 更新
Deck 创建
Agent Revision commit
文本编辑结束
Figure crop 应用
Slide reorder
Theme 修改
Undo / Redo
```

UI 可以使用轻量状态：

```text
Saving…
Saved
```

不需要永久显示一个大型 Save 按钮。

---

# 216. 保存失败

如果本地保存失败：

不能继续假装修改已经安全保存。

应提示：

```text
无法保存当前修改。
```

并尽量：

- 保留当前内存状态；
- 重试；
- 提醒用户不要关闭页面。

如果浏览器存储空间不足，需要明确指出：

```text
本地存储空间不足
```

而不是显示通用错误。

---

# 217. 重新打开 Project

打开最近项目时，应优先恢复：

```text
当前 Deck
当前 Slide
Theme
Paper / Figure Source
Agent History
最近稳定 Workflow State
```

不需要重新调用模型。

---

# 218. 恢复当前编辑位置

MVP 可以保存：

```text
lastOpenedSlideId
```

重新打开时优先回到用户最后查看的 Slide。

如果该 Slide 已被之后的 Undo / Version Restore 删除，则回到：

```text
第一个有效 Slide
```

---

# 219. 中断后的恢复入口

如果 Project 上一次处于：

```text
Generating
```

但没有正常完成，重新打开时显示：

```text
上次生成在“分析 Figures”阶段中断。

[ 继续生成 ]
[ 查看已完成内容 ]
```

不自动重新开始 API 请求。

---

# 220. 继续生成

点击：

```text
继续生成
```

系统应：

1. 读取最近稳定 Checkpoint；
2. 检查当前模型设置；
3. 检查必要 PDF / Paper 数据；
4. 从未完成阶段开始；
5. 已完成阶段不重复计算。

---

# 221. 重新开始当前阶段

对于可能产生损坏或不完整结果的阶段，可以提供：

```text
[ 重新执行当前步骤 ]
```

例如：

```text
Figure Analysis failed
```

可以重新分析 Figure。

但不需要重新解析整个 PDF。

---

# 222. 初始生成失败后的编辑能力

如果已经存在部分 Deck：

应尽量允许用户打开已有 Slides。

例如：

```text
已生成 8 / 14 页
```

后续生成失败。

用户至少可以：

- 查看这 8 页；
- 查看论文；
- 重新尝试继续生成。

是否允许完整编辑取决于 Deck 是否已经处于结构合法状态。

---

# 223. 部分结果不能破坏最终状态

初始 Deck 生成建议采用：

```text
Working Deck
→ Validation
→ Commit Ready Deck
```

如果生成过程中出现非法结构：

- 不把损坏 Deck 覆盖最近稳定版本；
- 保留前一稳定状态；
- 可以继续重试。

---

# 224. API Key 缺失时重新打开项目

Project 数据和 API Key 是分离的。

如果：

- 用户清除了 API Key；
- 在另一浏览器恢复项目；
- Provider 配置不可用；

已有 Project 仍然可以打开。

可以继续：

```text
查看 Slides
手工编辑已有内容
查看已缓存 Figure
导出（资源完整时）
```

但 Agent 功能提示：

```text
需要配置模型 API Key
```

---

# 225. 切换 Provider / Model

用户可以在项目存在期间从：

```text
DeepSeek
↔
GLM
```

切换。

切换模型后：

> **已有 Paper AST 和 Deck 不自动失效，也不自动重新生成。**

新模型只用于之后的新模型请求。

---

# 226. 为什么切换模型不自动重算

如果用户只是想：

```text
后续修改换一个模型试试
```

不应该触发：

- 全文重新分析；
- Figure 重新识别；
- Deck 重建。

这会：

- 浪费 API；
- 覆盖用户修改；
- 增加不可预测性。

---

# 227. 使用新模型重新生成

如果用户明确希望：

```text
“用 GLM 重新生成整套 PPT”
```

这属于：

```text
Regenerate Deck
```

而不是普通 Provider Switch。

必须保留当前 Deck 版本后再执行。

---

# 228. Paper Analysis 与 Deck Generation 分离

用户可以：

```text
保留当前 Paper AST
→ 用新模型重新生成 Deck
```

默认不重新做 PDF parsing 和 Figure extraction。

只有在用户明确要求：

```text
“重新分析论文”
```

或 Paper Analysis 明显损坏时，才执行更上游流程。

---

# 229. Reanalyze Paper

“重新分析论文”和“重新生成 PPT”必须是两个不同语义。

### Reanalyze Paper

可能重新生成：

```text
Paper Story
Claims
Figure Interpretation
Study Type
```

这可能影响下游 Deck。

### Regenerate Deck

使用当前 Paper AST：

```text
Paper AST
→ New Deck
```

不重新解释原 PDF。

---

# 230. Reanalyze Paper 的影响提示

由于 Paper AST 是 Deck 的证据基础，重新分析可能造成较大变化。

如果用户明确执行：

```text
Reanalyze Paper
```

产品应提示：

> 论文理解结果将更新。当前 Deck 不会立即删除，但之后重新生成时可能得到不同内容。

不需要自动覆盖现有 Deck。

---

# 231. 原始 PDF 在 Project 中不可静默替换

一个 Project 默认对应一篇固定论文。

MVP 不允许：

```text
在同一 Project 里把 Paper A 的 PDF 直接换成 Paper B
```

否则 Paper AST、FigureRef、Deck Source 都会失效。

如果用户上传另一篇不同论文：

> 应创建新 Project。

---

# 232. PDF 恢复 / Reattach

如果原始 PDF 因浏览器存储被清理或资源损坏而丢失：

Project 可以进入：

```text
Degraded Mode
```

已有 Deck 和可用缓存尽量继续保留。

提供：

```text
[ 重新关联原 PDF ]
```

---

# 233. PDF Reattach 的验证

重新关联 PDF 时，应尽量确认它与原项目是同一篇论文。

可以依据：

- 文件 fingerprint；
- 页数；
- title；
- DOI；
- metadata；
- 内容摘要；

进行验证。

如果明显不是同一文件：

> 不应直接覆盖旧 PDF。

提示用户创建新 Project。

---

# 234. PDF 缺失时的能力降级

如果原 PDF 丢失，但 Deck 仍在：

可以继续：

- 查看文本；
- 修改已有 Deck；
- Agent 基于已有 Paper AST 做有限修改；
- 导出已有完整资源。

可能不可用：

- Source Preview；
- 重新裁 Figure；
- 新提取 Figure；
- 重新分析 PDF 页面。

UI 应明确哪些能力因 PDF 缺失受限。

---

# 235. Figure Cache 丢失

如果 Figure cache 丢失但原 PDF 仍存在：

系统应：

```text
通过 FigureRef + bbox
→ 从 PDF 重新渲染 Figure
```

而不是要求重新做 Vision Analysis。

这也是 Figure 保存：

```text
page + bbox
```

而非只保存图片文件的重要原因。

---

# 236. Deck 不依赖临时 Blob URL

产品行为要求：

> 刷新浏览器后，Deck 中的 Figure 仍然可以恢复。

因此任何临时预览 URL 都不能成为唯一资源引用。

这属于实现要求，但直接关系到项目可恢复性。

---

# 237. Regenerate Slide 的版本行为

执行：

```text
Regenerate Slide
```

前保存当前 Slide 状态到 Revision History。

完成后：

- 新 Slide 覆盖当前显示状态；
- 一次 Undo 可恢复旧 Slide。

不创建一个新的 Project。

---

# 238. Regenerate Deck 的版本行为

整套 Regenerate 属于高影响操作。

MVP 推荐行为：

```text
Current Deck
→ 保存为 Previous Deck Snapshot
→ Generate New Deck
→ 用户查看新版本
```

新版本生成失败：

```text
Current Deck 保持不变
```

---

# 239. 不原地破坏当前 Deck

整套重新生成时，不应该：

```text
先清空当前 Slides
→ 再逐页生成
```

正确行为：

```text
Current Deck 保持可用
+
后台构建 Working Deck
→ Validation
→ 成功后切换
```

用户不会因为一次失败的重新生成失去已有成果。

---

# 240. Deck 版本策略

MVP 不需要复杂 Git-like Version History。

首版至少保留：

```text
Current Deck
Previous Major Deck Snapshot
Undo / Redo Revision History
```

其中：

- 普通编辑走 Undo / Redo；
- 整套 Regenerate 保留 Previous Snapshot。

---

# 241. Restore Previous Deck

如果存在整套重新生成前的版本，可以提供：

```text
[ 恢复上一版本 ]
```

恢复行为本身也应可撤销或至少有明确提示。

不需要第一版提供：

```text
Version 1
Version 2
Version 3
...
```

完整版本浏览器。

---

# 242. Project Rename

用户可以修改 Project 名称。

Project 名称与：

```text
论文标题
```

不是同一字段。

例如用户可以把：

```text
Cell 2026 - aging paper
```

作为项目名，而论文原始 title 保持不变。

---

# 243. Project Delete

删除 Project 属于不可轻易恢复的本地操作。

删除前确认：

```text
确认删除这个项目？

将删除本地保存的：
- PDF
- Paper Analysis
- Deck
- Figure Cache
- Agent History
```

如果未来支持 Trash，可以取消强确认，但 MVP 不需要增加回收站。

---

# 244. Project 删除不影响 API Key

删除 Project：

不删除：

```text
全局 Provider Settings / API Key
```

因为 API Key 属于应用设置，不属于项目数据。

---

# 245. 清除 API Key 不影响 Project

反过来：

```text
删除 / 更换 API Key
```

也不删除项目内容。

这是两个独立生命周期。

---

# 246. 浏览器数据清理风险

由于 MVP 是纯前端 Local-first：

如果用户主动：

- 清除站点数据；
- 卸载并清除 PWA 数据；
- 浏览器清理本地存储；

本地 Project 可能被删除。

首次使用或设置页应明确说明：

> 项目默认保存在当前浏览器中。清除网站数据可能删除本地项目。

---

# 247. 尽量请求持久化存储

如果浏览器支持持久化存储能力，应用应尽量请求：

```text
Persistent Storage
```

降低自动存储回收风险。

如果未获得持久化能力：

不阻塞使用，但可以在设置中提示：

```text
本地存储可能被浏览器自动清理
```

---

# 248. Project Backup

为了控制 MVP 范围：

```text
Project Backup / Import
```

不作为最早版本 P0。

但建议列为 P1。

未来可以导出一个本地 Project Bundle，例如包含：

```text
project metadata
paper.json
deck.json
theme
figure refs
必要 assets
```

用于：

- 手工备份；
- 浏览器迁移；
- 设备迁移。

---

# 249. Project Backup 不等于 PPTX Export

必须区分：

### PPTX Export

给 PowerPoint 使用。

### Project Backup

用于以后重新打开 Paper2PPT Project。

PPTX 不是完整 Project 数据备份。

---

# 250. Agent History 生命周期

Agent History 随 Project 保存。

重新打开项目后：

用户可以看到之前的重要对话。

但不要求把：

- 所有底层 prompt；
- 大量模型 token；
- 隐藏推理；
- 中间 Tool JSON；

全部长期保存。

---

# 251. Agent History 的最小保存内容

建议保存：

```text
User Message
Assistant Visible Message
Revision Summary
Revision Transaction ID
Timestamp
```

这样用户以后看到：

```text
“我上次为什么把 Figure 4 拆开了？”
```

至少能理解修改历史。

---

# 252. Undo / Redo 与重新打开

普通内存级 Undo Stack 是否跨浏览器重启完整恢复，不作为最早 MVP 强制要求。

但：

- 已 commit 的 Deck 必须恢复；
- 最近 Major Snapshot 必须恢复；
- Revision History 数据结构应允许未来扩展。

如果实现成本可接受，优先持久化最近若干次 Revision Transaction。

---

# 253. 导出不产生新的 Project 状态

导出 PPTX：

```text
Ready
→ Exporting
→ Ready
```

不会改变：

- Deck 内容；
- Paper AST；
- Revision History。

导出文件可以记录：

```text
lastExportedAt
```

但不需要创建“已导出版本”。

---

# 254. 导出时资源缺失

如果当前 Deck 使用的某个 Figure 无法恢复：

不能静默导出一个空白占位而不提示。

应：

1. 尝试从 PDF 重新生成；
2. 仍失败则指出具体 Slide；
3. 让用户决定修复后再次导出。

首版可以直接阻止存在关键资源缺失的完整导出。

---

# 255. 模型调用失败不污染状态

任何需要模型的阶段都应遵守：

```text
request
→ validate result
→ commit
```

而不是：

```text
request 开始
→ 先修改正式 Project
```

这样：

- timeout；
- malformed output；
- API 失败；

都不会污染稳定 Project。

---

# 256. 网络恢复

如果模型请求因网络中断失败：

重新联网后：

```text
[ 重试当前步骤 ]
```

即可。

不要求整个 App reload。

---

# 257. 模型 Rate Limit / Quota

如果 Provider 返回：

- rate limit；
- quota exceeded；
- account balance；

Project 应保持现状。

提示用户：

```text
当前模型暂时无法继续。
```

允许：

- 稍后重试；
- 更换 Provider；
- 修改 API Key。

切换 Provider 后可以从当前 Checkpoint 继续。

---

# 258. 跨 Provider 继续生成

如果：

```text
DeepSeek
```

在 Figure Analysis 后失败，用户切换：

```text
GLM
```

系统可以从最近稳定 Checkpoint 继续。

不要求前面的 Paper AST 由同一模型生成。

但应记录：

```text
artifact provenance / provider
```

供未来 Debug 使用。

普通用户无需看到这些内部信息。

---

# 259. Provider 变化不影响科学 Source

无论哪个模型生成：

最终科学来源仍然应指向：

```text
Paper
Figure
Panel
Page
Source Text
```

而不是“模型 A 说过什么”。

模型只是解释和编辑引擎，不是科学证据来源。

---

# 260. Project 的最终真值

Project 中不同数据的重要性层级：

```text
Original Paper
      ↓
Paper / Figure Source
      ↓
Current Deck
      ↓
Agent Conversation
```

科学事实以论文来源为基础。

用户真正编辑的产品状态以：

```text
Current Deck AST
```

为准。

Agent Conversation 不能覆盖当前 Deck 状态。

---

# 261. 项目恢复的最小验收

首版至少通过以下测试：

### Case 1：刷新页面

生成完成后刷新：

- Project 仍在；
- Deck 仍在；
- Figure 仍可显示；
- 不重新调用模型。

### Case 2：生成中断

Figure 分析完成后中断：

- 重新打开可从后续阶段继续；
- 不重复解析 PDF。

### Case 3：API Key 被删除

- Project 仍可打开；
- Agent 提示配置 Key；
- 已有 Deck 不受影响。

### Case 4：切换模型

DeepSeek → GLM：

- 当前 Deck 不变化；
- 下一次 Revision 使用 GLM。

### Case 5：Regenerate Deck 失败

- 当前 Deck 不丢失；
- 新 Working Deck 不 commit。

### Case 6：Figure Cache 丢失

- 原 PDF 存在时可从 bbox 重建。

### Case 7：PDF 丢失

- Deck 尽量仍可打开；
- Source / Crop 功能标记不可用；
- 可以重新关联原 PDF。

### Case 8：整套重新生成

- 当前版本先保存；
- 新版本成功后再切换；
- 可以恢复上一版本。

---

# 262. 生命周期设计总结

Project 生命周期遵循：

```text
本地 Project 永远优先保留
→ 长任务阶段化
→ 每阶段产生稳定 Checkpoint
→ 出错从最近 Checkpoint 恢复
→ 模型切换不自动破坏已有结果
→ 普通修改使用 Undo / Redo
→ 整套 Regenerate 保存 Major Snapshot
→ PDF / Figure 缺失时优雅降级
```

核心目标是：

> **用户已经完成的工作，不应该因为一次模型失败、刷新页面、切换 Provider 或重新生成而轻易丢失。**

---

# 263. MVP 产品冻结条件

当以下五个产品问题都已经明确后，MVP PRD 可以进入冻结：

```text
1. 输入范围
2. 自动生成策略
3. Figure / Source 规则
4. Agent Revision 规则
5. Project 生命周期
```

当前文档已经覆盖上述五部分。

后续新增功能原则上不再进入 MVP，除非：

- 阻塞核心闭环；
- 真实试用证明缺失会导致产品不可用；
- 属于数据安全 / 科研准确性的必要修复。

---

# 264. 产品冻结后的变更原则

MVP 开发开始后：

### 可以调整

- 默认页数；
- Prompt；
- Layout 细节；
- Theme；
- 文案；
- Figure 检测策略；
- UI 微交互。

### 谨慎调整

- Paper AST；
- Deck AST；
- Revision Tool Contract；
- Project Storage Contract。

### 原则上不新增

- 通用 Agent 功能；
- Shell；
- MCP；
- 插件系统；
- 云同步；
- 多人协作；
- 通用 PPT 编辑器能力；
- Review 论文工作流。

---

# 265. MVP 产品闭环

最终首版闭环应该保持非常简单：

```text
上传生物医学研究论文 PDF
        ↓
输入一句可选生成要求
        ↓
自动生成完整科研 PPT
        ↓
查看 Figure / Source
        ↓
自然语言或少量直接编辑调整
        ↓
Undo / 恢复
        ↓
导出 PPTX
```

用户不需要理解：

- Pi Agent；
- Tool Calling；
- Paper AST；
- Deck AST；
- Provider Protocol；
- PptxGenJS；
- OPFS。

这些都属于产品内部实现。

---

# 266. 首版产品最终定位

> **Paper2PPT 是一个面向生物医学原创研究论文的 Local-first AI Presentation Workflow。**

它不是通过“更多 AI 功能”取胜，而是通过以下能力形成差异：

```text
理解生物医学研究逻辑
+
理解 Figure / Panel
+
维护 Claim–Evidence–Source
+
生成适合科研汇报的故事结构
+
允许可控、局部、可撤销的 Agent 修改
+
最终输出真正可编辑的 PPTX
```

这就是首版产品应保持的核心边界。
